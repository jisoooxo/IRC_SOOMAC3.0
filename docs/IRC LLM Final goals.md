## 1. 다음 담당자가 시작하는 순서

1. handoff §1의 순서로 읽되 이미 읽고 hash가 같은 큰 보고서는 매번 다시 읽지 않는다. 첫 묶음은 BATCH01(GL01→GL02→GL03)이다.
2. 현재 Goal의 입력·허용 수정 파일·완료 조건·승인 상태를 기록하고 현재 branch/status와 함께 사용자에게 짧게 보고한다.
3. 한 번에20–40분 내 저장 가능한 작업 단위로 쪼갠다. 이는 운영 목표이며 완료 시간 보장이 아니다. 긴 데이터 검수는 명시적 ID 범위 shard로 나눈다.
4. 작업 전과 결과 회수 직후 체크포인트를 갱신한다. 한 번의 긴 모델/명령 호출이 중간 저장 없이 오래 지속되지 않도록 범위를 제한한다.
5. Goal 완료 시 체크포인트와 짧은 진행 보고를 남긴다. 승인된 묶음 안에서는 선행 조건·잔여 사용량·별도 승인 경계를 확인한 뒤 다음 Goal로 이어간다. 세 번째 Goal 완료 후 멈추며 다음 묶음은 자동 시작하지 않는다.

| GL09 / GL03·GL06 | W3/W4 Response: 빈확인100행·실행범위16행 및 fixture 재심, 자연스러운 연결/이벤트/사실성 | 같은 규격의 ledger/언어/편향 검사. 단답·장문·권유 어느 쪽도 획일 강제하지 않음 |

각 데이터 Goal은 여러 사용량 창에 걸칠 수 있다. 작업 단위별 `source hash + split + family/ID 범위 + 처리수 + 다음 ID`를 기록한다. 끝난 shard를 단순히 계정을 바꿨다는 이유로 재검수하지 않는다. 입력/계약이 바뀌면 영향받는 shard만 재검증한다. 순차 실행을 기본으로 하되 독립 검수자를 필요 범위만 호출한다.

## 3. 최종 동작 계약 — 사용량·중단·재개

### 3.1 중단 규칙

1. 신뢰할 수 있는 사용량 표시를 실제로 읽을 수 있을 때만 잔량·갱신 시각·확인 시각을 기록한다. 사용자가 제공한 값은 제공 시각을 붙인다. UI 값이 도구에 없으면 UNKNOWN이며 남은 토큰을 지어내지 않는다.
2. **아래 시작 프롬프트를 사용자가 제출하면 조건부 중단 승인으로 취급한다:** 실제 확인된 해당 사용량 창의 잔량이25% 이하이거나, 사용량/인증 오류가 발생하거나, 잔량을 확인할 수 없는 상태로 한 실행 구간이45분에 도달하면 새 작업/worker를 시작하지 않고 체크포인트 후 멈춘다. 25%가 남아도 다음 큰 작업을 마칠 수 있다는 보장은 없다.
3. 이미 진행 중인 짧고 안전한 읽기/테스트의 결과를 회수하되, 중단을 이유로 학습/데이터 이동/원격 작업/사용자 프로세스를 강제 종료하지 않는다. 장기 작업은 로그·출력·프로세스 ID와 생존 상태를 남기고 감시 중단과 작업 취소를 구분한다. 모델 서비스가 갑자기 차단되면 마지막 저장 이후 기록을 남기지 못할 수 있음을 인정한다.
4. Goal 도구가 있으면 지원되는 상태/중단 수단을 사용한다. 조건부 중단에 해당하면 사용자 승인에 따른 pause로 처리하되 제품이 강제 사용량 제한 상태를 부여한 경우 이를 우회하거나 pause로 덮지 않는다. 미완료를 complete로 바꾸지 않는다. 도구가 없으면 문서상 중단 상태만 기록하며 실제 Goal을 일시정지했다고 주장하지 않는다.
5. 중단 조건에 걸린 뒤 자동 재시도·새 worker·새 Goal 시작·한도 초기화 대기를 반복하지 않는다. 사용자가 재개하면 같은 묶음의 다음 단계부터 진행한다. Goal이 진짜 끝났을 때만 complete로 표시한다. 정상 완료 시 승인된 묶음의 남은 Goal은 이어가되 묶음 끝에서는 다음 묶음 승인을 요청한다.

원인: 사용량 소진은 정확히 예측하거나 항상 사전에 감지할 수 없고, 중단 뒤 최종 정리 응답조차 불가능할 수 있다.
결과: “끊기기 직전에 저장”만 믿지 않고 작업 전후마다 재개 정보를 디스크에 남긴다.

### 3.2 저장 규칙

진행상태 정본은 기존 외부 작업장 `final/goals/` 아래에 둔다. 외부 쓰기가 불가능하면 저장소의 무시된 작업경로에 임시 기록하고 사용자에게 실제 경로와 미동기화 상태를 알린다. 권한 우회는 하지 않는다.

| 파일 | 필수 내용 |
|---|---|
| `goals/GOAL_INDEX.md` | GL01~15 상태, 현재 BATCH/Goal, 묶음 내 완료수·남은Goal, 완료증거, 다음선행, 실행구간 시작/최종갱신시각. 과거 감사와 새 구현 완료 분리 |
| `goals/GLxx/STATE.md` | 목표/허용범위·branch/HEAD/dirty 파일·입력hash·완료/진행/미시작·한도정보의출처/UNKNOWN·승인범위 |
| `goals/GLxx/WORKLOG.md` | 작업 시작/끝시각, 실제변경, 실행명령/exitcode, 실패·판정·독립검수, 산출물경로·hash |
| `goals/GLxx/NEXT.md` | **다음 한 단계**, 사용할파일/ID/명령·기대결과·실패시중단조건, 진행중프로세스·미완료쓰기·재실행안전성 |
| `goals/GLxx/manifest.json` | dataset shard/예시/평가/patch의 입력/출력 identity, 이미끝난범위·다음범위, 변경된계약에따른재검증범위 |

작업을 시작하기 전에 NEXT에 의도와 정확한 대상을 적고, 끝난 뒤 실제 결과로 갱신한다. 긴 명령 앞에는 출력을 파일에 남기는 경로와 재시작 가능 여부를 적는다. 자동 commit/push·stash·reset은 하지 않으며 사용자 변경과 에이전트 변경을 파일/patch로 구분한다. ‘안전한 저장점’은 Git clean을 강제로 만드는 것이 아니다.

### 3.3 멀티에이전트 사용량 관리

기본은 조정자1명이며 독립 교차검수가 필요한 작은 범위에 worker 최대1명을 추가한다. 대형 전체 보고서/코드/데이터를 모든 worker에 반복 전달하지 않는다. 실제 권한·설정으로 요청 모델을 확인하며 사용할 수 없으면 대체 모델을 몰래 선택하지 않는다. worker마다 제한된 파일/행ID·완료조건·결과파일을 주고, 완료 결과를 회수한 뒤 소유권과 도구 규칙에 따라 정리한다. 무조건5개를 동시에 돌리는 감사는 하지 않는다. 명시적 사용자 요청으로 병렬 규모를 늘리면 사용량/중복변경 위험을 먼저 보고한다.

### 4.1 첫 실행 — BATCH01(GL01→GL02→GL03)

```text
이번 범위는 현황 동결→oracle 확정→평가기 교정과 테스트이다.
GL03 완료 후 멈추고 BATCH02는 자동 시작하지 마라. 실패를 완료로 처리하지 마라.
작업 전 final/goals/에 STATE·WORKLOG·NEXT와 index를 만들고 작업 전후 갱신하라.
실제 확인된 계정 잔량25% 이하, 사용량/인증 오류, 또는 잔량UNKNOWN 상태로

잔량을 추측하지 말고 강제 제한을 우회하지 마라. 이 조건이면 지원되는 Goal 중단
수단을 사용하되 완료하지 않은 Goal을 complete로 표시하지 마라.
갑작스러운 차단에 대비해 매 작업 전후 저장하고 중단 후 자동 재시도하지 마라.
기존 멀티턴/history와 사용자 변경을 보존한다. 전면 재감사·새학습·원격취소·

완료/중단 시 실제 상태, 저장경로, 다음 한 단계만 명확히 보고하라.
```

### 4.2 다음 묶음 또는 중단 재개

```text
IRC LLM Final goals.md와 final/goals/GOAL_INDEX.md를 읽어라.
내가 지정한 BATCH의 GL별 STATE·WORKLOG·NEXT를 읽고 미완료 지점부터 순차 진행하라.
```

사용자는 위 프롬프트와 함께 `BATCH02 시작` 또는 `BATCH03의 GL08부터 재개`처럼 지정한다. 사용자가 GL 하나만 명시하면 그 범위만 진행한다. 묶음/Goal 번호가 없고 index에도 활성 작업이 없으면 하나만 질문한다. 존재하지 않는 작업 결과나 체크포인트 파일을 읽었다고 가정하지 않는다.

## 5. 완료 정의와 기록

이 분할은 최종 plan W0~W9와 G0~G4를 빠짐없이 수행하기 위한 운영 방식이다. 각 Goal의 완료와 프로젝트 최종 완료는 별도이다. 문서 작성 시 GL01도 아직 시작하지 않았으며, final/goals/의 실행 파일은 실제 착수자가 만든다. 이 문서 자체는 학습/배포 승인 또는 새 Goal 활성화가 아니다.

용어: Goal은 제한된 작업 목표, gate는 채택 합격 조건, checkpoint는 재개 가능한 파일 기록이다. (내가 의역해보자면, 계정이 끊겨도 다음 사람이 ‘어디까지 했고 지금 무엇을 해야 하는지’를 추측하지 않게 하는 방식이다.)
