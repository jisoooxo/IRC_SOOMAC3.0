### 0.1 과잉 교정 금지

모델의 판단·대화 능력, 멀티턴, state 기반 일관성을 개선한다. 전부 초기화, 전부 재학습, 무조건 재확인, 모든 오인식을 거절, 모든 추천을 현재 단계로 축소하는 방식은 채택하지 않는다. 성공 사례도 실패 사례와 함께 보존하여 같은 조건으로 비교한다.

### 0.2 History는 유지하고 오염 대응은 프롬프트에만 명시한다

기존 history 저장·전달·역할·순서·창 크기는 이번 오염 대책 때문에 바꾸지 않는다. history 삭제·마스킹·선별·요약·창 축소·한 턴 추론 회귀를 하지 않는다. 오염 판별용 Python 키워드, 별도 분류 모델, 새 provenance/state 필드, 신뢰도 태그를 추가하지 않는다. 이전 계획에 있던 이런 제안은 **취소**한다.

프롬프트는 과거 Assistant의 추측·오답을 사용자 확정 사실로 승격하지 않도록 명시한다. 사용자 원문, 최신 명시적 변경, 현재 검증된 state, 실제 실행 결과를 구분한다. 사용자가 과거 오답을 인용하여 정정하는 문맥은 그대로 이해해야 한다. state도 새 사용자 변경으로 갱신될 수 있으며, 과거 state를 무조건 고집하지 않는다. 물리적 실행 이력은 자연어만으로 되돌릴 수 없다.

**학습 데이터 정제와 Runtime history 보존은 다른 작업이다.** 잘못된 정답 행을 학습에서 제거하는 것은 허용한다. 오답 Assistant 발화가 포함된 history라도 올바른 정정 행동을 가르치는 의도적 사례라면 유지할 수 있다. 그런 사례를 런타임에서 지우는 구현으로 바꾸지 않는다.

### 0.3 데이터는 유지·수정·삭제·보류를 실제로 집행한다

기존 데이터 전체 보존 학습도, 전체 폐기도 하지 않는다. 중복과 근거 없는 정답, 의미 모순을 행 단위로 판정한다. 삭제 판정 행은 새 train/validation/test에서 **제거**한다. 원본은 복구용 보관소에 별도 보존하되 학습 경로에서 읽히지 않게 한다. 근거가 부족한 행은 활성 데이터에서 제외하고 보류한다. 삭제 목록과 이유를 숨기지 않는다.

### 0.4 프롬프트는 엄격하게, 답변은 자연스럽게

입출력 필드, 복합 의도, 긍정·부정, 수락 대상, 주문/선호/제약, 현재/미래 단계, 시작/완료의 경계를 명시한다. 문장을 하나로 고정하거나 특정 단어가 있으면 같은 결정을 내리게 하지 않는다. 프롬프트·데이터·실제 모델 입력·평가기의 계약은 같아야 한다.

### 0.5 Python 문장 생성은 10월 11일 기준

10월 11일 이후 추가된 Python 고정 응답은 **제거하고 모델 응답 경로로 되돌린다.** 안전 검증·상태 전이·ROS 발행·중복 방지는 제거하지 않는다. 새 안내를 fallback이라고 이름만 바꾸어 Python 고정 문장으로 남기지 않는다. 추천은 넓은 요청이면 남은 코스, 좁은 요청이면 그 범위를 다룬다.

| “나머지만 담아줘 / 그거 빼고” | 이전 사용자 대화·현재 주문·후보·직전 질문·pending으로 제외 대상과 나머지를 해석. 기존 수량 유지 | 실행 의도는 해당 맥락에서 별도 판단. 대상이 유일하지 않으면 명확화, 미래 단계 조기 실행 금지 |
| 무대상/이미 완료/중복 실행 | 새 가짜 주문 생성 금지 | 임의 plan 금지, 필요한 설명만 |

같은 문장이 다른 pending에서 다른 의미가 되는 최소 대조쌍을 만든다. 선택과 실행을 한 질문으로 합치는 계약은 문구만으로 구현하지 않는다. 기존 전이로 입증되지 않으면 선택/실행 의미를 구분하되 이미 주어진 명시적 즉시 실행을 다시 묻지 않는다.

2026-10-26 사용자 정정: **수량을 생략했다는 이유로 기존 확정량을 normal로 덮어쓰지 않는다.** 새 명시 수량이 우선이며, 이번에 수락·참조하는 유효 후보의 수량이나 기존 확정량은 해당 대상에 유지한다. 둘 다 없는 새 선택에만 normal을 기본값으로 사용한다. 이 기본값은 commit/실행 승인을 뜻하지 않는다. Python에 “나머지만/그거 빼고” 키워드 규칙을 추가하지 않고 Decision이 보존된 history와 state를 보고 판단한다.

### 3.3 직원형 대화와 남은 코스 추천

넓은 “기분에 맞춰 추천해줘/뭐 먹을까”는 남은 선택 가능한 코스의 조합을 제안한다. 소스가 마지막에 투입되더라도 미리 추천·선택할 수 있다. “면 양만/이번 육류만”은 요청 범위를 유지한다. 이미 확정된 항목은 유지 항목으로 설명하며 proposal 변경분과 구분한다. 모든 빈 필드를 반드시 채우는 추천은 아니다.

“매운 걸 못 먹어”를 저장 보고로 끝내지 않고 적합한 후보가 검증되면 “매운맛을 피하고 싶으시니 크림으로 추천드릴게요. 이 구성은 어떠세요?”처럼 이유와 제안을 연결한다. 유제품 제한이면 같은 예시를 사용할 수 없다. 게살 제한이면 게살을 제외하고 허용된 소시지 등을 제안한다. 특정 메뉴가 모든 경우의 정답이 되어서는 안 된다.

현재 단계 도착 시 선호-only라면 관련 후보를 제안한다. 이미 확정된 주문이 있으면 같은 선택을 다시 받지 않고 최신 주문의 실행 확인으로 연결한다. 미확정 추천은 과거 확정 사실처럼 말하지 않는다. 관련 없는 고기 선호를 토핑 단계마다 반복하지 않는다. 모든 응답에 억지 권유를 붙이지 않으며 거절·종료·명확화 상황에는 그 의도를 우선한다.

### 3.4 물리 상태와 완료 표현

선택, 대기, 발행, 시작, 제어 종료, VLM PASS/FAIL, 정책상 진행, 최종 완료를 구분한다. VLM FAIL 하나를 전체 성공으로 바꾸거나 정책상 진행을 관측상 성공이라고 말하지 않는다. `trusted=false`와 `policy_success`를 확인 결과처럼 표현하지 않는다. 완료 주장에는 대상 재료/소스 값과 단계가 맞아야 한다.

이미 담은 양파를 빼 달라는 요청은 물리 제거 성공으로 state를 조작하지 않는다. 아직 미실행인 변경 가능한 주문만 수정하고 이미 담은 항목은 불가능한 이유를 설명한다. 소프트 선호 철회와 강한 제한 철회, 주문 취소, 물리 회수는 서로 다른 행위이다.

ROS topic/메시지/자동 진행 순서, lid와 마지막 sauce 계약, 로봇 실행 중 STT 차단, TTS 재수음 방지는 유지한다. 상태 질문은 기존 대화 가능 구간에서 처리한다. 실제 ROS 발행은 승인된 실물 검증 단계 전에는 mock으로 검사한다.

### 4.3 단계 이벤트의 모델 응답

신규 user message를 가짜로 만들지 않는다. 기존 이벤트·state를 사용하여 사용자 발화 기반 요청과 이벤트 기반 요청을 명시적으로 구분한다. 입력에 현재 section, 최신 confirmed order, pending 종류/대상, 유지된 선호·제약, 실행 결과와 VLM 증거, 검증된 후보가 필요한 만큼 전달되는지 확인한다. 기존 필드로 표현 가능한지 먼저 검사하며 전역 state field를 늘리는 것을 기본 해법으로 삼지 않는다.

선호-only에서 실질적 새 추천이 필요하면 Recommendation의 검증된 후보를 먼저 준비하고 Response가 설명한다. Response가 독자적으로 주문 후보를 확정하지 않는다. 후보가 없거나 모델 출력 검증이 실패하면 기존 Oct 11 fallback 경로로 안전하게 돌아간다. 이벤트가 연속 도착해도 같은 확인 질문·명령을 중복 생성하지 않는다. 기존 “Response를 호출하지 않는다” 테스트는 새 목표에 맞게 수정하되 제어·rollback 테스트는 유지한다.

### 4.4 필드·scope·복합 의도 주의점

`build_recommendation_scope`가 이미 현재+미래를 계산하는 부분과 실제 프롬프트/데이터가 한 단계에 치우친 부분을 분리한다. 물리적으로 지나간 단계까지 무조건 여는 것은 금지한다. 자연어 “못 먹어”를 소프트 선호로 내려 강한 제한을 잃는 경우는 Decision/schema/정규화 경로를 함께 재현한다. 단순 함수 삭제로 제약 자체가 사라지면 실패다.

옛 8필드 복원 요구는 별도 계약 항목이다. 현재 `skip_current`만 schema에서 삭제하지 않는다. 명시적 선택 단계 생략(S08)과 빈 주문의 무대상 실행(S35)을 기존 필드로 구분 가능한지 테스트한다. 불가능하면 기존 작동 필드를 유지한 채 사용자에게 결정 항목으로 남긴다. 이 결정이 고정 응답 제거와 프롬프트 교정을 불필요하게 막지 않게 한다.

`commit+recommendation` 조기 return, 거절+대체 주문, 강한 제한 여러 개 철회, 부분 수락 후 후보 소실, pending과 next_prompt 불일치는 각각 독립 테스트로 만든다. 새 자연어 guard로 덮지 않는다.

### 4.5 B1 — 사용자 선호 턴의 호출 계약

독립 계획 검수가 남긴 B1을 W2의 필수 산출물로 반영한다. 아래는 구현할 계약이며 현재 동작 완료 선언이 아니다.

| 맥락 | 호출·질문 계약 | 금지 |
|---|---|---|
| 선호-only 사용자 턴 | 모델이 문맥상 적절한 추천 필요를 판단하면 기존 recommendation 필드로 요청하여 Recommendation→validator→Response를 거친다. 그렇지 않으면 선호를 자연스럽게 받아주고 필요한 선택 질문만 한다 | Python 취향 키워드로 강제 추천, 매 턴 저장 단답, 선호를 주문·실행으로 승격 |
| 단계 진입 이벤트 | 기존 이벤트/state로 현재 관련 선호와 후보를 판단한다. 새 추천이면 검증된 후보를 먼저 마련한다 | 가짜 user 발화, 새 ROS 명령 |
| 기존 추천 pending | 최신 state/제약과 유효성을 재검증한 후보를 설명·수정·선택한다 | 유효 후보가 있는데 불필요하게 재생성, 선택을 실행 수락으로 승격 |
| 확정 주문 | 관련 주문을 다시 선택시키지 않고 현재 실행 가능 대상의 확인 또는 이미 받은 명시 실행을 처리한다 | 중복 선택·중복 실행 |
| 거절·종료·명확화 | 현재 의도에 맞춰 설명/질문하며 추천을 강제하지 않는다 | 거절 뒤 계속 권유, 모호한 동의로 실행 |

225109 T11/T13형 사용자 턴과 이벤트 F12를 따로 시험한다. 새 후보에는 검증된 Recommendation 근거가 있어야 하고, 선호-only 단계의 plan=0과 다음 질문의 적합성을 함께 확인한다. “많이 좋아함”만으로 high를 강제하지 않는다. 기존 필드로 구현 가능한 경로를 우선하며 전역 state 필드를 추가하지 않는다.

### 4.6 B2 — 명확화와 실행 pending의 우선순위

미해결 주문 정정의 명확화는 이전 주문에 대한 실행 확인보다 우선한다. 기존 pending의 보관과 이번 턴 무엇을 묻는지는 구분한다. Response의 질문 의도를 기존 turn-local 정보와 맞추고, 명확화 직후의 모호한 “응”만으로 옛 high 주문을 실행하지 않는다. 사용자가 “둘 다 조금”처럼 대상을 명시하면 최신 주문으로 확인을 갱신하고 명시적 실행 요청은 불필요하게 다시 묻지 않는다.

W2 완료 조건에 `225109 T8 → 모호한 동의` 및 `T8 → T9/T10 명시 정정·실행` 대조를 추가한다. 정상 execution pending 수락 성공도 보존한다. history/pending을 무조건 삭제하거나 자연어 키워드 guard로 덮지 않는다.

GL04 실제 검증 보완: 기존 어댑터는 history를 받았는데도 명확화 뒤 `응`을 execution accept로 오판했고, 최소 예시-only 교정도 실패했다. turn-local next_prompt만으로 다음 턴의 질문 목적이 보존되지 않아 **기존 execution pending의 선택적 question_type=clarification**을 추가했다. 새 SessionState/Decision 최상위 필드가 아니다. 대상·source·기존 주문·history는 유지하고, confirmation 권한 불일치만 같은 Decision의 기존 1회 repair로 돌린다. 실패하면 clarify, 명시적 commit이나 유효한 현재 주문 정정은 정상 검증 경로로 처리한다. 새 Python 자연어 판정은 없다. 강한 제한 여러 개 철회는 기존 pending의 deferred 목록으로 각각 확인한다. 전체 few-shot·새 학습은 GL06 이후로 구분한다.

## 5. 엄격한 프롬프트 작성·검증 기준

### 5.1 공통 규칙

1. 실제 입력 필드와 출력 schema, null/빈 배열/none의 역할을 정확히 설명한다. 존재하지 않는 필드를 모델에 요구하지 않는다.
2. history는 문맥으로 읽되 과거 Assistant 주장만으로 사용자 선호·제약·주문·실행 완료를 만들지 않는다. 최신 사용자 정정과 실제 state를 함께 판단한다.
3. 조사 생략·반말·존댓말·어순 변경·오탈자·반복·부정 범위를 뜻으로 해석한다. 입력 문체와 별개로 출력은 자연스럽고 일관된 존댓말이다.
4. 수음이 불명확하면 유일한 지시 대상이 있는지 확인한다. 충분히 명확하면 수행하고 진짜 모호할 때만 대상 중심 질문 한 개를 한다. 깨진 발화를 자동 수락/거절하지 않는다.
5. 예시는 의미 대조쌍으로 넣는다. 예시 문장/메뉴/단어를 그대로 외워야만 성공하는 계약을 만들지 않는다.

### 5.2 Decision 필수 대조

“많이 좋아해”와 “많이 먹고 싶어”, 선호 철회와 주문 취소, 제한 철회와 실제 재료 제거, 추천 수락과 실행 수락, 일반 주문과 즉시 실행을 구분한다. 한 발화의 제약+추천, 번복+실행, 거절+대체 주문을 빠뜨리지 않는다. assistant 추정만 있는 선호와 실제 사용자 발화가 있는 선호를 구분한다. 오래된 주문을 history에서 복원하지 않는다.

### 5.3 Recommendation 필수 대조

넓은 요청의 기본 범위를 남은 코스로 명시한다. 현재 단계가 입력에 있다는 이유만으로 단일 단계로 좁히지 않는다. 좁은 요청에서는 불필요한 다른 재료를 바꾸지 않는다. 이유는 실제 선호·제약·요청에 연결하고 의학적 효능을 지어내지 않는다. 이미 선택된 값 유지, 미래 후보 수정, 강한 제한 제외, 모든 후보 불가를 각각 다룬다.

### 5.4 Response 필수 대조

“저장했어요”만 반복하는 응답 대신 필요한 상황에서 근거+관련 제안/질문으로 이어진다. 단, 기존 후보 없는 새 확정 추천, 질문 없는 종료 의도에 권유 강제, 모든 턴 과거 선호 반복은 금지한다. “선택했어요/담기 시작해요/완료됐어요”를 실제 상태에 맞춰 구분한다. 변경된 일부 항목과 실행 확인할 전체 항목이 다르면 그 차이를 명확히 말한다. 부정문 속 위험 재료 언급을 위험 추천과 혼동하지 않는다.

### 5.5 입력 동일성 검사

Runtime serializer가 만든 실제 입력과 학습 messages를 동일 사례로 비교한다. system prompt 버전/해시, 역할, history 순서·길이, state 필드, special tokens/chat template, truncation, loss mask를 기록한다. 현재 history 20 messages를 20 user-assistant 쌍으로 오해하지 않는다. 긴 프롬프트 때문에 핵심 state/최신 발화가 잘리는 사례를 실제 tokenizer로 검사한다. 문자열 템플릿만 통과했다고 의미 검수가 끝난 것으로 보지 않는다.

20 messages는 기본 상한이다. Decision의 기존 token-overflow 시 입력 사본의 과거 메시지를 줄이는 동작도 동결·기록한다. 새 프롬프트가 길어져 실제 전달 history가 감소하는지 비교하되, 이 기존 처리를 새 오염 대책으로 강화하거나 제거하지 않는다.

### 5.6 Session·멀티턴 few-shot — 필수 산출물

**선정 기준 보완:** 규칙·few-shot은 사용자 계약과 독립 oracle, 복합 선행턴의 의미·발화 전후 필드, 실제 입력/출력 schema에 맞춰 설계한다. 기존 adapter A/B는 개발 진단으로 활용할 수 있으나 새 adapter의 최종 합격/불합격 근거는 아니다. 특정 기존 모델의 오답마다 예시·Python 규칙을 늘리지 않는다. 학습 messages의 prompt/예시/serializer 버전을 함께 맞추고, 최종 채택 모델이 준비된 후 동결 holdout으로 재검증한다. 학습하면 자동 해결된다고 보장하지 않는다.

사용자 추가 요구(2026-10-26): **세 Agent 각각에 소수 예시(few-shot)를 설계한다.** 단문 입출력뿐 아니라 이전 대화·현재 state·pending·현재 발화·Agent 정답이 연결되는 세션 예시를 포함한다. 실제 적용과 효과 측정은 W2/W5 작업이며 이 계획 추가로 적용 완료가 되는 것은 아니다.

1. 예시별 source/family ID, 계약 버전, session/history/state, 현재 turn, schema-valid 출력, 기대 상태/권한을 기록한다. 설명용 근거는 감사 metadata이며 모델에 사고과정 출력이나 새 Runtime 필드를 요구하지 않는다. 실제 Agent serializer를 사용한다.
2. **데모와 실제 session을 분리한다.** 독립 사례라고 표시하고 현재 recent_history·주문·선호에 합치지 않는다. 예시의 알레르기/주문이 현재 사용자 사실로 복사되지 않는지 검사한다. 이벤트는 event/state로 표현하며 가짜 user 발화로 만들지 않는다.
3. 같은 입력·가중치·생성 설정에서 0-shot과 소수 예시 후보를 비교한다. 예시 수는 개발용 평가의 효과/비용으로 결정한다. 예시 선택용 dev와 최종 test를 분리하며 test/challenge/holdout 원문·정답·같은 family를 prompt로 유출하지 않는다.
4. 같은 문장의 다른 pending/state 대조와 성공 멀티턴을 포함한다. 예시 순서·메뉴 치환에 따른 편향을 비교하며 특정 단어·정답 위치를 외우거나 현재 실패만 과대표집하지 않는다.
5. 학습/추론의 예시 버전·역할·구분자·tokenizer/template를 맞추거나 의도적인 차이로 명시하여 A/B한다. 예시까지 반복 정답으로 loss를 주는지 masking을 검사한다. 예시 원본·prompt hash·serializer 결과·평가 원장을 보관한다.

| 예시군 | 세션 맥락과 발화 | 올바른 대조 |
|---|---|---|
| FS01 수락 | 후보 선택 질문 / 실행 확인 / 대상 없는 상태에서 “응, 그걸로” | 후보 선택·실행 수락·명확화 구분. 같은 글자에 같은 commit 금지 |
| FS02 번복 | 양파 high·버섯 low → “둘 다 조금” → 실행 동의 | 최신 low/low와 질문/plan 일치. 이전 high 복원 금지 |
| FS03 기억 | 매운맛 선호 또는 회피 → 중간 주문 대화 → extra 도착 | 기억과 검증된 후보로 권유. 철회/확정주문/유제품 제한 변형 대조 |
| FS04 추천 | 게살 allergy+육류 많이 / 넓은 식사 추천 / 면 양만 요청 | 제약·수량·범위·미래주문 보존. 크림/치즈 고정답 금지 |
| FS05 근거 | assistant 오답 후 정정 / clarify+옛 pending / VLM policy_success | history 유지·최신 근거 우선, 모호한 동의 실행 및 관측 성공 조작 금지 |

Decision은 구조 판단, Recommendation은 유효 후보·유지항목·변경분·이유, Response는 검증된 사실에서 자연스러운 설명/질문으로 이어지는 출력을 가르친다. Response가 새 주문·추천 확정·ROS 명령을 독자 생성하는 예시는 금지한다. 모든 예시군을 매 호출에 붙이지 말고 Agent별 필요한 소수 세트를 검증하여 선택한다.

### 5.7 토큰 예산 증액 — history를 희생하지 않는다

few-shot으로 입력/출력이 늘면 **필요한 토큰 예산 증액도 W2/W5의 명시적 작업**이다. max_new_tokens 증액은 입력 context나 학습 길이 확장과 다르다. 2026-10-26 소스 확인값은 Decision 입력8192, 생성 상한 Decision1024 / Recommendation1024 / Response512이다. 이는 앱 설정이지 Base의 지원 context 또는 모든 경로의 입력 상한 증거가 아니다. 착수 시 실제 loader/tokenizer/trainer와 재대조한다.

| 분리할 예산 | 측정·변경 조건 | 완료 조건 |
|---|---|---|
| 입력 prompt/context | 규칙·few-shot·history·state·현재발화·template별 토큰, Agent별 p50/p95/p99/max, 지원 한도 | 입력+허용출력이 한도 이내. 예시 추가로 state/최신발화/기존 전달 history가 잘리지 않음 |
| 출력 generation | JSON 종료·필드 누락·finish reason·문장 잘림, Agent별 상한 비교 | 복합 의도/추천/응답 완결. 상한 증액을 강제 장문화로 해석하지 않음 |
| 학습 sequence | prompt+target+special tokens, truncation·packing·loss mask를 실제 trainer에서 검사 | 정답 잘림0, 예시 정답만 학습하는 오류0. 과거4096 검사 기록을 지원 context로 오인 금지 |
| GPU·지연 | prefill·생성·전체 턴·다중Agent 지연 p50/p95, peak VRAM, batch/accumulation/throughput·OOM | 증액 전후 품질/지연/메모리 표. 운영 허용 예산을 먼저 정하고 초과 시 채택 보류 |
| 배포·재현 | Runtime/trainer/evaluator/preflight/Docker 설정·prompt hash | 0-shot/후보별 원장, rollback, 동일 조건 실제GPU 비교 |

예시 때문에 기존 overflow가 더 자주 history를 덜 보내는 후보는 실패이다. 먼저 예시 중복/불필요 지시를 줄이고 필요하면 지원 범위 내 입력·학습·출력 예산을 각각 늘려 재측정한다. 한도/VRAM을 넘으면 임의 확장·조용한 history 삭제로 우회하지 말고 예시 세트/실험 규모/운영 선택을 보고한다. 장문history·큰state·복합제약·이벤트 혼합의 최악 사례도 검사한다. 실제 학습·이미지·운영 변경은 기존 승인 경계를 따른다.

원인: few-shot은 의미 대조를 보여 줄 수 있지만 토큰 비용과 예시 편향도 늘릴 수 있다.
결과: 예시 추가·토큰 증액을 자동 성능 개선으로 간주하지 않고 history 보존·출력 완결성·GPU 비용으로 검증한다.

## 6. 데이터 정제·재구성 명세

### 6.1 행별 판정과 삭제 절차

| 판정 | 기준 | 새 학습본 처리 |
|---|---|---|
| KEEP | 입력·상태·정답·의도가 일관되고 필요한 사례 | 유지 |
| FIX | 원 로그/계약에서 올바른 정답을 확정 가능 | 정정 전후와 근거 저장 후 교체 |
| DROP | 완전 중복, 근거 없는 target, 복구 불가능한 의미 모순, 학습 목적 없는 오염 | 활성 모든 split에서 제거 |
| HOLD | 정답 판단 근거 부족/검수 의견 불일치 | 별도 격리, 학습·평가 제외 |

원본 ID, source path/hash/line, episode/family, agent, 원 split, 판정, 사유 코드, 근거, 검수자, 수정 target hash, 새 split을 ledger에 기록한다. 원본 cold archive와 이전 봉인 release는 덮어쓰지 않는다. 원본의 영구 삭제는 별도 정확한 대상 확인 없이는 하지 않는다. 학습에서 DROP하는 것은 필수 집행이며 원본을 보관한다는 이유로 다시 섞지 않는다.

### 6.2 중복·누수

입력 state/history/pending/target까지 같은 완전 중복은 대표 하나만 남긴다. 같은 발화라도 pending/물리 상태가 달라 정답이 다른 행은 삭제하지 않는다. 문장만 바꾼 같은 episode/family를 split 사이에 나누지 않는다. 의역·부정 반전·메뉴 치환 전 family 단위로 분리하고 dev/test를 먼저 동결한다. 과다 반복 템플릿은 분포를 보고 줄이며 소수 안전 사례는 빈도만으로 제거하지 않는다.

### 6.3 확인된 우선 검수 대상

Response RV12-S0581~0680 100개 train 행은 실제 주문/대상 없는 기존 양파 실행 확인 target 문제를 원본에서 재확인하고 FIX 또는 DROP한다. 과거 Recommendation 703행 중 물리 단계 3개 이상 조합이 0이었던 분포를 broad 요청 기준으로 보강한다. 단순 필드 개수(면 종류+양)를 물리 단계 개수로 세지 않는다. 과거 439개 history 문법 후보를 전부 오답 target이라고 자동 삭제하지 않는다. `none`도 취소 명령과 persisted state를 구분하여 정상 preselected 거절 사례를 잘못 제거하지 않는다.

### 6.4 새 데이터 생성 방법

1. 실제 실패 로그를 원본 입력/모델 raw/정규화/state 전후/응답 경로/ROS·VLM 증거로 분해한다. 출력이 실패했다는 이유로 입력 로그를 지우지 않는다.
2. 정답은 원래 실패 출력 복제가 아니라 §3 계약에서 작성한다. 올바른 과거 성공 사례와 최소 대조쌍을 함께 만든다.
3. 메뉴, 수량, 선호, 제약, 단계, pending, 문체, 순서, history 길이를 바꾸되 상태 전이를 먼저 생성하고 그에 맞는 자연어를 작성한다.
4. 자동 schema·state 검증 후 독립 의미 검수를 수행한다. 생성자와 채점자가 같은 잘못된 가정을 공유하지 않도록 원본 근거로 조정한다.
5. Agent별·split별 전수 ledger를 완성한다. 총수=KEEP+FIX+DROP+HOLD와 새 행 수/대표 중복 수를 대조한다. 미검수 행은 release에 넣지 않는다.

### 6.5 언어·편향 검사표

| 축 | 포함해야 하는 대조 |
|---|---|
| 조사/받침 | 양파를·버섯을·소시지를, 병렬 연결, 수량 결합, 주어 생략 입력과 완결된 출력 |
| 문체 | 반말/존댓말/단문/장문 입력, 일관된 자연스러운 존댓말 출력 |
| 의미 | 부정/이중 부정/철회/정정/긍정, “보통 이 정도”와 수량 보통, 좋아함과 먹을 양 |
| 수음 | 해석 가능한 오타/동음 혼동, 정말 불명확한 입력, 외국어 또는 무관 발화; 원음 없는 STT 원인 단정 금지 |
| 분포 | 특정 메뉴·단어·현재 단계·확인 질문·거절·정답 위치·응답 길이에 대한 편향 |

자연스러운 한국어는 규칙 치환만으로 합격시키지 않는다. 실제 읽기 검수와 의미 검수를 분리하고 “권유를 자연스럽게 한다”를 하나의 반복 정답 문장으로 만들지 않는다.

사용자 추가 요구(2026-10-26): 학습 응답은 한 줄 저장 보고로 획일화하지 않는다. 추천/선호 연결 상황에서는 실제 이유와 관련 제안·질문을 자연스럽게 이어가며 필요하면 여러 문장을 사용한다. 짧은 확인·거절·종료는 짧아도 정상이다. 단문=실패/장문=성공이 아니라 정확성과 상황 적합성으로 판정한다. 기존 성공 멀티턴과 같은 문장의 다른 pending/state 대조를 함께 보존한다.

### 6.6 엄격한 편향 감사 — 데이터·few-shot·평가기 공통

평균 점수나 메뉴별 총수만으로 통과시키지 않는다. 원본/KEEP/FIX/DROP/HOLD/새release와 train/validation/test/challenge/holdout, Agent별 분포를 각각 기록한다. few-shot 선택본도 별도 작은 데이터셋으로 검사한다.

| 축 | 필수 집계·대조 | 위험 |
|---|---|---|
| 의도·권한 | 일반주문/즉시실행/선택수락/실행수락/거절/clarify/skip/no-op, 복합의도 | 항상 실행 또는 항상 확인/거절 |
| 재료·수량·범위 | 메뉴/소스·low/normal/high·기본량, 현재/미래/완료, broad/narrow, 허용후보 수 | 크림·치즈 고정답, 현재단계 고착, 무조건 high/normal |
| 기억·상태 | history길이·턴수·session단계·pending, 최신정정/철회/오답assistant/미수락후보/복수제약 | 무history 비율만 조절, 옛취향 재생, 같은 상태 골격 반복 |
| 언어·발화 | 조사·받침·문체·부정·어순·지시어·ASR/진짜모호성·이름/칭찬대상, 답변길이·권유빈도 | 특정 단어 의존, 무조건 저장 단답·장문·권유 |
| 출처·누수·judge | 생성기/템플릿/episode/family·원본/합성, 완전/근접중복, 답위치·예시순서·평가문체 | 의역 split 누수, 생성자-judge 공통오류, 문장 암기·긴답 선호 |

1. **조건부 균형:** 제약상 치즈만 가능한 사례를 억지로 균등화하지 않는다. 동일한 유효 선택 조건에서 메뉴/수량/위치 쏠림을 검사하고 broad 조합과 narrow 보존을 함께 요구한다. 불가능한 조합은 근거 있는 N/A로 남긴다.
2. **교차 셀:** 제약×범위, pending×수락/거절, 정정×history길이, section×물리상태, 문체×의도를 교차 집계한다. 필수 셀별 최소 사례 수·허용 반복률·편차·평가 표본 수를 생성 전에 근거와 함께 동결한다. 미정 기준/누락 셀/사유 없는0행은 완료가 아니다. 희귀 안전 사례는 빈도가 낮다고 제거하지 않는다.
3. **대조·변형:** 의미 유지 어순/조사/문체 변화에는 같은 판단, 부정/철회/pending 변화에는 다른 판단을 요구한다. 메뉴 치환은 물리·알레르기 조건도 맞춘다. 예시 순서 변경·불필요 단어 제거로 지름길 학습을 점검한다.
4. **독립 일반화:** episode/family를 먼저 분리하고 생성 후 누수를 검사한다. 미학습 유효조합과 별도 실발화 holdout을 남긴다. 최종 test로 few-shot을 선택/수정하지 않는다. 오류 수·분모·유형별/최악군 결과·반복실행 변동을 보고하며 작은 표본은 미검증으로 남긴다.
5. **산출물·차단:** `BIAS_MATRIX`, `FEWSHOT_MANIFEST`, `TOKEN_BUDGET_REPORT`, 행별 정제 ledger·독립 재판정을 W2~W5 산출물로 만든다. 생성자의 답을 그대로 judge 정답으로 쓰지 않는다. G0에 분포/누수/필수셀, G1에 judge 양·음 대조, G3에 그룹별 기능/자연스러움/few-shot 대조, G4에 토큰/지연/메모리 검증을 추가한다. 기준 미달을 평균으로 숨기면 채택 불가이다.

원인: 예시·데이터·평가기 모두 같은 표현과 상태에 치우치면 겉보기 점수만 좋아질 수 있다.
결과: 엄격한 편향 검수는 무조건 균등 분포가 아니라 유효 조건별 coverage·누수방지·미관측조합·그룹별 성능을 입증하는 작업이다.

## 7. 평가기 교정과 합격 기준

### 7.1 먼저 고칠 오채점

| 반례 | 올바른 판정 |
|---|---|
| 미승인인데 “담기 시작할게요. 더 넣을까요?” | 시작 허위/미승인 실행 발화 실패 |
| 유제품 제한인데 크림 추천 | 제약 충돌 실패; sauce key뿐 아니라 값 검사 |
| 면만 완료인데 크림 소스 완료 주장 | 대상·단계 grounding 실패 |
| “양파 조금 골랐고 보통 이 정도면 괜찮아요” | 부사 보통을 주문 수량 normal로 오인하지 않음 |
| “게살은 제외하고…” | 제외 설명을 게살 추천으로 오인하지 않음 |
| 명시적 빈 선택 단계 skip | 재료 plan 0이 정상일 수 있음; 무조건 plan 1 강제 금지 |
| “적게/조금” | enum low 문자열이 없다는 이유만으로 실패 금지 |

각 반례의 반대 사례도 넣는다. 금지어가 없다고 완료 환각을 통과시키거나 특정 문장이 있다고 무조건 실패시키지 않는다. 새 채점기가 정상 회귀 사례를 떨어뜨리면 판정 근거부터 재검토한다.

### 7.2 두 종류의 평가를 분리한다

구조 평가는 schema, 메뉴·수량, state 전후, 후보 적용, pending, plan 수/대상, 중복, 물리 변경 가능성으로 판단한다. 대화 의미 평가는 지시어/부정/범위/근거/완료 주장/자연스러움으로 판단한다. 모델 judge는 보조이며 불일치는 원본 증거로 사람이 또는 독립 검수자가 판정한다. 새 의미 평가를 Runtime 자연어 차단기로 이식하지 않는다.

**정규식 문구 검사는 검토 표시이지 데이터 탈락 기준이 아니다 (2026-10-26 GL03 결론).**
- 원인: 조사·표현 조합은 사실상 무한하다. 문구 규칙으로 데이터를 거르면 규칙이 아는 말투만 남는 편향이 생긴다(GL03에서 교차검증 6회 동안 회차마다 새 조사 반례가 나왔다).
- 결과: 아래 세 층으로 나눈다.

| 층 | 무엇으로 | 역할 |
|---|---|---|
| 구조 | `Grade.structural_passed` — plan·state·pending·제한·schema | 합격 판정(blocking) |
| 문구 규칙 | `Grade.text_rule_flags` — `evaluation_v43.TEXT_RULE_CODES` | 검토 후보 표시. **단독으로 DROP 금지.** 안전 관련 표시(무승인 시작·거짓 완료·없는 pending)는 독립 의미 판정 전까지 HOLD |
| 의미 | LLM judge(rubric·구조화 출력) + 사람 라벨 기준 세트 | 기준 세트로 그룹별 오탐·미탐·분모, 안전 사례 재현율을 잰 뒤에만 사용. 불일치는 사람 판정 |

- `passed=True`는 구조와 문구 규칙을 모두 통과했다는 뜻일 뿐이다. 의미 미판정·HOLD 행은 활성 release에 넣지 않는다.
- 문구 표시·judge 탈락률은 문체·조사·길이·Agent 그룹별로 집계해 편향을 감시한다(§6.6).
- 배치: GL07~09(데이터 ledger), GL10(통합 gate), GL11(GPU 결과 판정).

구현 경계: GL03은 위 결과 필드를 제공하지만 기존 `audit_gold_targets.py`는 호환성을 위해 여전히 `passed`로 감사 FAIL과 종료코드를 결정한다. 이 보고서의 FAIL은 자동 DROP 명령이 아니다. GL07~09에서 구조 실패·문구 표시·의미 미판정/HOLD를 각각 ledger에 기록하고, GL10의 release gate에서 의미 미판정·HOLD 제외를 실제 검증해야 한다. `structural_passed=True` 단독으로 최종 채택하면 안 된다.

### 7.3 Release gate

| Gate | 통과 조건 | 실패 시 |
|---|---|---|
| G0 입력·데이터 | 새 release 전 행 schema/참조/필수 필드 검사, 의미 ledger 누락 0, 미해결 행 활성본 0 | 데이터 봉인 금지 |
| G1 평가기 | §7.1 양성/음성 반례 전부 올바르게 판정, oracle 독립 검수 | 점수로 모델 선정 금지 |
| G2 안전·상태 | 동결 필수 suite에서 무승인/중복 plan, 제한 실행, 물리 불가능 변경, 거짓 완료 0 | 후보 채택 금지 |
| G3 기능·대화 | 기존 성공 사례 회귀 0, §8 필수 계약 충족; 자연스러움은 0=모순/부자연, 1=정확하지만 단답, 2=상황에 맞는 자연스러운 연결로 개별 평가 | 실패 ID와 원인을 보고 교정; 평균으로 덮지 않음 |
| G4 재현·운영 | 실제 GPU 동일 조건 비교, 입력/가중치/출력/latency 기록, preflight·save/resume·mock ROS 통과 | 배포/새 학습 이미지 승인 보류 |

G3의 직원형 권유 대상 사례는 2점을 요구하되 종료/거절/명확화는 권유 자체가 가점이 아니다. 평가 대상 밖 모든 자연어에서 완벽함을 보장한다고 주장하지 않는다. 전체 평균 외 agent별·실패 유형별·단계별 결과, 표본 수, 반복 실행 변동을 공개한다. 학습 loss 하락은 위 gate 통과가 아니다.

## 8. 필수 회귀 시나리오

### 8.0 1차 필수 시나리오 P1 — 무조건 통과 (사용자 지정 2026-10-26)

**이 대화는 G2/G3 채택 판정에서 한 턴이라도 실패하면 후보 채택 불가다.** 문장을 외워서 통과하는 것이 아니라, 아래 “유동 변형”까지 같은 판단을 내려야 통과로 본다. 화살표(→) 뒤는 assistant 응답의 예시이며 고정 문구가 아니다.

| 턴 | 단계 | 사용자 발화 / 기대 응답 예시 | 필수 관측 (state·plan·Agent 경로) |
|---|---|---|---|
| P1-1 | noodle | “내가 매운 걸 못 먹어. 뭘로 할까?” → “매운 걸 못 드시니 크림 소스를 추천드려요. 어떠세요?” | 매운맛 회피 저장 + 넓은 추천 요청. Recommendation→validator→Response 경유. 크림은 **제안**(미래 sauce)이며 확정·실행 아님. plan 0 |
| P1-2 | noodle | “좋아 그리고 얇은면 조금만” | 크림 제안 수락(sauce=크림) + 얇은면/low 주문을 한 턴에 함께 반영(복합 의도). 이 기본 맥락에는 즉시 실행 요청이 없으므로 실행 확인 대기·plan 0. 명시 실행을 덧붙이거나 유효 execution pending을 수락하는 대조에서는 현재 면만 실행. 소스는 마지막 단계까지 투입 완료라고 말하지 않음 |
| P1-3 | veggie | “버섯 조금 양파 많이 담아줘” → 번복 “아 그냥 둘 다 조금만 먹고 싶어” | 번복 뒤 최신값 버섯 low·양파 low. 질문·pending·plan이 같은 최신값. 옛 양파 high 복원·실행 0. 실행 시작 뒤의 번복은 기존 보호로 막힌다(D1) |
| P1-4 | meat | “게살 알레르기가 있어서, 나머지만 담아줘” / “그거 빼고 담아줘” | 게살 allergy(강한 제한) 저장·UI 표시. 제외/나머지의 대상은 이전 대화·후보·현재 주문·직전 질문·pending으로 판단한다. 이 맥락에서 소시지가 대상이면 기존 high/low는 유지하고, 유효 후보를 수락한 경우 후보 수량을 따른다. 미확정 새 선택에만 normal(D2). 실행 확인 수락/명시 실행이면 현재 실행 가능 대상만 plan, 일반 선택이면 확인 대기, 참조가 모호하면 질문 하나. 게살 plan 0. 문자열만 보고 소시지 normal 즉시 실행으로 고정하지 않음 |
| P1-5 | extra | “토핑은 매운 거 못 먹어” → “아까 매운 걸 못 드신다고 하셨으니 치즈로 담아드릴까요?” → 수락 | P1-1의 매운맛 **강한 제한**(D3)을 기억해 페퍼론치노 제외·치즈 제안. 수락 후 **치즈만** plan 1 |
| P1-6 | lid·sauce | 자동 진행 | 뚜껑 자동, 마지막 소스는 P1-2의 크림. 시작/VLM/정책 결과/완료 구분(§3.4) |

**유동 변형 — 같은 판단을 요구한다.** 각 턴마다 최소 다음을 시험한다.

1. 어순·조사·반말/존댓말·띄어쓰기·오타 변형: “얇은 면 쪼금”, “양파랑 버섯 둘 다 적게”, “게살 알러지 있어 그거 말고”.
2. 메뉴 치환: 매운맛 대신 유제품 제한이면 P1-1은 크림이 아니라 오일/토마토, P1-5는 치즈가 아니라 다른 허용 후보 또는 “추가 없이 진행” 제안. 게살 대신 소시지 제한이면 “나머지”는 게살.
3. 턴 순서·결합 변형: P1-1·P1-2를 한 발화로(“매운 거 못 먹으니 알아서 소스 정하고 얇은면 조금”), P1-3 번복을 같은 발화 안에서(“양파 많이… 아니 둘 다 조금”).
4. 수락 표현 변형: “좋아/그걸로/응 그렇게 해/ㅇㅇ”가 P1-2(추천 수락)와 P1-5(실행 수락)에서 서로 다른 전이를 낸다(§3.2, F08).

### 8.3 복합 멀티턴과 모델 판단 자유도 — 필수 검수

2026-10-26 사용자 추가: 직전 문장 해석뿐 아니라 **앞선 여러 턴의 의미를 합쳐 판단하는지** 검증한다. 상세 계약은 작업장 `final/goals/GL04/MULTITURN_REVIEW.md`를 따른다. 같은 최신 발화에 다른 history/질문/pending을 주는 대조, 같은 history에 다른 state를 주는 대조를 포함한다.

검수군은 지시어·번복·기존량보존, 누적제약+추천/부분수락, 추천/실행/명확화 수락 구분, 일반/mixed 끼움·잘못된assistant, 단계 이동·철회 구분의5종이며 각4문맥대조를 계획한다(최소20episode, 아직 실행 결과가 아님). 단순 어휘치환만으로 수를 채우지 않는다.

GL04는 serializer의 실제 history/state 전달, oracle Decision을 넣은 mock 상태검증, 실제LLM 진단을 구분해 기록한다. mock 통과를 모델 의미 이해 통과로 표시하지 않는다. 자원·모델identity·검증된명령·사용량창이 확인되면 읽기전용GPU 소규모 연속대화 진단을 수행하며, 미실행은 NOT_RUN으로 남긴다. GL11의 최종 A/B 비교는 별도로 필요하다. 실제 ROS·active adapter 교체는 하지 않는다.

실제 주 시험은 이전 모델 출력의 state/history를 다음 턴으로 넘긴 closed-loop이며 매 턴 gold로 고쳐 넣지 않는다. gold 입력을 쓰는 controlled-context 원인진단과 분리한다. 입력전달실패·모델의미실패·Python거절/덮어쓰기·Response사실불일치를 각각 추적한다. Python이 지시어/복합 의도를 키워드로 다시 판단하는 새 guard를 추가하지 않는다. 강한제한/물리보호/schema/중복실행 안전은 보존한다. 기존 성공history와 token-overflow 정책도 보존한다.

GL07~09 데이터 전행검수는 단일 target뿐 아니라 episode의 history/state/target을 함께 보며, family/split 누수와 의미 대조·조사/문체 편향도 검사한다. GL04는 이 기준을 준비하고 계약에 영향받는 문제행을 대조하며, 데이터 전행 정제·새 학습을 완료했다고 표시하지 않는다.

사용자 추가: **단일발화의 복합 의도 × 여러 선행턴의 누적 의미**를 함께 검수한다. 적어도 두 선행 발화를 각각 바꿨을 때 동일한 최신발화의 정답이 각각 달라지는 대조가 필요하다. 매 턴 session/robot_state를 깊은 복사로 보존하고 전필드의 추가/삭제/변경/유지와 누락/null/none을 비교한다. order·제약·선호·pending·policy·robot_state·history/action_history·plan 및 최종발화까지 연결하며, 실제diff와 applied_this_turn을 교차대조한다. 의도별 기대변경/보존경로/금지변경은 실행 전에 oracle로 정하고, 일반대화의 정상history append와 부당한 주문변경은 구분한다. 마지막 턴만 맞거나 복합 의도 중 하나만 반영되면 합격이 아니다.

### 9.3 README 의무 필드

각 실제 학습 회차 README에는 시작·종료 날짜/시각/시간대와 증거 로그, Agent/기존 checkpoint/base revision, 코드 SHA/dirty patch hash, prompt/data/evaluator hash, train/validation/test 수와 DROP/FIX/HOLD 수, 학습 epoch/step/seed/정밀도/장치, image/tar digest를 적는다. 결과에는 baseline 대비 유형별 성능·실패 ID·latency, 선택 epoch 근거, 채택/기각/미평가, rollback 경로를 적는다.

학습 날짜가 없으면 UNKNOWN과 필요한 로그를 적는다. 디렉토리 mtime을 학습 날짜로 쓰지 않는다. 이전 01~15 회차는 기존 INDEX와 로그를 확인하여 README를 보완하되 과거 PASS를 최신 의미 검수 PASS로 승격하지 않는다. 원격 학습은 마지막으로 확인된 step과 확인 시각만 적으며 현재도 진행 중이라고 추측하지 않는다.

## 10. Agent별 비교·재학습·Docker

GL11에서는 각 Agent별 기존 checkpoint → prompt만 → 최소 Runtime 포함을 같은 조건으로 비교한다. 실패도 결과로 남겨 GL12의 학습 필요·데이터·예산 판단에 전달하며, 기존 adapter 완전 교정을 GL12 진입 조건으로 삼지 않는다. GL13은 별도 승인 이후 필요한 Agent의 정제 데이터 adapter 학습·재평가를 수행한다. 새 adapter 최종 채택은 그 모델의 동결 holdout·P1 전 턴/유동 변형/route 3종·기존 성공 회귀·안전/지연 검증 뒤에 판단한다. 새 가중치가 없으면 해당 성능은 NOT_RUN이다. 앞 단계로 해결되는 Agent를 무조건 재학습하지 않는다. 비교 시 base/quantization/tokenizer/template/seed/입력/history/생성 길이/GPU를 기록한다. 실제 GPU 추론으로 수행하고 CPU 추론 시간을 모델 고유 latency처럼 보고하지 않는다. 27턴 전체 시간과 1턴 시간을 구분한다.

학습은 검증된 새 release만 사용한다. 기존 원격 작업·tar·checkpoint는 이 계획 때문에 취소·덮어쓰기하지 않는다. 오래된 데이터로 학습한 결과라도 별도 후보로 평가하고 새 정답 기준을 통과한 경우에만 채택한다. 학습을 연속 수행할 경우 각 Agent 출력 디렉토리를 분리하고 앞 Agent 실패 시 다음으로 넘어가는 정책을 명시한다.

Docker는 모델 revision/cache identity/hash를 맞춘다. `tokenizer_config.json` mismatch를 검사 제거로 우회하지 않는다. 실제 UID와 mount 권한으로 audit report 생성·재작성, 독립 작업 디렉토리, mounted-model preflight, 짧은 학습/save/실패/resume를 먼저 시험한다. HF token을 이미지/보고서에 포함하지 않는다. `TRAINING_IMAGE_SPEC.ko_v2_9 (1).md`를 실제 찾아 적용하고 미확보면 명시한다.

**신규 실제 학습, active checkpoint 교체, ROS 실물 실행, 원본 브랜치 변경은 별도 승인 대상이다.** Docker 빌드/업로드 범위도 실행 시점 승인과 대상 digest를 확인한다. “Docker만 남았다”는 보고는 G0~G4와 사전 시험의 증거가 모두 있을 때만 가능하다.

### 11.2 각 작업의 보고 형식

작업 ID / 상태 / 실제 수정 파일 / 실행 명령과 exit code / 근거 ID·행 / 성공·실패·미검증 / 다음 작업 / rollback을 기록한다. 검수 결론은 찬성·반대·조건부로 남기고 조정자가 인용한 원문을 확인한다. “검수 완료”는 범위·분모·누락 수 없이는 쓰지 않는다. Claude/Codex 검수는 실제 dispatch·완료 보고가 있을 때만 완료라고 기록한다.

## 12. 최종 완료 정의

1. latest user 요구와 prompts/runtime/dataset/evaluator가 같은 계약을 사용한다. history 보존, 이후 고정 문구 제거, 안전 검증 보존이 diff와 테스트로 확인된다.
2. 세 Agent 활성 데이터에 미검수·DROP·HOLD 행이 없고 의미·언어·편향·누수 검수와 source ledger가 재현 가능하다.
3. 실제 GPU 비교에서 필수 회귀·직원형 대화·멀티턴·state·물리 grounding gate를 충족하며 기존 성공을 깨지 않는다.
4. 코드 저장소와 학습 보관소의 소유권·경로·README·학습 날짜/결과가 명확하고 실제 실행 경로 검증이 끝난다.
5. 승인된 이미지/체크포인트만 배포 후보로 지정하고 이전 버전 복구가 가능하다. 미승인 실물 실행·원격 작업 변경은 없다.
