## 0. 쉽게 설명

### 지금 무슨 일이 일어나나

```text
사용자:  "양판은 먹을게"            (STT가 양파를 양판으로 받아씀)
모델:    양파 넣기                  ← 맞게 알아들음
Python:  "발화에 '양파' 글자 없네?" ← 글자 그대로 비교
         → 버림 → "양판 메뉴는 제공하지 않아요"
```

오늘 로그(현재 코드로 돈 세션 2개, 42턴) 중 **19턴(45%)** 이 이렇게 모델의 정답을 Python 이 뒤집은 경우다.
모델이 직접 틀린 건 1턴뿐이다.

### 왜 이렇게 됐나

메뉴 이름은 이미 **스키마 enum**(`agent_contract.py:41`)이 막고 있다.
모델은 `domain.py` 에 있는 메뉴 말고는 출력할 수가 없다. "떡볶이"를 주문에 넣는 건 구조적으로 불가능하다.

그런데 그 위에 Python 이 **한국어 단어 목록**(`"빼"`, `"제외"`, `"해제"`…)과 **글자 일치 검사**를 또 얹었다.
단어 목록은 사람이 말하는 방식을 다 담을 수 없다. 그래서 목록에 없는 말투나 STT 오타는 전부 거절됐다.

### 바꾼 뒤 구조

```text
모델이 해석한다 (튜닝된 출력 형식 그대로, 재학습 없음)
   │
Python 은 두 가지만 본다
   ├─ 이 메뉴가 발화에 "비슷하게라도" 나왔나?   ← 자모 유사도 (domain.py 메뉴 목록만 사용)
   └─ 지금 상태에서 해도 되나?                  ← 이미 담았나 / 알러지 충돌인가
```

## 2. A — 맞는 답을 버리는 가드 (빼기 또는 교체)

### A1. 메뉴 근거 검사: 글자 일치를 자모 유사도로 교체

- **문제**: 양판→양파, 패퍼런지노→페퍼론치노, 계살→게살이 전부 "없는 메뉴"가 됨 (17:55 #8, #9, #21, #23)
- **해결**: 모델이 낸 정식 메뉴 이름마다, 발화 안에서 가장 비슷한 구간을 자모 단위로 찾아 점수(0~1)를 낸다.

| 점수 | 처리 | 오늘 로그 실측 |
|---|---|---|
| ≤ 0.35 | 통과 | 양판→양파 0.20, 계살→게살 0.20, 패퍼런지노→페퍼론치노 0.27, 얇은→얇은면 0.33 |
| 0.35 ~ 0.65 | 기존 `menu_confirmation` 으로 되묻기 | 벗어선→버섯 0.40, 벌써→버섯 0.60 |
| ≥ 0.65 | 근거 없음, 버림 | 고추→페퍼론치노 0.91, 햄→소시지 0.83 |

- **검사 순서** (Codex 조건 반영):
  1. 문맥으로 이미 정해진 대상 (`resolved_targets`, 확인 질문의 targets, 추천 select) → 검사 안 함
  2. 집합어 (야채 → 양파+버섯) → 기존 경로 유지. 단 `ORDER_COLLECTION_TARGETS` 는 `domain.py` 로 옮긴다 (메뉴 데이터이므로)
  3. 나머지 → 자모 유사도
- **검사 대상은 메뉴 이름만**이다. `low/normal/high` 같은 양은 검사하지 않는다.
- **수정 위치**
  - 새 함수 `menu_surface_score(user_text, canonical)`: `llm_policy.py` 에 추가
  - `llm_policy.py:391-443`: 면 종류·토핑 근거 검사를 교체하고, `"얇은"/"넓은"` 하드코딩(392-395)은 삭제
  - `llm_policy.py:340-372`: 제약 해제 대상 검사도 같은 점수 함수로 교체
  - `llm_langgraph.py:600-609`: "없는 메뉴" 판정은 **어떤 메뉴와도 0.65 이상 다른 mention** 일 때만
- **완료 기준**: 위 표의 사례를 단위 테스트로 고정한다.

### A2. 추가와 제거가 모순인지 단어로 판정하는 가드: 삭제

- **문제**: "버섯은 **제외**하고 양파만 보통" → 모델 답 `양파: normal` 이 정답인데 "제외"가 보여서 거절됨 (18:18 #6)
- **해결**: `ORDER_REMOVE_MARKERS`, `ORDER_MUTATION_MARKERS`, `INFORMATION_ONLY_MARKERS` 와 이를 쓰는 검사를 삭제한다. 추가인지 제거인지는 모델 출력(`amount` vs `"none"`)을 믿는다.
- **수정 위치**: `llm_policy.py:51-79`, `llm_policy.py:403-468`
- **위험**: 모델이 추가와 제거를 뒤집을 수 있다. 하지만 담기 전이면 되돌릴 수 있고, 담은 뒤면 `protected_order_keys` 가 막는다.

### A3. 제약 해제 단어 목록: 삭제하고 상태 기반 확인으로 교체

- **문제**: "양파 제약 **빼**자"가 무시됨. 목록에 `"빼"`가 없어서다 (17:55 #32)
- **해결**:
  - `RESTRICTION_REMOVE_MARKERS` 와 `restriction_remove_not_explicit` 검사를 삭제한다.
  - 알러지·섭취 불가 제약을 해제하는 경우는 **단어가 아니라 상태로** 한 번 확인한다. 기존 `pending_confirmation` 구조를 재사용한다.

- **수정 위치**: `llm_policy.py:81-88`, `llm_policy.py:470-479`

## 3. B — 제약 질문이 계속 쌓이는 문제 (상태 버그)

### 지금 구조의 문제

```text
#7  "…알러지가 있고 양파만은 적게"
    → 양파 알러지 충돌 → pending_confirmation 생성
       (알러지는 실제 주문 상태에 안 들어가고, 그 시점 세션 전체 사본에만 들어감)
#8 ~ #33
    → 사용자가 "응/아니"로 답한 적이 없음 → pending 이 안 지워짐
    → 매번 "양파를 포함해서 담아도 괜찮을까요?" 가 붙음
```

| # | 증상 | 원인 위치 |
|---|---|---|
| B1 | 답 안 하면 확인 질문이 영원히 남음 | `llm_langgraph.py:133` (confirmation=none 이면 그대로 반환) |
| B2 | "제약 해제해"가 안 먹힘. 알러지가 실제 주문 상태에 없음 | `llm_langgraph.py:795-802` (사본에만 저장) |
| B3 | 알러지 확인 대기 중인데 로봇 실행이 허용됨 (#15, #18) | `llm_policy.py:1019` (실제 주문 상태의 제약만 검사) |
| B4 | 늦게 "응" 하면 #7 시점 세션으로 통째로 되돌아감 | `llm_langgraph.py:154` (오래된 사본으로 교체) |

### 해결: pending 을 "작게, 한 턴만"

1. **알러지는 즉시 실제 주문 상태(`order.restrictions`)에 저장한다.**
   - 안전 정보는 확인과 상관없이 바로 기록한다. → B2, B3 이 같이 해결된다. 실행 검사가 실제 상태를 보기 때문이다.
2. **pending 에는 "충돌한 주문 patch"만 담는다.** 세션 전체 사본은 담지 않는다.
   ```python
   {"type": "restriction_conflict", "conflicts": [...], "held_patch": {...}, "held_commit": bool, "history_turn": n}
   ```
   - accept: 제약을 해제하고 `held_patch` 를 **지금 상태 위에** 적용한다. → B4 해결
   - reject: `held_patch` 를 버린다. 제약은 유지된다.
3. **pending 수명 = 다음 1턴.** 다음 턴이 확인 답이 아니면 pending 만 지운다.
   - 보류된 patch 는 버린다. 알러지는 1번에 따라 이미 저장돼 있으니 안전하다.
   - → B1 해결. 단어가 아니라 `history_turn` 으로 판단한다.
- **수정 위치**: `resolve_pending_confirmation` (`llm_langgraph.py:127-182`), `check_policy` 의 hitl 분기 (`llm_langgraph.py:795-802`), `build_next_prompt` (`llm_policy.py:869-876`), `decision_overrides.py:31-44`
