## 1. 원본은 검수가 끝났으니 전부 괜찮은가?

**아니다. 기존 검수 근거는 있지만 원본 전체의 무결함·최신 계약 적합성·모델 성공을 보증한 것은 아니다.** 앞선 “93행 보강 + 108행 교체”는 시작할 수 있는 확정 장부이지, 나머지 모든 행을 확인 없이 학습하라는 뜻이 아니다.

| 실제 확인된 것 | 확인되지 않았거나 별도인 것 |
| --- | --- |
| 원본 v5 7,784행과 source·ID·hash·기존 판정 연결 | 7,784행을 이번에 모두 새로 의미 검수한 것은 아님 |
| D 5,300행 기존 판정 재사용 + 영향 19행: KEEP3/FIX4/계약 HOLD12 | 현재 모델이 복합 의도를 정확히 추론한다는 증거는 아님 |
| Q 기존 640행 연결 + 47행 추가 검수, 고유 수정104행 | 최신 prompt와 학습 직렬화가 최종 조립본에서 일치하는지 재확인 필요 |
| P 기존 1,688행 판정 재사용 + 영향90행, 이번 원본 패치0 | P 모델의 사실 오류가 없다는 뜻 아님. 올바른 데이터라도 분포·대조가 부족할 수 있음 |
| exact 입력 정답 충돌0, 변경 관련 exact 교차 split 충돌0 | 의역·동일 대화 골격 누수0을 입증하지 않음. 수치 편향은 사용자 결정으로 DEFERRED |

근거는 `FINAL_VERIFICATION.json`의 `PASS_INACTIVE_DELTA_ONLY`, `OVERLAY_DELTA_CHECK.json`의 `PASS_EXACT_DELTA`, 후보 `MANIFEST.json`의 `enabled=false`, `requires_full_dataset_assembly=true`, `model_success=false`다. 해당 파일은 당시 감사 증거이며 현재 Runtime까지 검증했다고 고쳐 쓰지 않는다.

Cause: 기존 감사는 장부·불변 의미 판정 재사용과 당시 영향 검수에 대한 것이며, 이후 prompt·Runtime·실제 실패까지 자동 검증하지 않는다.

Effect: 재사용 근거와 새 영향 범위를 명시해야 한다. “전수 재시작”과 “원본 전부 통과 처리” 둘 다 하지 않는다.

## 4. 실행 순서 — R1 → R2 → R3 → R4 → R5

**아래는 다음 실행용 작업 명세다. 이번에는 수행하지 않았다.** R2의 Agent별 영향 검수는 서로 다른 파일·행 집합으로 병렬 가능하다. R3 통합과 R4 마감은 선행 결과를 받은 뒤 진행한다. 각 작업자는 실제 schema·builder·해당 policy 분기를 읽고 입력/정답을 판단한다.

### R1. 원본·계약·판정 장부 결속

목표는 “어떤 원본의 어떤 정답을 재사용하는지” 확정하는 것이다.

1. 원본 `quality_finish_20261028/packaging/training_inputs_v5/dataset/`와 감사 `data_reaudit_20261031/`의 ID/행/hash·split·기존 semantic 판정 연결을 확인한다. 과거 verifier 결과를 현재 실행 결과로 복사하지 않는다.
2. 모든 행에 기존 판정 유효/계약 영향/근거 미확인/명확한 오류/계약 보류를 구분한다. schema 통과만 있는 행을 의미 통과로 승격하지 않는다.
3. 현재 prompt·Runtime·serializer 변경이 어떤 family/field에 영향을 주는지 `CONTRACT_IMPACT.json`에 기록한다. 내용·계약·판정 근거가 같은 기존 KEEP은 재사용한다.
4. 사용자 시연, few-shot, 기존 개발 회귀의 노출 여부를 기록한다. 구체적인 학습·평가 family 경계를 먼저 정하고 그 뒤 변형을 만든다.
5. 출력은 `INPUT_MANIFEST.json`, `ROW_LEDGER.jsonl`, `CONTRACT_IMPACT.json`, `NEXT.md`다. 각 행의 현재 처리가 설명되면 종료하고 같은 장부를 다시 생성하지 않는다.

예: 과거 “버섯만 보통” 정답이 버섯만 normal로 바꾸고 양파 low를 보존하며 최신 계약도 같다면 KEEP을 재사용한다. 반대로 “아직 담지 마”에 주문 삭제 target이 있다면 해당 행만 다시 연다.

### R2. 영향 행 의미 정제 + 부족한 연결 대조 보강

1. D: 복합 선택+추천, 후보 수락+실행, 변경+실행, 제약+선택+실행, “나머지/처음 말한 것”의 복합 history 참조, 기존량 보존을 검수한다. 마지막 문장·“바로” 단어만으로 정답을 정하지 않는다.
2. Q: 안전한 전체/미래 추천 가능성을 유지하고 명시 좁은 요청도 존중한다. 소스 요청에 면만 추천하지 않으며 이미 확정한 면·양을 바꾸지 않는다. 알레르기 회피 이유와 새 수량 근거를 검사한다. 추천 요청 없는 모든 턴에 Q를 만들지 않는다.
3. P: 이번 선택/변경/유지와 실제 시작/완료를 구분한다. 근거 없는 크림 확정·“이미”·pending 없는 실행 확인·불필요 추천을 교정한다. 유효한 이유+권유는 자연스럽게 이어가고 조사·받침·존댓말도 실제 읽어서 판단한다.
4. 확정 delta93/대체108/HOLD12를 먼저 재사용한다. 원본 P 패치0은 추가 영향을 검사하지 않아도 된다는 뜻이 아니며, 과거 RV12 양파100행 등이 v5에서 이미 처리됐으면 다시 새 오류로 세지 않는다. 기존 alignment139행은 자동 병합하지 않는다.
5. 새 판단은 KEEP/FIX/DROP/HOLD와 근거·검수자·source/target hash를 장부에 남긴다. 단순 문구 flag는 검토 신호이고 단독 DROP 사유가 아니다. 같은 입력의 서로 다른 합법 sparse 표현을 무조건 모순으로 세지 않고 실제 전이·의미를 대조한다.

실제 전후 전 필드에서 기대 변경·보존·금지 변경을 기록한다. `order`뿐 아니라 preferences, restrictions, pending, action_history, robot의 active/queue/completed와 P 입력·발화도 해당 경로에 맞게 확인한다. 로봇 상태는 읽기 전용이며 실제 물리 사실을 새로 판정하지 않는다.

**오류 로그를 쓰는 두 방법은 구분한다.** 정상 학습 대화는 올바른 이전 턴을 누적해 다음 D/Q/P 입력을 만든다. 오류 회복 대화는 실제 잘못된 state/history를 보존하되 P 정답은 그 상태에 없는 주문을 확정했다고 말하지 않는다. 실패 P 문장을 정답으로 복사하지 않는다.

### R3. 새 후보본 조립 — 잘못된 원본을 append하지 않는다

1. 원본을 읽기 전용 입력으로 삼고 **새 버전 디렉터리**에서만 조립한다. source ID+행+before hash가 모두 맞는 replacement만 적용한다. 기존행과 수정행을 둘 다 남기지 않는다.
2. 계약 HOLD·의미 미확정·DROP은 활성본에서 제외하되 원본·판정 근거는 보관한다. 명시 위임 실행 HOLD12를 “사용자 말이 모호함”으로 바꾸거나 임의 commit=false로 학습시키지 않는다.
3. 현재 계약에서 유효한 고유 보강93행을 넣고 alias11개는 장부로만 남긴다. 추가 영향 정제·신규 보강이 있으면 별도 증감표에 적는다. few-shot은 데이터 전체에 자동 복제하지 않는다.
4. 기존 split을 조용히 섞지 않는다. **108개 교체 중 train98/test2/challenge8**이다. 평가용 정답 교정은 새 버전 평가 errata로 남기고 train에 넣지 않는다. 기존 봉인 평가 파일은 보존한다.
5. 출력은 `records/<agent>/<split>.jsonl`, `contracts/`, `ROW_LEDGER.jsonl`, `SOURCE_REPLACEMENTS.jsonl`, `EXCLUSIONS.jsonl`, `MANIFEST.json`이다. 모든 행을 역추적할 수 있고 입력→교체→제외→추가 합계가 맞으면 종료한다.

이전 확정 delta만 적용한 **가상 예상**은 전체 split 합계 `7,784−12+93=7,865행`이다. 이는 train 행 수가 아니다. 원본 train 합계는6,113행이고 HOLD 중 train5개를 제외하고 보강93개를 모두 train_candidate로 채택하면 train예상6,201행(D4,119/Q602/P1,480)이다. 이후 추가 FIX/DROP/HOLD·누수 판정에 따라 달라질 수 있으므로 실제 완료 수치로 미리 쓰지 않는다.

### R4. 통합 검사 — 모양 검사와 말뜻 검사를 따로 통과한다

1. **구조·실행 계약:** JSON 파싱·중복 키·허용 field/type·메뉴/양·strict bool/null·none 취소 patch와 persisted order 구분·state diff·pending 대상·실행 권한을 검사한다. 채점기 실패는 데이터 오류와 분리하고 해당 반례만 교정한다.
2. **대화 의미·한국어:** 발화/history/state/target/이유/질문 목적/시제·조사·받침·존댓말을 확인한다. 별도 검수자가 생성자 결론을 복사하지 않고 입력과 실제 코드를 대조한다. 의미 judge는 검증된 사람 정답 대조셋을 통과한 보조 수단만 사용하고 미결은 HOLD다.
3. **중복·평가 누수:** exact뿐 아니라 같은 episode/생성 골격/의역·메뉴 치환 family가 train과 unseen 평가에 나뉘는지 본다. 자동 유사도는 후보 표시이지 자동 삭제가 아니다. 충돌하면 split/노출 표기를 조정한 새 버전을 기록하고 옛 봉인 파일은 보존한다.
4. **분포·편향:** 아래 §6의 조건별 사례 수와 빠진 조합을 D/Q/P 및 split별로 낸다. 기존 60/70/10 등의 수치 임계값은 사용자 재승인 없이 합격 기준으로 부활시키지 않는다. 임계값 미정이면 DEFERRED로 명시하며 “편향 해결”로 쓰지 않는다.
5. **실제 trainer 입력:** 현재 system/few-shot·template·history·target·EOS·loss mask와 토큰 길이를 실제 trainer encode로 검증한다. 정답 잘림·필수 state 손실·history 추가 삭제는 허용하지 않는다. 과거8192 통과는 옛 prompt의 결과이고 현재 D 입력은17턴 계측에서8,092~8,492토큰이었으므로 cap을 다시 계산한다. 필요하면 길이/배치를 조정하는 별도 설정안을 내고 말귀 검증을 history 삭제로 해결하지 않는다.

구조 `structural_passed`와 문구 `text_rule_flags`, 최종 의미 판정을 별도로 저장한다. 구조만 맞거나 문구 검사가 모두 조용하다고 최종 합격시키지 않는다. “정상 주문 변경이면 action_history가 비어야 함”, “추천 불가능도 항상 status=ok” 같은 임의 가정을 검사기에 넣지 않는다.

### R5. 학습 준비 판정과 후속 모델 검증 계획

1. 각 Agent에 남은 실패와 새/수정 데이터 범위, 재사용 근거, 추가 데이터 수·제외 수·미해결 수를 보고한다. 현재 로그의 D/P 실패를 우선 다루되 Q의104개 정책 수정은 별도 반영한다. Q는 최신17턴에서 호출되지 않았으므로 성능 실패라고 단정하지 않는다.
2. 학습본 준비 완료와 학습 실행·모델 채택을 분리한다. 계약 HOLD·수치 편향 미확정·누수 의심 등 남은 항목을 숨기지 않고 학습 전 판단이 필요한 점을 명시한다.
3. 필요한 Agent별 재학습 설정과 원본회귀/시연seen/별도unseen 평가를 계획한다. 모든 Agent를 무조건 재학습하거나 이번 계획에서 학습을 자동 시작하지 않는다.
4. 새 adapter가 준비되면 정답 주입 없는 복합6턴·분리11턴을 전체 기록한다. 캐시 ON/OFF 품질 대조는 Claude와 단일 GPU 소유권을 조율한다. 캐시에서만 생긴 추가 오류는 데이터를 비틀어 가르치지 않는다.
5. 생성 plan은 오프라인 검사하고 실제 로봇은 별도 승인 후 검증한다. 막힌 뒤 강제로 정상 state/section을 넣는 시험은 진단으로만 분리한다. 새 모델이 운영 채택 기준을 통과하기 전 경로를 교체하지 않는다.

## 5. 반드시 연결할 시연과 대조 예시

### 5.1 사용자 시연 — 한 턴에 여러 뜻을 빠뜨리지 않는다

| 발화/문맥 | D·주문·제약의 정답 의미 | 다음 발화·실행·응답 조건 |
| --- | --- | --- |
| “면은 얇은면으로 보통 양으로 주고, 소스는 느끼한 걸로 추천해줘.” | 얇은면/normal + 추천 request | Q가 안전한 크림 후보를 보관. 크림은 아직 확정 아님. P는 이유와 후보 선택 질문을 자연스럽게 말함 |
| 위 후보 뒤 “크림으로 선택할게. 바로 담아.” | 유효 후보 수락 또는 명시 크림 선택 + commit | sauce=크림 확정 후 현재 면 실행 검사. 면 실행을 소스 투입 완료로 말하지 않음 |
| 양파·버섯 low 선택 뒤 “버섯만 보통 양으로 바꿔서 바로 담아.” | 버섯 normal + 양파 low 유지 + commit | 안전/단계 검증 통과 시 현재 채소 계획. P/기존 시작 안내는 실제 변경·허가 사실만 말함 |
| “게살 알레르기가 있어서 소시지만 많이 바로 담아줘.” | 게살 allergy + 소시지 high + commit | 게살 금지 유지, 안전한 현재 육류 실행 검사. 취향만 저장하거나 allergy 누락하면 실패 |
| “페퍼론치노는 빼고 치즈만 적게 골라서 바로 담아.” | 페퍼론치노 none patch + 치즈 low + commit | persisted order에 취소 none을 남기지 않음. 현재 토핑 실행 검사, 실제 담기 전 완료 발화 금지 |

소스 선택은 면 단계 입력에 필요하지만 면 실행이 크림 소스 물리 투입을 뜻하지 않는다. 이후 section 도달은 실제 실행 결과/시험의 명시적 물리 fixture와 구분한다. 주문·후보를 미래 단계까지 다룰 수 있다는 원칙과 현재 단계만 물리 실행하는 안전 경계는 충돌하지 않는다.

### 5.2 같은 단어, 다른 정답 — 무조건 commit을 외우지 않는다

| 문맥·발화 | 올바른 차이 |
| --- | --- |
| “소시지 많이 골라줘” / “소시지 많이 골라서 바로 담아줘” | 둘 다 high, 전자는 자동 실행 없음 / 후자는 commit |
| “바로 담도록 해” / “바로 담지는 마” / “‘바로 담아’라고 말하면 돼?” | 실제 명령은 commit / 부정·인용 질문은 그 단어 때문에 실행하지 않음 |
| 크림 후보 뒤 “그걸로 할게” / 실행 질문 뒤 “응, 그걸로 해” | 후보 선택 수락과 실행 확인 수락을 실제 직전 질문·pending으로 구분 |
| 소시지 low가 기존 주문에 있음 / 아무 주문·양 근거가 없음, “소시지 골라줘” | 기존 low 유지 / 새 선택만 normal. 사용자 취향·수락 후보에 양 근거가 있으면 그 근거 존중 |
| 소시지 high 신규 변경 기록 있음 / 이미 high이며 변경 기록 없음 | “많이 선택했어요” / 기존 선택 유지 설명. 두 경우 모두 담기 완료라는 뜻 아님 |

### 5.3 복합 멀티턴 — 마지막 문장만 보면 안 된다

검수는 실제 사용자 발화 누적 수·history message 수·로봇 이벤트 수를 따로 센다. “12턴” label만 있고 사용자 이전 발화가 1개뿐인 데이터를 복합 멀티턴으로 세지 않는다.

1. **지시 대상 연결:** 소시지·게살 후보를 앞서 제시 → 게살 allergy → 다른 끼움 대화 → “그거 빼고 나머지만 많이 바로 담아.” 근거 집합에서 게살만 제외해 소시지를 선택·실행한다. 과거 후보가 다른 경우 같은 마지막 문장도 달라진다.
2. **번복 누적:** “양파 많이, 버섯 조금” → “둘 다 조금” → 잡담 → “버섯만 보통으로 바꿔서 바로 담아.” 최종 양파 low/버섯 normal을 유지한다.
3. **선호 기억 권유:** 앞서 치즈를 좋아한다고 말함 → 다른 단계 여러 턴 → 추가 토핑 단계. 유효 선호라면 관련 권유를 하되 이미 치즈 low가 확정됐으면 다시 주문을 만들지 않는다. 철회됐다면 언급하지 않는다.
4. **오류 회복:** assistant가 “크림 선택 완료”라고 잘못 말했지만 state.sauce=null인 이력을 유지 → 사용자가 “아직 선택 안 했잖아. 크림으로 할게.” 최신 명시 선택을 반영하고 기존 거짓말을 사실로 삼지 않는다.
5. **물리 변경 경계:** 양파를 실제 담은 증거 뒤 “양파 빼줘.” 취소 의도는 해석하되 실제 제거 완료를 발명하지 않는다. 실행 전 선택 취소 사례와 분리한다.

2/3/6/8/12개 선행 사용자 발화 수준의 서로 다른 조합, task/general/mixed 끼움 턴과 거절·철회를 포함한다. 매 턴 불필요한 추천을 넣거나 같은 “저장했어요” 문장을 반복하도록 작성하지 않는다. 선호는 관련 시점에 이유로 쓰고, 현재 질문이 단순 수량 변경이면 필요한 변경 안내로 끝낼 수 있다.

## 7. 산출물 위치·중복 작업 방지·정지 조건

### 7.1 위치와 문서 역할

### 7.2 한 번 처리한 것을 반복하지 않는다

1. 처리 키는 source ID+source 내용 hash+계약 버전+정답 hash다. 같은 키의 판정이 있으면 재사용하고 새 성과로 세지 않는다. 계약 변화가 있으면 영향을 받은 판정만 연다.
2. D/Q/P 독립 행은 병렬 검수할 수 있지만 같은 대화의 state 연결은 단일 episode 원장으로 합친다. 생성자와 독립 검수자의 쓰기 파일을 분리한다. Runtime·공통 계약 변경은 단일 소유자만 한다.
3. 한 묶음마다 새 오류/기존 재사용/검수자 오판/미결을 따로 집계한다. 이미 수정된 원본을 또 발견했다는 이유로 수정본을 중복 append하지 않는다.
4. 서로 다른 정답이 남으면 근거 비교 후 확정하거나 HOLD한다. 모델 호출을 반복해 다수결로 정답을 만들지 않는다. 기술 문제의 같은 수정이 3회 실패하면 의심 가정을 적고 해당 작업을 멈춘다.
5. R1~R5의 산출물·완료 조건이 충족되면 그 작업을 마감한다. 더 큰 “모든 자연어 완벽” 조건을 추가해 무한 전수감사를 재시작하지 않는다. 미정은 미정으로 보고하고 학습/운영 채택에 필요한 결정만 요청한다.

## 8. 완료 기준과 지금 다음 한 단계

데이터 준비 완료는 **원본 보존 + 전행 판정 근거 연결 + 확정 수정·보류 집행 + 현재 계약 직렬화/토큰 검증 + 의미/누수 검수 결과 및 남은 편향 한계 명시**가 있을 때만 보고한다. 모델 품질은 그 뒤 실제 새 adapter로 별도 검증한다. unit test894개 또는 CPU 정답 replay 성공을 모델의 자연스러운 주문 이해로 바꾸어 보고하지 않는다.

최초 작성 시점의 완료는 **계획 작성과 근거 대조뿐**이었다. 이후 승인 실행의 최신 상태는 문서 상단과 최종 결과를 따른다. 새 학습·cache실험·모델채택은 이번 실행에서도 하지 않았다.

**최초 착수 지시는R1이었으며이제완료했다. 현재 다음 한단계는새후보의학습길이·배치·직렬화설정검토이다.** 완료한R1~R4를새로전수재시작하지않는다.
