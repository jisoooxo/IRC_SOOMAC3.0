# 최종 5개 시나리오 — STT/TTS 상주와 D/Q/P 워밍업 비교

**3/3 완료. Qwen STT·CosyVoice TTS·vLLM을 함께 올린 네 조건에서 최종 5개 시나리오를 각각 완주했다. 총144/144턴이 상태·계획·계약 검사를 통과했다. 워밍업 후 첫 스피커 출력 요청까지 약3.2초,36턴 처리 시간은 두 설정 모두 약4분6초였다.12K는16K보다 장치 VRAM을 약2GiB 덜 사용했다.**

원인: 추가 D/Q/P 워밍업으로 실제 첫 요청의 프롬프트 계산 일부를 준비 단계에서 처리했다.
효과: 첫 사용자 대기는 약5.7초 줄었지만, 음성을 읽는 시간을 포함한 전체 대본의 절감량은3~6초였다. 총 계산 시간이 사라진 것은 아니다.

## 1. 측정 조건과 경계

사용자가12K/.50과16K/.58 두 설정 모두의 비교를 승인했다. 각각 추가 워밍업 없음/있음으로 총4회 실행했다. 각 조건마다 STT/TTS/vLLM/LLM 클라이언트를 새로 시작하고, 끝날 때 소유 프로세스를 모두 종료했다. 운영 기본값16K/.58과 시작 절차는 변경하지 않았다.

| 항목 | 실제 실행 |
|---|---|
| LLM | Gemma4 12B NF4/BF16 vLLM, D epoch6/Q epoch6/P best150 별도 LoRA, 전체 Decision 보강, batch invariant ON |
| STT | Qwen3-ASR-1.7B-hf BF16 CUDA 상주. 조건별 저장 음성10초의 실제 인식1회. Silero VAD는 CPU 상주만 함 |
| TTS | 실제 CosyVoice3-0.5B, 기존 초기화 워밍업 유지. 매 턴 실제 답변을 합성하고 soomac_speaker OutputStream으로 재생 요청 |
| 대화 | 실제 D/Q/P graph 출력으로 state/history를 이어가는 closed-loop 평가. 실행 턴의 기존 Python 고정 안내 유지 |
| 격리 | localhost18001/ROS217. STT 인식 결과와 TTS 제어 이벤트는 측정기 내부 캡처. 실제 로봇 명령 없음 |

**마이크 발화 종료→실제 소리 발생의 전체 지연 측정은 아니다.** 시나리오 입력은 원문 텍스트이며, STT 실제 인식은 별도 저장 음성으로 측정했다. VAD 종료 대기·마이크 수음·사용자가 말하는 시간·UI/MAIN 처리·로봇 이동·VLM 판정은 포함하지 않았다. 물리 완료는 기존 평가기의 fixture이며, Decision 출력은 실제 모델 결과이다.

추가 워밍업은 기존 실제 첫 D/Q/P HTTP 입력3개를 운영 어댑터·프롬프트·출력 문법으로 실행하고 결과를 폐기하는 방식이다. 실세션 state/history를 갱신하지 않는다. `cold` 파일명은 **LLM 추가 워밍업 없음**을 뜻하며, vLLM 기본 엔진 워밍업·TTS 기본 워밍업·별도 STT 파일 인식은 모든 조건에 있다.

## 2. 핵심 시간·메모리 결과

`첫 출력`은 첫 사용자 텍스트를 graph에 넣은 시점부터 TTS의 첫 `speaker.write` 호출까지이다. 음향 센서로 실제 소리 발생을 측정한 값은 아니다. `36턴 총시간`은 graph·TTS 합성·재생 요청·평가기 진행을 포함하며, 마지막 TTS callback 종료까지이다. 장치에 남은 재생 버퍼의 최종 소리 종료를 직접 측정하지 않았다.

| 설정 | D/Q/P 추가 워밍업 | 첫 출력 | 첫 턴 TTS callback 완료 |36턴 총시간|장치 VRAM peak|최소 여유|
|---|---|---:|---:|---:|---:|---:|
|12K/.50|없음|8.88초|17.54초|251.25초, 약4분11초|27.51GiB|4.35GiB|
|12K/.50|있음|**3.23초**|11.90초|245.59초, 약4분6초|**27.47GiB**|**4.39GiB**|
|16K/.58|없음|8.96초|17.64초|248.72초, 약4분9초|29.46GiB|2.40GiB|
|16K/.58|있음|**3.19초**|11.86초|245.62초, 약4분6초|29.47GiB|2.39GiB|

추가 워밍업 자체는12K7.82초,16K7.92초였다. 준비 완료 전에 약8초를 더 쓰는 대신 첫 대화의 대기를 줄이는 것이다. 전체 시작→준비 완료는118.92/91.98/126.40/93.78초였으나 초기화 시간 변동이 있으므로 “워밍업을 넣으면 기동도 빨라진다”고 해석하지 않는다. TTS 로딩/기본 워밍업은 실행별 약11~51초로 달랐고, 초기화 로그에는 ModelScope 메타데이터 조회도 있다. 그 변동의 원인은 별도 분리하지 않았다. 오프라인 기동 검증이 아니다.

| 설정 | LLM graph 시간 합계 | 첫 출력 중앙값 | 첫 출력 P95 | 첫 출력 최대 |
|---|---:|---:|---:|---:|
|12K 추가 워밍업 없음|58.33초|1.85초|4.50초|8.88초|
|12K 추가 워밍업 있음|51.92초|1.81초|4.24초|4.57초|
|16K 추가 워밍업 없음|58.11초|1.87초|4.73초|8.96초|
|16K 추가 워밍업 있음|52.58초|1.86초|4.27초|4.60초|

전체 대화는 자연스럽게 자체 캐시를 쌓으므로 워밍업 효과가 모든 턴에서 첫 턴만큼 반복되지는 않는다. 신규 입력이나 다른 Response 경로에서는 추가 계산이 남는다. 워밍업 후에도 cache hit0 요청이 관측됐지만 모두 정상 완료했다.

각 설정은1회씩의 전후 비교이다. 실행 순서는12K 없음→12K 있음→16K 없음→16K 있음이며 순서를 무작위화하지 않았다. 위 차이는 관측값이지 반복 측정으로 확정한 인과 효과나 지연 SLA가 아니다.

## 3. 최종 시나리오와 실제 출력

[최종 시연 문서](2026-11-05_verified_multiturn_scenarios.md)의 아래5개 대본을 사용했다. 서로 독립된 시작 상태를 쓰며 각 대본 내부는 실제 대화 상태를 이어갔다.

| 시나리오 | 턴수 | 네 조건의 상태·계획·계약 |
|---|---:|---|
|기본 필수 복합 주문|6|각6/6|
|추천 수락과 명시적 면 실행|2|각2/2|
|짧은 수락 뒤 재질문·실행|11|각11/11|
|수량 수정과 지시어|11|각11/11|
|기분 대화에서 주문·보류·실행|6|각6/6|

실제 답변 예시:

- “그걸로 하고 면은 바로 담아줘.” → “얇은면을 보통 양으로 담을게요.” 실제 평가 계획은 noodle_thin×2이다.
- 양파 적게/버섯 많이 선택→“아니, 버섯도 적게 바꿔줘.”→“그럼 그걸로 담아줘.” → “양파와 버섯을 적은 양으로 담을게요.” 평가 계획 onion×1,mushroom×1이다.
- 소시지 많이→적게 수정→“응, 그걸로 담아줘.” → “소시지를 적은 양으로 담을게요.” 평가 계획 sausage×1이다.
- 치즈 적게→보통 수정→“그걸로 담아줘.” → “치즈를 보통 양으로 담을게요.” 평가 계획 cheese×2이다.
- 기분 대화 뒤 추천→면 실행 보류→“지금 면이 이미 담긴 건 아니지?” → “네, 면은 아직 담기 전이에요.” 이후 명시 실행에만 계획을 만들었다.

실행 안내 예시는 기존 Python 고정문장이다. 전체144턴 중 실제 Response 모델 호출88회와 고정 실행 안내56회이며, D144회/Q16회가 실제 수행됐다. 시나리오 HTTP248회와 워밍업 HTTP6회, 합계254회 모두 finish_reason=stop이었다.144회 TTS 완료와 WAV 생성도 확인했다.

12K 전후는36개 답변과62개 시나리오 HTTP 요청이 모두 동일했다.16K 전후는 답변31/36이 동일했고5개는 표현 차이가 있었다. 예를 들어 “버섯을 보통 양으로 늘렸어요. 담을까요?”에 “양파는 적은 양 그대로예요.”가 추가되거나 “소시지를 적게 담을까요?”가 “지금 담을까요?”로 바뀌었다. 해당 주문 state/수량/실행 계획은 검사에 통과했다. 출력 차이가 뒤 history에 반영되어16K 전후의 모든 요청이 동일하지는 않으며, 총시간 차이 전체를 워밍업만의 효과로 단정하지 않는다.

기존 최근20메시지 정책을 유지했으며,12K 예산 때문에 추가로 history를 잘라낸 건수는0이다. 이 대본의 성공이 미검증 자유대화 전체나 다른 cache 조건의 결정성을 보장하지 않는다.

## 4. STT·VRAM 해석과 로그 확인

Qwen은 각 조건에서10초 저장 음성을 실제로 인식했고 인식 구간은0.874/0.857/0.862/0.860초였다. 같은5초 참조 음성을 반복한 입력이며, 실제 주문 문장의 마이크 인식 정확도 평가가 아니다. 이 시간을 각 시나리오 턴에 일괄 더해 실측 end-to-end 지연이라고 부르지 않는다.

NVML v1 장치 전체 사용량을50ms 목표 간격으로 기록했다. 드라이버 예약도 포함하며 최대 표본 간격은 조건별80.5/76.6/75.3/84.5ms였다. 순간 최대값을 모두 잡았다는 보장은 없다. 이번은 **세 모델 동시 상주, 대화 처리에 따른 순차 연산**이다. 앞선 STT·TTS·LLM 동시 연산에서16K31.37GiB/여유0.49GiB로 중단된 기록이나12K28.97GiB 기록을 대체하지 않는다. VLM7장 동시 부하를 다시 검증한 것도 아니다.

TTS 로그의 `em` 미설치 traceback은 ROS 코드 생성 모듈의 DEBUG import 경고였다. 실제 표준 메시지 사용과144회 합성/재생 요청은 완료했다.12K 워밍업 조건의 vLLM EngineDeadError는 모든 요청 종료 후15:26:53 소유 scope 종료 과정에서 기록됐다. 추론 도중 장애와 구분하여 원문을 보존했다. CUDA OOM·자원 guard 발동·HTTP 요청 실패·TTS 명시 실패는 관측하지 않았다.

## 5. 판정·현재 적용 상태

**이번 범위에서는12K/.50 + D/Q/P 시작 워밍업을 운영 적용 후보로 권고한다.** 두 설정의 워밍업 후 첫 출력과 전체 대본 시간은 거의 같았고,12K는 약2GiB 더 여유로웠다. 이전 동시 부하 결과도 함께 고려한 판단이다. 서버/클라이언트 예산과 준비 완료 처리를 함께 바꾸는 실제 적용은 이번 시험에서 하지 않았다.

원본 소스41개와 세 어댑터 경로·가중치·설정 SHA가 실행 전후 같았다.16개 소유 scope의 종료와 GPU compute 프로세스0,8000/18001 포트 반환을 확인했다. 운영 파일·어댑터·사용자 대화·원본 TTS last.wav는 변경하지 않았다. 생성 음성은 이 시험 결과 폴더에 저장했다.

교차검수는 내부 자료를 보내지 않은 일반 측정 방법론만 Codex CLI(gpt-6-sol/high)로 수행했고 조건부 찬성이었다. 특히 software speaker-write를 실제 음향 시작으로, callback 종료를 최종 재생 종료로 표현하지 않도록 반영했다. 로컬 코드/수치의 독립 외부 검수와 구분하며, 실행 증거·시간 순서·출력·자원 반환은 주담당자가 직접 대조했다.
