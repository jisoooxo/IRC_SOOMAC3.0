## 1. 토큰 확대와 평가 범위

**보강 문구는 압축하지 않았다.** 최초 전체 보강 문구를 복원하고 평가 vLLM의 `max_model_len`과 `max_num_batched_tokens`를 16,384로 확대했다. 클라이언트도 D/Q 입력15,360+출력1,024, P 입력15,872+출력512로 맞췄다. 운영 설정/프롬프트 파일은 변경하지 않았다.

처음16K/.45 GPU할당률은 KV5.25GiB 필요 대비2.67GiB 확보로 엔진 사전검사에서 종료됐다. 실패 로그를 `FAILED_STARTUP_01/`에 보존했다. 평가 할당률만.58로 올린 실행은 KV6.77GiB/21,106tokens 확보 후 정상 기동했다. 이는 PC 전체 정지나 OS OOM을 관측한 사건이 아니다. maxseq2지만 두 요청이 동시에16K를 모두 쓰는 용량은 검증하지 않았다. STT/TTS와 동시 운영 성능도 미검증이다.

기존 학습/서빙 기준 NF4/BF16·batch invariant·별도 D6/Q6/Pbest150 LoRA를 유지했다. 가중치 병합/학습/실물 ROS/VLM/원격 변경은 없다. 이전 epoch 비교를 반복한 것이 아니라 선택된 조합의 프롬프트×안내 방식4조건을 비교했다. **운영 Decision 어댑터는 아직 교체하지 않았다.**

개별 D는137문항(서로 다른 실제 입력132개)×기존/보강2조건을 새로 추론했다. 누적 대화는13개82턴×4조건이다. 모델 안내 조건에서는 동일 프롬프트의 독립 D 점수를 재사용하며, 누적 대화82턴은 각각 새로 추론했다. 입력은 관측 전 동결했지만 이전 실패를 이미 본 개발 평가이므로 비노출 일반화 정확도가 아니다. 정답과 표현이 같은지를 평가하는 JSON 완전일치와 실제 실행의 적합성을 구분한다.

이 표는 자연어 의미 검수까지 모두 합격했다는 뜻이 아니다. 자동 통과한 답변에서도 어색한 공감, 요청하지 않은 치즈 제안, 실행 전 ‘시작했어요’라는 시점 표현을 별도 기록했다. 수량 생략과 잘못된 수량을 구분했으며, 이328턴에서 확인한 자연어 수량 모순은 없다. 과거의 ‘버섯 적게’를 ‘많이’로 말한 기록은 취소하지 않는다.

필수 compound6턴·split_control11턴은4조건 모두 상태/계획 통과했다. 추가 추천/수량 수정/제한/취향/상황/mixed/general 대화도 실패 여부와 무관하게 마지막 계획 턴까지 관측했다. 기대 상태는 별도로 유지하고 **실제 상태를 정답으로 덮어쓰지 않았다.** 로봇 완료는 실제 허용된 실행에만 적용한 명시적 오프라인 fixture이다.

### 사용자가 요청한 표현

추천 직후 **“그걸로 하고 면은 바로 담아줘.”**는4조건 모두 크림 선택+얇은면 normal 실행이었다. 실제 계획은 `noodle_thin/repeat_count=2`이다.

| 안내 방식 | 실제 답변 |
|---|---|
|고정|얇은면을 보통 양으로 담을게요.|
|모델|크림 소스를 선택했고 얇은면은 보통 양으로 담을게요.|

“그걸로 담아줘”에 크림 선택 후 면 실행을 재질문한 응답은 사용자의 최신 판정대로 정상이다. 이번 연결 대화는 그 다음 “그럼 면은 지금 바로 담아줘”부터 마지막 치즈 실행까지11턴 모두4조건에서 정상 상태/계획이었다. 단, 별도의 고정 입력에서는 짧은 표현을 즉시 commit으로 해석하는 차이가 남았다. 한 대화의 성공을 모든 history에서 같은 동작이라고 확대하지 않는다.

## 3. 실패의 발생 지점과 후속 영향

### 일반대화·취향·제한

보강 prompt는 피곤함/기분 관련8개 개별 입력을 general로 바꿨다. 예컨대 기존 “피곤할 때는 든든하게”라는 근거 없는 취향 추가가 없어졌다. 연결 대화에서도 기분2턴의 task 오분류가 사라졌고 이후 음식 주문·대기·실행까지 유지됐다.

반면 “반가워, 오늘 처음 이용해 봐”, “여기 주문 도우미는 무슨 역할…”은 여전히task, 추천 이유 질문은general이었다. 새 인사/역할 질문3개는 성공했다. **전면적인 일반대화 분류 해결은 아니다.**

“매콤한 건 힘들어. 부담 없는 조합으로 추천해 주겠어?”는 두 prompt 모두 `preferences=맵지 않게`와 추천만 출력하고 `restrictions`를 누락했다. 누락은 원본 Decision JSON에서 직접 보이며 전송 중 필드 손실이 아니다. 더 명시적인 “매운맛은 못 먹어”는 제한으로 추출했고 후속 페퍼론치노 추가를 막았다. 모델이 왜 두 표현을 다르게 학습했는지의 가중치/데이터 원인은 미확정이다.

보강안은 독립 입력1건에서 기존 게살allergy 조회에 cannot_eat를 추가했다. `llm_policy.py:428`의 제한 추가는 기존allergy를 유지하므로 알레르기를 해제한 오류는 아니다. 그래도 조회만 했는데 상태를 추가하려는 출력이며, 보강안의 회귀 위험으로 남긴다. 실제 연결된 동일 주제 대화에서는 이 추가가 발생하지 않았다.

완전일치 개선11건/악화2건에는 같은 의미의 `confirmation`/`commit`, 후보 수락, 표현 차이도 포함된다. `덜 매콤하게`와 `맵지 않게`, 요청에 근거한 추가 취향을 무조건 모델 오류로 세지 않는다. 원본 점수는 보존하고 [별도 의미 판정](../training/learning_first_v43/final/goals/GL10/dqp_prompt_multiturn_20261105/INDEPENDENT_SEMANTIC_REVIEW.json)에 해석을 기록했다.

| 순서 | 사용자 | 모델 안내 조건의 실제 답변 |
|---|---|---|
|1|양파는 적게, 버섯은 많이 골라줘.|양파는 적게, 버섯은 많이 선택했어요. 이대로 야채를 담을까요?|

마지막 D 원문은 `{"route":"task","order":{"toppings":{"버섯":"none"}}}`로 commit이 없다. Runtime은 이를 상태 수정만으로 처리했다. **양파량 오류나 잘못된 실행이 아니라 실행 요청 누락**이다. 두 prompt의 모델 안내 조건에서 동일하게 발생했다.

고정 안내 조건의 같은 턴은 commit=true이며 양파1 계획을 만들었다. 직전 세션을 필드별 대조하면 order·pending·robot은 같고 history만 다르다. dtype이나 상태 갱신 누락을 관측한 것은 아니다. 다만 아래 동일 요청 재실행에서도 출력 차이가 관측됐으므로 history만을 유일한 원인으로 단정하지 않는다. 마지막 계획 턴에서 실패했으므로 별도 후속 대화로 재요청 회복을 추적했다.

## 4. 실제 전송·문장·지연 검수

4조건910 HTTP 요청 전체에서 tokenizer로 전송 문자열을 복원해 입력 JSON 값/자료형과 raw 출력 대응을 확인했다. D prompt가 baseline/patched 원본과 같은지도 확인했다. **추가 history trim0건**, 저장된 세션 history prefix 보존, 기존 최근20메시지 입력 창 유지이다. 무제한 history 전달을 뜻하지 않는다.

실측 최대 입력+예약 출력은10,101토큰이었다. 이번 문항이 실제10,240를 넘었다고 주장하지 않는다. 기존 한도에서는 정적 prompt+상태 여유1,024를 확보하는 사전검사에 걸렸으며,16K는 그 여유와 앞으로의 입력을 확보한 설정이다. 최종 raw 한도 검증은16K와 별도로 기록했다. 본910요청은 전부 finish_reason=stop이며 길이 한도에 의한 중단은0이었다.

기존/보강 고정 안내의 실행 턴 중앙값은0.409/0.460초, 모델 안내는1.196/1.210초였다. 양쪽 모두 실행한 같은25턴의 차이 중앙값은 각각+0.791/+0.754초였다. D→Q/P 전체 호출과 Python 경로를 포함한 이번 로컬 측정이며 TTS/로봇 시간이나 HF와의 새 비교가 아니다. 실제 history가 달라지는 운영 비교로, 순수 P 단독 연산 차이라고 해석하지 않는다.

원문은 각 run의 `OUTPUTS.md`, 의미 판정은 `MANUAL_REVIEW.json`, 모든 요청 대조는 `TRANSPORT_TOKEN_AUDIT.json`에 있다. 동일 문장은 이미 읽은 원문 검수를 재사용하고 달라진 문장은 모두 따로 읽었다. 독립 D137개 전체를 두 명이 검수한 시험은 아니며, 변경된13출력/보강의 완전일치 실패19건/추가20문항을 직접 검토했다.

## 5. 채택 범위

**현재 시연에는 고정 실행 안내를 유지하는 쪽을 권고한다.** 필수 시나리오뿐 아니라 모호한 변경 요청 뒤 명시적 실행도 이번 고정 안내 조건에서 통과했다. Response는 실행 이외56/82턴에서 실제 답변했고 Q도 각 조건7번 실제 호출됐다. 전체 대화를 Python 고정문장으로 대체한 평가가 아니다.

전체 보강 prompt는 기분 분류 개선 후보지만 일반대화/완곡한 섭취 제한을 모두 해결하지 못했고 독립 입력 회귀도 있으므로 운영 적용 완료로 판정하지 않는다. 별도 D6/Q6/Pbest150의 이전 평가상 후보 지위와 실제 운영 파일 교체 여부를 구분한다. 현재 보고서는 운영 배포 승인을 대신하지 않는다.

## 6. 실패에서 멈추지 않고 이어간 결과

[실제18턴과 상태·제한·계획 원문](../training/learning_first_v43/final/goals/GL10/dqp_prompt_multiturn_20261105/failure_continuation/REVIEW.md). 이 개발 진단의34요청도 입력 JSON 값/자료형·raw·16K 한도·추가history trim0을 확인했다. 본328턴 점수에는 합산하지 않는다.

기존prompt에서 완곡한 섭취 곤란을 말한 뒤 페퍼론치노를 요청하면 **선택이 허용됐다**. restrictions가 비었기 때문에 Runtime이 강한 제한으로 차단할 근거가 없었다. 아직 담지 말라고 한 뒤 “매운맛은 아예 못 먹어. 페퍼론치노는 빼고 치즈만 적게 골라줘”라고 정정하면 restriction이 저장되고, 다음 페퍼론치노 추가는 차단됐다. 치즈low 최종 실행도 맞았다. 잘못된 물리 실행은 수행하지 않았다.

보강prompt는 이extra단계 입력에서는 완곡한 표현도 제한으로 추출하여 처음부터 페퍼론치노를 차단했다. 원래noodle단계 독립 입력의 실패를 이 성공으로 대체하지 않는다. 동일한 말이라도 상태가 바뀌었을 때 강한 제한 추출의 안정성이 충분하지 않다.

기존prompt의 실행 누락은 실제 실패 직전 상태를 복원했을 때 재현됐다. 다음 “아까 말한 대로 양파만 지금 바로 담아줘”에서 양파1 실행으로 회복했고, 버섯을 함께 담았는지 묻자 제거된 상태라고 답했다. 실패를 정답 state로 고치지 않았으며, 사용자 재요청이 회복의 계기였다.

보강prompt를 같은 실패 직전 상태에 적용한 대조에서는 첫 요청부터 commit이 생성됐다. 그런데 이 대조는 원래patched_model의 실패 요청과 **8,825개 입력토큰·생성 한도·stop token·grammar가 모두 같다.** 모델 등록 경로와 서버argv도 같다. 클라이언트는temperature0, 서버 seed0, batch invariant1이었고 재사용 캐시는 원래8,576 vs 재실행8,320이었다. 따라서 성공만 보고 보강prompt가 실행 누락을 해결했다고 판정하지 않는다. ### 동일 요청 재현성 대조

평가용 localhost 서버에서만 cache reset API를 활성화해 하나의 요청을7조건씩 비교했다. 운영 서버에는 적용하지 않았다. 첫 실행의 prefix priming은 마지막64토큰 블록이 재사용되지 않아 실제cache가8,256/8,512였다. 이 원본 결과를 보존하고, 별도 실행에서 실제cache를8,320/8,576으로 정확히 맞췄다. 두 실행 각각 target7호출+priming4호출이며 추가 반복은 하지 않았다.

| 별도 서버 실행 | 실제 cache 조건 | 동일한 target 요청7회의 결과 |
|---|---|---|
|첫 캐시 대조|0, 8,768, 8,256, 8,512 및 반복|모두commit=true|
|정확한 블록 대조|0, 8,768, 8,320, 8,576 및 반복|모두commit 누락|

두 실행의 첫cache0 요청부터 결과가 다르다. 따라서 **캐시 길이만 바꾸면 문제가 해결된다는 가설은 지지되지 않았다.** target 요청14개는 토큰·생성 조건이 동일하고, 서버 인자·선택 어댑터 경로도 같다. 세 선택adapter 바이너리 SHA는 최종에도 원래 선택값과 일치한다. `temperature=0`, 서버seed0, `VLLM_BATCH_INVARIANT=1`을 확인했지만 서버 실행 간 완전 결정성을 보장했다고 말할 수 없다.

**내부 근본 원인은 UNKNOWN이다.** 초기화/양자화/선택된 kernel 등 어느 내부 단계인지는 이 자료만으로 특정하지 않는다. 다음 진단은 같은 cold 요청을 기준으로 기동 시 계산 경로와 실제 로딩된 tensor를 계측하는 별도 작업이어야 한다. 캐시를 끄거나 dtype을 바꾸면 해결된다고 추측해 운영 설정을 바꾸지 않았다. 이 제한 때문에 본 표의 수치는 각 조건 한 실행에서의 관측이며 재기동 후 보장 성공률이 아니다. ## 7. 종료와 다음 적용 범위

실제 요청은 본 비교910+실패후속34+캐시진단22=**966 HTTP completions**이다. 캐시 priming8개는 고의로max_tokens1을 사용한 입력 준비이므로 모델 정확도/잘림 실패 분모에서 제외한다. 본 비교910과 후속34는 모두 정상stop이다. 모든 진단 로그와 실패 로그는 남겼다.

동결된 source38개·processor5개·입력 파일은 불변이며 선택한3adapter SHA도 불변이다. CPU 사전검사와 실패 후 실제 상태 유지 테스트2개는 통과했다. 실제 서버4개 모두 stop0/process0, 정확한 unit 이름4개 inactive, GPU compute 목록 비어 있음,18001/8000포트 반환을 최종 확인했다. [실제 성공한 시연 후보5개와 답변 원문](2026-11-05_verified_multiturn_scenarios.md)을 기준으로 대화 흐름을 검토할 수 있다. 시연 후보라는 뜻이며 재시작 안정성/임의 표현/완곡한 섭취 제한까지 완전 합격한 배포 승인서는 아니다. 운영 Decision 어댑터·고정 안내·프롬프트는 이번 작업에서 교체하지 않았다.

Effect: 단일 성공과 완전일치 점수만으로 운영 채택을 확정하지 않고, 고정 실행 안내 유지와 조건부 평가 결과/남은 원인을 기록한다.
