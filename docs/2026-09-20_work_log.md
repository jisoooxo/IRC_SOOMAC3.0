## 1. V7 분리 및 실행 안전성 강화

V6를 유지한 채 다음 V7 파일을 별도로 사용한다.

| 파일 | 역할 |
|---|---|
| `order_v7.py` | 메뉴, restriction, 물리 section 정본이다. |
| `agent_v7.py` | Tool 결과 검증, 명시적 진행 의도 확인, 물리 상태 방어를 담당한다. |
| `call_model_v7.py` | Tool 분류와 구조화된 자유응답 생성을 담당한다. |
| `llm_node_v7.py` | ROS 상태와 Agent transaction을 연결하고 최종 응답을 발행한다. |

V7 턴 순서는 다음과 같이 변경했다.

```text
Agent 결과 생성
  → 결과 형식 검증
  → 최종 응답 생성 성공
  → 주문·실행 상태 commit
  → 사용자 응답 발행
```

응답 생성이 예외로 실패하면 주문, 실행 상태, history, action history를 commit하지 않는다.

Cause: 응답 생성보다 상태 commit이 먼저 발생하면 사용자에게 결과가 전달되지 않은 턴도 내부 상태에는 반영될 수 있었다.

Effect: 응답을 만들지 못한 실패 턴은 미처리 상태로 남으며 다음 턴과 실제 주문이 어긋나지 않는다.

## 2. 명시적 진행 의도와 pending 확인 parser

`confirm_section` 또는 `set_order_and_confirm`으로 Tool이 분류됐다는 사실만으로 로봇을 시작하지 않는다. 사용자 원문에 명시적인 진행 의도가 있어야 Python 검증을 통과한다.

```text
사용자: 양파 적게 맞지?
모델 Tool 오분류: confirm_section
결과: 양파 작업을 시작하지 않고 명시적인 진행 요청을 요구한다.
```

```text
사용자: 그대로 진행해
결과: 필수 선택값과 물리 상태가 정상이면 현재 section 작업을 시작한다.
```

확인 응답은 공용 parser에서 부정어를 먼저 검사한다.

```text
"네, 그래도 넘어가지 마" → 거부
"조금 생각해볼게" → 모호함, 네/아니요 재질문
"응, 넘어가" → 승인
```

추천안도 명시적 동의가 없으면 주문에 반영하지 않는다.

## 3. 이미 담긴 재료 변경·제외 방어 확인

V6와 V7을 대상으로 완료된 `양파`에 다음 네 요청을 직접 넣어 검증했다.

| 사용자 의도 | 내부 처리 | 사용자 안내 | 로봇 정지 |
|---|---|---|---|
| `양파 빼줘` | `blocked_active_or_completed` 또는 `blocked_past_section`으로 삭제 차단 | 이미 담기 시작한 항목은 변경할 수 없다고 안내한다. | 없음 |
| `양파가 싫어` | dislike restriction은 기록하되 물리적으로 담긴 양파는 유지한다. | 이미 담기 시작해서 취소할 수 없다고 안내한다. | 없음 |
| `양파 알레르기가 있어` | allergy restriction은 기록하되 담긴 재료와 active/completed 상태를 유지한다. | 철회할 수 없으며 섭취에 유의하라고 경고한다. | 없음 |
| `양파를 먹을 수 없어` | cannot-eat restriction은 기록하되 담긴 재료는 유지한다. | 철회할 수 없으며 섭취에 유의하라고 경고한다. | 없음 |

로봇 작업 중에는 `llm_node_v6.py`와 `llm_node_v7.py`가 `active_task` 또는 `task_queue`를 확인해 늦게 들어온 STT를 주문에 반영하지 않는다. 작업 완료 뒤 같은 요청이 들어오더라도 Agent가 `completed_tasks`와 현재 section을 검사해 이미 끝난 재료를 삭제하거나 변경하지 않는다.

직접 검증 결과는 V6·V7의 네 상황에서 모두 다음 조건을 만족했다.

```text
기존 주문 재료 유지
completed_tasks 유지
robot_started 유지
로봇 stop 명령 생성 없음
상황별 경고 응답 생성
```

(내가 의역해보자면 이미 그릇에 들어간 재료는 주문표에서 지워서 없던 일로 만들지 않고, 뒤늦게 들어온 안전 정보는 경고와 이후 선택 제한에만 사용한다.)

Cause: 주문 데이터만 삭제하면 실제 도시락과 화면·대화 상태가 서로 달라진다.

Effect: 물리적으로 시작·완료된 재료는 유지하고, restriction과 사용자 경고만 추가한다.

## 5. V6 소스 VLM 실패 후 정지 현상

V6의 의도된 동작은 영구 정지가 아니다.

```text
1차 non-PASS
  → /vlm/confirm에 fail 발행
  → main이 /main/confirm으로 재작업 요청
  → control의 /control/vlm_confirm_ready 대기
  → 2차 VLM 판정
  → 2차도 non-PASS이면 policy_success로 공정 진행
```

실제 로그에는 토마토의 1차 `FAIL`과 `robot_retry`까지만 있고 두 번째 `/llm/confirm_start`가 없다. 저장소 내부에서는 `/main/confirm` 소비자와 timeout/watchdog을 확인하지 못했다.

소스 section의 `/llm/next`는 완료 처리 대신 `/llm/reset`을 기다리며, `/llm/reset`도 VLM 확인 전에는 보류한다. 따라서 외부 control이 재작업 후 ready를 다시 보내지 않으면 계속 대기할 수 있다.

Cause: 재작업 요청 뒤 새로운 ready 신호에 의존하지만 이 저장소 안에는 해당 소비 계약과 timeout이 없다.

Effect: 소스 실패 뒤 멈춰 보이는 현상은 정상 완료가 아니라 control–VLM handshake가 중간에서 끝난 상태이다.

실행 로그에서 뚜껑은 작업 후 이미지 5장과 직전 비교 이미지로 판정했으며 다음 결과를 냈다.

```text
검은색 뚜껑이 도시락을 정상적으로 덮음
판정: PASS
```

이후 토마토 판정에는 참고 이미지, 닫힌 뚜껑 비교 이미지, 작업 후 이미지 5장으로 총 7장이 전달됐다. 참고 이미지는 저해상도 `Napoli Tomato` 포장지이며 포장지 중앙에 파스타 사진이 인쇄되어 있다. VLM은 이 인쇄 사진을 실제 파스타 음식으로 오인해 토마토 포장지가 없다고 판정했다.

또한 VLM 입력 토픽은 원본 카메라가 아니라 `/vision/overlay_image`이다. 앞선 판정에서 VLM이 `noodle_thin`, `onion` 같은 화면 표시 글자를 실제 투입 근거로 사용한 기록이 있다.

## 7. V6·V7 소스 VLM 프롬프트 보강

토마토·오일·크림 세 종류에 공통으로 다음 규칙을 적용했다.

- 판정 대상은 소스 내용물이 아니라 **밀봉된 소스 포장지**이다.
- 포장지에 인쇄된 파스타·토마토·음식 사진을 실제 음식으로 해석하지 않는다.
- bounding box, class 글자, 체크 표시 같은 overlay를 실제 물체의 증거로 사용하지 않는다.
- 브랜드, 포장 방향, 크기, 세부 디자인 차이만으로 FAIL하지 않는다.
- 포장지가 없거나 명확히 다른 소스이거나 뚜껑이 실제로 열렸을 때만 FAIL한다.
- 가림·흔들림·반사로 종류를 확인할 수 없으면 UNCERTAIN으로 판정한다.

종류별 허용 표기는 다음과 같다.

| 소스 | 같은 종류로 인정하는 표기 |
|---|---|
| 토마토 | `tomato`, `pomodoro`, `Napoli`, `나폴리`, `토마토` |
| 오일 | `oil`, `olio`, `오일` |
| 크림 | `cream`, `크림` |

RAG 참고 이미지는 세 종류 모두 존재한다. 확인된 크기는 토마토 `142×250`, 오일 `150×241`, 크림 `136×247`이다.

## 9. 저장 공간과 GitHub 접속 점검

Git 오류 `Could not resolve host: github.com`은 저장 공간 부족과 무관했다.

```text
전체 용량: 1.4 TB
사용: 768 GB
여유: 559 GB
사용률: 58%
inode 사용률: 3%
저장소 크기: 74 MB
Git garbage: 0 bytes
```

점검 시점에는 `github.com` DNS 해석, HTTPS `200`, `git ls-remote`가 모두 성공했다. 화면의 오류는 발생 당시의 일시적인 DNS 또는 네트워크 이름 해석 실패이며 정확한 일시 장애 원인은 남은 로그가 없어 알 수 없다.

## 10. V7 VLM 판단 근거 TTS 선택 기능

V7에 다음 상단 설정을 추가했다.

```python
VLM_JUDGE_REASON_SPEAK = False
VLM_JUDGE_REASON_MAX_CHARS = 300
```

`False`에서는 기존 고정 안내만 발행한다. `True`에서는 VLM 출력의 마지막 판정 줄을 제거하고, 최대 300자의 관찰 근거와 기존 안내를 한 문장으로 합쳐 `/llm_response`에 한 번 발행한다.

소스 작업 이름은 다음처럼 손님용 표현으로 바꾼다.

```text
토마토 → 토마토 소스
오일 → 오일 소스
크림 → 크림 소스
```

VLM 예외 문자열 `ERROR:`는 TTS 근거에서 제외한다. UNCERTAIN과 PASS 발행 뒤에는 각각 `return`하여 다음 FAIL 정책으로 내려가지 않게 했다.

검증 상태:

```text
Python 문법 검사: 통과
실제 GPU·카메라·TTS 통합 실행: 미실시
기본 토글: OFF
```

Cause: 기존 VLM 설명은 로그에만 남고 손님은 고정 결과 문장만 들었다.

Effect: 시나리오 평가 때 상단 토글 하나로 관찰 근거와 기존 안내를 한 번에 들려줄 수 있다.

## 11. 손님 UI 추천 상태 표시

Agent·Tool·멀티턴 상태를 변경하지 않고 `llm_node_v7._publish_status()`에서 UI 전용 값을 파생한다.

```json
{
  "recommendation_status": "confirming",
  "recommendation_sections": ["면", "야채", "육류", "추가 재료"]
}
```

손님 화면의 `현재 주문` 아래에는 상태에 따라 다음 안내 중 하나를 표시한다.

```text
추천할 범위를 확인하고 있어요
추천 조합 확인 대기 · 면, 야채, 육류, 추가 재료
추천 확정 · 자동 진행 예정 · 육류, 추가 재료
추천 재료 자동 투입 중 · 육류
```

추천 상태가 없으면 배지를 숨긴다. 기존 `/agent/status` 토픽과 Socket.IO `agent_status` 이벤트를 그대로 사용한다.

검증 상태:

```text
Python 문법 검사: 통과
인라인 JavaScript 문법 검사: 통과
git diff --check: 통과
실제 ROS·브라우저 통합 실행: 미실시
```

Cause: 확정 전 추천안은 실제 `order`와 분리되어 있어 기존 UI에서는 주문이 전부 비어 보였다.

Effect: 실제 주문을 미리 반영하지 않고도 추천 대기·확정·자동 실행 여부를 손님에게 표시한다.

## 12. 추천안 일부 수정 로그 분석

`tool_turns_20260920_170316_620433.jsonl`에서 다음 흐름을 확인했다.

```text
추천안: 토마토, 얇은면, 양파, 소시지, 치즈
사용자: 소시지는 빼고 싶어졌어.
Tool 출력: set_order {toppings: {소시지: none}}
실제 결과: 실제 order가 비어 있어 ignored_same_value
추천 결과: 대기 중인 추천안의 소시지는 그대로 유지
```

전부 삭제된 것이 아니라, 확정 전 추천안이 실제 주문에 아직 들어가지 않았고 UI가 실제 주문만 보여줘 전부 사라진 것처럼 보였다. 동시에 `set_order`가 실제 주문을 대상으로 실행되어 소시지 제외 요청도 추천안에 반영되지 않았다.

현재 `set_order` 계약은 현재 section 필드로 제한되지 않는다. `sauce`, `noodle_type`, `noodle_portion`, 모든 `toppings`, `restriction_changes`를 받을 수 있고, Python이 active·completed·과거 section을 차단한 뒤 현재 또는 미래 section 변경을 실제 `order_after` 복사본에 적용한다.

## 13. 추천안 일부 수정 방어 — 구현 완료

당장은 Tool 프롬프트 의미를 바꾸지 않는다. 현재 LoRA가 학습한 프롬프트·라벨 분포와 달라질 수 있기 때문이다.

Python에 좁은 방어 분기를 구현했다.

```text
recommendation.phase == confirming
AND Tool == set_order 또는 set_order_and_confirm
AND 변경 대상이 현재 대기 중인 추천안에 실제로 존재함
  → 실제 order는 그대로 유지
  → recommendation 복사본에서 해당 항목만 수정
  → 전체 추천안을 다시 검증
  → 수정된 추천안을 다시 읽고 확인 요청
```

변경 대상이 추천안에 없거나 대상이 불명확하면 실제 주문에 적용하지 않고 어느 대상을 바꾸려는지 재질문한다. `restriction_changes`는 알레르기·섭취 불가 안전 정보가 있으므로 단순 추천안 편집으로 흡수하지 않고 실제 restriction 정책과 추천안 재검증을 함께 거쳐야 한다.

추천안 수정만 요청한 발화에는 확인 의도 parser를 사용하지 않는다. `set_order_and_confirm`처럼 수정과 실행을 함께 요청했을 때만 원문을 다음 순서로 판정한다.

```text
명시적 부정 → False
질문·주저·모호 표현 → None
명시적 진행 표현 → True
나머지 → None
```

parser는 부정어를 먼저 검사하고 `진행해도 될까`, `시작해야 하나` 같은 질문형·주저 표현을 긍정 표현보다 먼저 `None`으로 처리하도록 보강했다.

회귀 사례:

```text
소시지만 빼줘 → 추천안의 소시지만 제거, 실제 order 유지, 재확인
양파를 적게로 바꿔줘 → 추천안의 양파 양만 변경, 재확인
소시지 빼고 진행해 → 수정 후 명시적 확인을 통과할 때만 반영·실행
소시지 빼되 진행하지 마 → 추천안만 수정하고 실행하지 않음
소시지 빼고 진행해도 될까 → 모호함으로 처리하고 재질문
```

Cause: 프롬프트만 바꾸면 기존 Tool LoRA의 학습 분포와 runtime 지시가 어긋날 수 있고, 현재 `set_order` 일반 경로는 실제 주문 복사본을 수정한다.

Effect: 프롬프트와 여덟 Tool 계약을 유지하면서 관측된 오분류만 Python에서 좁게 흡수하고 실제 주문 변경을 막는다.

별도 장기 계획은 [`2026-09-20_tool_reply_adapter_plan.md`](./2026-09-20_tool_reply_adapter_plan.md)에 기록했다.

직접 수정 위치와 스니펫은 [`2026-09-20_pending_recommendation_edit_guide.md`](./2026-09-20_pending_recommendation_edit_guide.md)에 기록했다.

## 14. LLM Debug와 실운영 Reply 경로 통합

`reply_v7.py`에 실운영과 다른 Debug 전용 응답 방어가 존재하면 Debug 결과와 실제 로봇 응답이 달라질 수 있다. 별도 구현을 제거하고 `llm_node_v7.py`의 모듈 함수 `build_turn_reply()`를 실운영 Node와 `llm_debug_v7`이 함께 호출하도록 변경했다.

Debug는 `LLMNode`를 생성하지 않으므로 ROS topic·카메라 subscriber를 만들지 않는다. `describe_scene`에는 카메라 없음 응답을 전달하며 VLM·RAG는 사용하지 않는다. 이를 위해 `VlmRag` import를 `ENABLE_VLM`인 실제 Node 생성 시점으로 이동했다.

검증 결과:

```text
V7 응답·Debug·Tool 전환 테스트: 43 passed
Python compile: PASS
git diff --check: PASS
```

Cause: Debug 전용 Reply 구현이 실운영보다 더 많은 문장을 차단해 동일 입력에도 결과가 달라질 수 있었다.

Effect: 자유응답 생성·필터·정책 문장 결합은 실운영과 Debug가 같은 함수를 사용하고, Debug에서는 VLM과 외부 topic만 실행하지 않는다.

## 용어 정리

- **active task**: 로봇이 현재 실행 중인 한 작업이다.
- **completed task**: 실제 로봇 작업이 끝나 물리적으로 되돌릴 수 없는 작업 기록이다.
- **physical conflict**: restriction이나 삭제 요청과 실제로 이미 담긴 재료가 충돌하는 상태이다.
- **overlay image**: 원본 카메라 위에 bounding box, class 이름, 상태 표시 등을 그린 영상이다.
- **handshake**: 여러 ROS 노드가 요청과 준비 완료 신호를 주고받아 다음 상태로 이동하는 계약이다.
- **policy success**: 재시도도 non-PASS일 때 실제 PASS로 기록하지 않으면서 공정만 진행시키는 정책 결과이다.
