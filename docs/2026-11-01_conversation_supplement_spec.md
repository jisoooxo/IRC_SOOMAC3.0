## 1. 기본 시연 — 기존 보강본을 재사용한다

초기 주문은 비어 있고, 지원 메뉴·안전 조건이 유효하며 로봇은 대화 가능한 상태이다. 소스는 크림을 금지하는 제한이 없는 것으로 한다. **턴 사이의 실제 제조 완료와 단계 전환을 별도 입력으로 제공해야 한다.** 사용자 발화만으로 단계를 넘어간 사실을 만들지 않는다. 오프라인 재생에서는 이를 명시된 모의 bridge로 기록하고 실제 완료로 보고하지 않는다.

위 표 다음 추가 재료 단계에서는 **“페퍼론치노는 빼고 치즈만 적게 골라서 바로 담아.”**를 사용한다. D는 치즈low·페퍼론치노none·commit=true를 함께 표현한다. 적용 후 실제 주문에는 페퍼론치노 키가 없고, 기존 게살allergy와 다른 확정량은 유지되어야 한다. 실행 대상은 치즈low이며 페퍼론치노 담기·새 추천·반복 실행 확인은 없다.

표의 P 문장은 허용 답변의 예시이다. 한 문장으로만 정답을 고정하거나 Python 응답 템플릿으로 넣지 않는다. 동일한 의미와 사실·질문 계약을 만족하는 존댓말 표현을 허용한다. **현재 실행 시작 안내는 기존 deterministic 경로를 유지하므로, 해당 경로에 없는 P 학습 행을 만들지 않는다.**

단계 전환의 야채·육류·추가재료 안내는 별도 상단 토글 `hard_cording_response`로 선택한다. 기본True는 기존 고정 안내, False는 실제 전환event에 대한 기존 Q/P 모델 경로이다. 기존 데이터의 고정 단계 안내history는 그 모드에서 실제 발화한 문맥이므로 가짜user로 바꾸거나 지우지 않는다. 모델모드 검증에는 실제event·user_text=null과 조건부Q/P 입력을 사용한다. 뚜껑/소스 자동 실행 안내와 시작 안내를 이 토글로 일괄 제거하지 않는다.

## 2. 새로 보강할 대화 — 다섯 묶음

### A. 주문과 추천을 동시에 받는 대화

현재 train에서 `order` patch + 추천request 조합은 드물다. 다음은 **제안하는 새 의미 변형**이며 기존 후보 중복 여부는 생성 시 확인한다.

| 대화 | D 정답 | Q/P 정답 기준 |
| --- | --- | --- |
| “얇은면은 조금만 골라줘. 소스는 고소한 쪽으로 추천받고 싶어.” | 면 얇은면/low 확정 + 추천request, commit 없음 | 제한 없는 이 fixture는 크림 후보. 새 후보를 확정으로 말하지 않고 자연스럽게 선택 질문 |
| 앞서 “양파는 적게 먹고 싶어.” → “버섯은 보통으로 고르고 고기는 추천해줘.” | 버섯normal + 추천request. 기존 양파low 유지 | 현 scope와 제약 내 육류 후보. 다른 항목의 low를 새 육류량으로 옮기지 않음 |
| “면은 보통 양으로 할게. 소스는 나중에 고를 테니까 지금 추천하지 마.” | 현재 지시 대상이 명확할 때 면normal, 추천request 없음 | Q 미호출. 소스 미선택을 안내할 수 있으나 크림 후보·확인 질문을 지어내지 않음 |

소스·면이 미정이고 “매운 걸 못 먹는데 뭘 먹을까?”라는 넓은 요청에는 선택 가능한 안전 소스와 면을 함께 고려한다. 제한 없는 fixture의 크림 예시를 쓰되 **유제품 알레르기 fixture에서는 크림 금지**이다. “못 먹는다”는 현재 합의대로 `cannot_eat`, 명시 알레르기는 `allergy`로 구분한다. 모든 비매운 요청을 크림으로 고정하는 자료는 만들지 않는다.

### B. 같은 실행 표현, 다른 직전 질문

| 앞선 문맥 | 이번 발화 | 정답 |
| --- | --- | --- |
| 미확정 크림 후보를 “이걸로 고를까요?”라고 물음 | “응, 그걸로 골라줘.” | 추천 수락·크림 확정. 추가 실행 의도가 없다면 실행 시작 없음 |
| 같은 추천 후보 | “응, 그걸로 골라서 바로 진행해.” | 후보 수락·크림 확정과 commit=true를 함께 처리 |
| 양파low/버섯normal의 유효 실행 확인 대기 | “응, 그걸로 해.” | 현재 실행 확인 수락. raw accept 또는 명시 commit 표현을 계약에 따라 인정하고 effective 실행을 검사 |
| pending은 없지만 앞 사용자와 현재 state가 크림/얇은면/normal을 명확히 확정함 | “처음에 정한 걸로 지금 담아.” | history와 state로 대상을 해석하고 commit=true. pending 부재만으로 의미를 보류하지 않음 |

`바로 담아`, `바로 담아줘`, `바로 담도록 해`, `바로 진행해`, `지금 담아줘`를 사용하되 부정·인용·조건·과거 회상과 짝지어 검수한다. “아직 바로 담지 마”는 선택을 보존하고 실행을 거절한다. **문자열 포함을 기준으로 모든 commit을 true로 만드는 데이터나 Python 규칙은 사용하지 않는다.**

| 앞 assistant는 크림을 확정했다고 했지만 실제 소스null, applied에소스없음, 실행불허 | “크림으로 요청하셨는데 아직 주문에 반영되지 않아 담기를 시작하지 못했어요.” | 크림 확정/담기 시작을 거짓으로 말하기, 없는 execution pending에 “담을까요?” 붙이기 |

복구 예시는 정상 직원형 대화의 목표가 아니라 **오류가 발생했을 때 거짓말을 하지 않는 경계**를 학습하기 위한 것이다. 사용자가 이미 크림을 명시했다면 이를 못 알아들은 척 반복 질문하는 문장을 기본 정답으로 강요하지 않는다. P가 state를 수정하거나 새실행을 만들 수는 없으므로, 자연스러운 정상 성공은 D의 선택/추천/commit 추출 개선으로 해결해야 한다.

위 답변들도 `policy`, `next_prompt`, `applied_this_turn`, 실제 완료 증거와 함께 정식 builder로 만들어 검수할 초안이다. 입력에 없는 내부 오류 원인까지 “저장이 실패해서” 등으로 단정하지 않는다. `execution_authorized=false`가 이번 실행 불허를 뜻할 뿐 과거 작업 전체 미완료를 뜻하지 않으므로, 항목별 완료 증거를 확인한다.

**추가 필수 기준: 같은 안내·추천·질문을 불필요하게 반복하지 않는다.** 표현만 바꿔 동일한 실행 확인을 매 턴 재요청하는 것도 반복이다. 사용자 발화와 직전 assistant 답변, 이번 변경, 현재 질문의 목적을 함께 읽어 필요한 차이만 이어서 말한다. 이를 문자열 중복률만으로 합격/탈락시키거나 Python에서 응답을 잘라 숨기지 않는다.

반복 방지는 사실·질문·안전 고지를 생략하라는 뜻이 아니다. 주문·대상·수량이 달라져 새 확인이 필요하거나 사용자가 재확인을 요청하면 다시 설명할 수 있다. 다음 관련 단계에서 유효한 취향·제약을 근거로 자연스럽게 권유하는 것도 허용한다. 이미 수락/거절한 같은 후보를 새 요청 없이 다시 내거나, 알레르기 저장 안내를 매 턴 덧붙이는 것은 피한다. 짧은 문장과 같은 재료명을 재사용한 것 자체는 실패가 아니다.

Cause: 한 턴의 그럴듯한 답변만 맞추면 이전 답변을 반복하며 진행을 멈추는 문제가 남을 수 있다.

Effect: 학습 입력에 실제 직전 assistant 답변을 포함하고, 새 변경에 대한 답변·새 질문 필요성·이미 받은 실행 동의를 함께 검수한다. 반복을 피하려고 사실·수량을 바꾸거나 새 추천을 만들지 않는다.

## 3. 데이터로 만들 때의 결속과 검수

1. **기존 결과 재사용:** ID만 비교하지 않고 input/system/target의 엄격 의미 키와 이전 FIX/HOLD를 연결한다. 기존 기본 시연과 동일한 새 행은 추가하지 않는다. 기존 HOLD12를 미해결 위임실행의 긍정 정답으로 바꾸지 않는다.
2. **턴 전후 대조:** before의 주문·선호·제약·pending·현재물리단계, D patch와 commit, after의 실제수량·제외·후보, 실행허가와plan을 함께 검증한다. Graph가 막은 잘못된 실제 모델 출력에 맞춰 정답을 약화하지 않는다.
3. **D/Q/P 입력 연결:** 정상 대화는 D정답을 실제 Graph로 적용해 Q/P 입력을 얻는다. 오류 복구는 실제 실패 trace 또는 원인을 명시한 실패주입 branch로 구분한다. 정답 D를 적용했는데 실패state를 정상after처럼 붙이지 않는다. Q/P 미호출 경로에 가짜 행을 만들지 않는다.
4. **표현·의미 대조:** 조사/받침·존댓말/반말 사용자 입력·수음 변형을 포함하되 assistant는 자연스러운 존댓말로 한다. 같은 마지막 문장에 다른 앞대화를 줬을 때 달라질 필드와 변하지 않을 필드를 명시한다. 직전 assistant의 반복을 피해야 하는 경우와 사용자 요청으로 재설명해야 하는 경우를 짝지어 검사한다. 의미가 같은 문장을 무작위로 바꾸는 것만으로 반복 해결이라고 보지 않으며, 문구 regex만으로 의미 합격/삭제하지 않는다.
5. **학습/평가 분리:** 이 사용자 시나리오는 seen이다. 같은episode와 의미적으로 가까운 파생 변형을 train/평가에 흩뿌려 unseen 성적을 만들지 않는다. 현재train의 부족한셀을 우선하되 수치quota·전체편향합격은 임의로 선언하지 않는다.

취소 명령인 `none`은 Decision의 취소 patch에만 쓰며 persisted order에는 남기지 않는다. 확정량·수락한 유효후보량·사용자 명시량이 있으면 그 값을 보존하고, 근거 없는 **새** 선택/추천량만normal이다. Q의 근거는 현재 유효사용자발화/선호/제약과 연결하고, P가 이를 자연스럽게 설명하되 검증되지 않은 이유 문구를 사실처럼 복사하지 않도록 한다.

## 4. 이번 산출물과 다음 작업

처음에는 **기존 재사용 대상과 신규 대화·정답 기준을 구분한 명세**를 만들었다. 후속 생성 승인 뒤에는 §6과 같이 실제342행 초안과 비활성 미리보기를 생성했다. 표의 모든 가능한 변형이 이미 들어갔다거나 최종 의미검수가 끝났다는 뜻은 아니다. 기존 후보를 덮지 않는다.

다음 한 작업은 생성한 새행의 문맥 의미·반복·오류복구를 최종검수하는 것이다. 원본 source/확정 장부를 먼저 연결하고, C/E의 대조와 같은 묶음에서 검사한다. 의미 정답만 나열한 이 문서나 CPU 정답주입 통과를 실제 모델 합격으로 보고하지 않는다.

Cause: 시연 성공에 필요한 복합 출력과 실패 복구를 기존 자료의 단순 복제로 채울 수 없다.

Effect: 무엇을 재사용하고 어떤 새 대화를 만들지 확정할 수 있으며, 기존 정상 기능을 보존한 국소 보강으로 이어갈 수 있다.
