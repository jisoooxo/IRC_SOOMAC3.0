## 1. 사용자 최종 목표

이전 대화와 현재 주문·취향·제약·실제 로봇 상태를 함께 이해하는 자연스러운 직원형 대화이다. 단일 문장 분류기나 현재 단계 메뉴를 반복하는 안내기가 아니다. (내가 의역해보자면, 손님이 말을 이어가거나 번복해도 직원이 지금 주문을 놓치지 않고 자연스럽게 다음 선택을 도와주는 것이다.)

핵심은 복합 멀티턴 이해, 현재부터 미래까지 유연한 추천·주문 수정, 취향/후보/확정/실행의 분리, 이유와 제안을 연결하는 응답, 실제 상태에 맞는 말이다. 자연스러움을 특정 한 문장·매번 권유·무조건 짧은 답으로 고정하지 않는다. 모델은 입력 말투와 별개로 일관되고 자연스러운 존댓말을 사용한다.

**섹션에 구애받지 않는다는 것은 대화·추천·변경 가능한 주문의 범위이다. 로봇 역주행·이미 담은 재료 회수는 현재 지원하지 않는다.** 코드에서는 실제 투입 여부뿐 아니라 지나간 section도 보호하므로, 지나간 빈 단계를 다시 여는 기능까지 있다고 말하지 않는다.

## 3. 기능별 확인 목록

여기서 코드 확인은 독립 oracle의 구조화 판단을 받았을 때의 상태/실행 처리 검사이다. 모든 자연어를 실제 모델이 이해했다는 의미가 아니다.

### 3.1 주문 추가·삭제·번복

| 기능 | 확인 범위와 주의점 |
|---|---|
| 여러 재료·수량 동시 주문 | 여러 field를 같은 턴에 반영하는 경로 확인 |
| 둘 다 조금으로 번복 | 최신 주문·pending·실행량 정합성 대조. 실행 시작 후는 보호 |
| 삭제+추가+취향 변경 | 가능한 정상 부분을 보존하고 거절된 부분은 별도 설명 |
| 수량 생략 | 최신 명시량 우선, 유효 수락 후보량/기존 확정량 보존, 둘 다 없는 새 항목만 normal |
| 그거/나머지/둘 다 | 앞선 복수 발화·후보·직전 질문·현재 주문을 모델이 판단. Python 키워드로 대상 고정 금지 |

### 3.2 단계 간 추천·미래 주문

| 기능 | 확인 범위와 주의점 |
|---|---|
| 남은 코스 전체 추천 | user 요청 입력에 현재+미래 변경 가능 범위 제공. 모든 빈 field를 반드시 채울 필요 없음 |
| 이번 육류만 등의 좁은 요청 | 모델이 요청 범위를 해석. Python이 모든 user 추천을 현재 단계로 축소하지 않음 |
| 미래 소스/재료 미리 선택 | 미래 주문 저장과 실제 투입을 구분 |
| 미실행 미래 주문 수정/취소 | 물리적으로 보호되지 않은 field는 변경 허용 |
| 해당 단계 도착 | 선호-only면 관련 후보 제안, 확정 주문이면 같은 선택 재질문 없이 실행 확인 |

사용자 요청과 단계 이벤트는 다르다. **사용자가 넓게 요청하면 남은 코스 전체**, 새 발화 없는 단계 이벤트에서는 현재 단계에 관련된 추천만 한다. event에 가짜 user 발화를 추가하지 않는다.

예: 면 단계에서 크림+소시지high+치즈제외를 미리 선택할 수 있다. 야채 단계에서 미래 소시지를low/소스를오일로 바꿀 수 있다. 육류 단계에서 미래 치즈를 취소할 수 있다. 아직 실행하지 않았더라도 지나간 단계로 돌아가는 변경은 현재 보호 규칙상 허용하지 않는다.

### 3.3 취향·제약·기억

| 기능 | 확인 범위와 주의점 |
|---|---|
| 매운 걸 못 먹음 | cannot_eat 강한 제한으로 보존, 페퍼론치노 후보/주문 안전 검사 |
| 게살 알레르기+육류 추천 | 게살 제외 후 허용 후보 검증. 대안/이유 의미 생성은 모델 담당 |
| 취향 철회 vs 주문 취소 | 취향 철회만으로 별도 확정 주문을 자동 취소하지 않음 |
| 최신 사용자 정정 vs assistant 오답 | history를 지우지 않고 사용자 근거·최신 structured state로 판단하도록 prompt 명시 |
| 잡담·상태 질문 중 주문 유지 | 불필요한 order/pending 변화 방지 회귀. 다음 주문 흐름 보존 |

최근20메시지 입력 창을 유지한다. few-shot 추가에 따른 추가 history 손실을 막도록 측정 입력 cap16384를 적용했다. 장문에서 무조건20개 모두 전달·무제한 원문 기억을 보장한 것은 아니다. 보존된 state와 최근 대화를 함께 사용한다. 모델이 최초 의미를 누락하면 구조 안전 검사만으로 그 사실을 알아낼 수는 없다.

### 3.4 실행·거절·단계 생략

| 기능 | 확인 범위와 주의점 |
|---|---|
| 새 주문+명시 즉시 실행 | 현재 유효 대상과 모든 검증 통과 시 불필요한 재확인 없이 실행 |
| 유효 실행 질문 뒤 수락 | 최신 대상/수량 대조·한 번 실행, 중복 차단 |
| 일반 주문/추천 수락 | 선택 수락을 자동 실행으로 승격하지 않음 |
| 추천/실행 거절·명확화 | 각 질문 목적 구분. 명확화 뒤 모호한 응으로 옛 주문 실행 금지 |
| 선택 단계 생략 | 현재 선택 해소가 필요하며 생략 자체로 재료 plan을 발행하지 않음. 빈 commit을 임의 skip으로 바꾸지 않음 |

미래 후보는 현재 실행과 무관하면 보존할 수 있지만, 미수락 미래 소스가 자동 lid/sauce 진입과 충돌하면 먼저 해소한다. 기존 자동 진행·ROS topic·실행 중 STT 차단을 유지한다.

### 3.5 응답·사실성

| 기능 | 확인 범위와 주의점 |
|---|---|
| 저장 단답 대신 이유+제안 | 검증된 후보와 모델 추천 이유를 Response에 전달. 이유 의미 자체는 Python 검증 완료라고 하지 않음 |
| 이전 취향 활용 | 현재 단계와 관련된 유효 정보만 연결. 철회된 취향 부활 금지 |

효과: 예시와 계약을 교정하고 후속 데이터/새 모델 필수 실패 항목으로 인계했다. 자유 생성 재발0의 증명은 아니다.

## 4. 강한 제한을 Python이 검사하는 이유와 해제 동작

**Python의 구조화 안전 검사와 Python의 자연어 재판정은 다르다. 전자는 유지하고 후자는 새로 추가하지 않는다.**

| 책임 | 담당 |
|---|---|
| 못 먹음/싫어함/가능해짐/철회의 의미와 대상 판단 | Decision이 user+history+state로 판단 |
| 저장된 제한이 매운맛/cannot_eat인 상태에서 페퍼론치노 충돌 검사 | Python의 domain 매핑·추천 후보 검증·주문/실행 검증 |
| 강한 제한 삭제 요청 후 확인 수락/거절에 따른 state 변경 | 기존 pending 기반 Python 안전 절차. 수락/거절 의미 판단은 Decision |
| 확인 질문·해제 결과·대안 추천을 자연스럽게 표현 | 정상 경로의 Response, 추천 후보 생성은 Recommendation |

`domain.py`의 매운맛→페퍼론치노 매핑은 메뉴 지식이지 사용자 발화를 검색하는 keyword parser가 아니다. Decision이 매운맛/cannot_eat 제한을 만들지 않았다면 Python은 원문을 읽고 임의로 새 제한을 만들지 않는다. 반대로 잘못된 강도로 모델이 구조화하면 불필요한 차단이 생길 수 있으므로, 못먹음/싫어함/약한선호/철회의 대조 데이터와 실제 모델 검증이 필요하다. 모델 오해 가능성을 없앴다고 단정하지 않는다.

원인: 강한 제한이 활성인데 모델이 실수로 충돌 후보나 실행을 내보내는 상황을 막아야 한다.
효과: 자연어 판단은 모델에 남기고, 활성 state의 안전 불변조건을 코드가 보장한다. 영구 페퍼론치노 금지나 치즈 자동 주문이 아니다.

### 4.1 제약 해제 후 다시 가능한가

**가능하다. 단 강한 제한은 기존 확인 절차에서 해제 수락까지 끝나야 한다.**

| 순서 | state/권한 변화 |
|---|---|
| 활성 매운맛/cannot_eat | 페퍼론치노 추천 후보 제외·충돌 주문/실행 차단 |
| Decision이 해당 제한 remove 요청 | 제한은 유지하며 restriction_removal 확인 pending 생성 |
| 해제 질문에 거절 | 제한 유지, 계속 차단 |
| 해제 질문에 수락 | 해당 target/reason 제한 제거, 남은 안전/물리 조건을 기준으로 선택지 재계산 |
| 이후 새 페퍼론치노 주문·명시 실행 | 다른 제한·물리/단계·busy 등 충돌이 없으면 정상 검증·실행 허용 |

해제만으로 과거 취소된 주문을 복구하거나 자동 실행하지 않는다. 같은 재료를 막는 별도 allergy/cannot_eat/dietary_rule이 남으면 그 제한은 계속 적용한다. 소프트 기호가 남으면 추천 선호도는 달라질 수 있다. 이미 지나간 단계의 변경 제한도 해제되지 않는다.

### 4.2 이번 추가 확인 결과

`training/learning_first_v43/final/goals/FOLLOWUP_20261026/restriction_lifecycle.py`로 실제 Graph에 구조화 oracle Decision을 넣어 활성차단→해제요청대기→거절유지→수락해제→후보복귀→새주문실행허용을 확인했다. 다른 제한 잔존·지나간 단계 보호·자동 주문복원 없음·입력 불변도 assertion 통과했다. 결과는 같은 디렉토리의 restriction_lifecycle.json이다.

**모델/ROS/학습 실행이 아니라 코드 진단이다. GL06의612테스트 집계에 이 진단을 더하지 않는다. Runtime 소스는 수정하지 않았다.**

### 4.3 멘트가 고정인가

제한 적용·철회 확인/거절/수락·정상 추천 문장은 Response 모델 경로이다. 매운맛 제한이면 반드시 같은 문장을 출력하거나 치즈를 자동 선택하도록 새 Python 문장을 넣은 것은 아니다. 실제 실행 시작 안내, 추천 불가능 fallback, 모델/발행 장애 안내 등 기존에 보존하기로 한 결정적 경로는 여전히 있으므로 모든 멘트가 비고정이라고 말하지 않는다. 정상 Response가 호출되는 것과 그 모델의 문장이 항상 자연스럽고 사실적이라는 보장은 별개다.

## 5. 사용자 시나리오의 목표 동작

| 흐름 | 올바른 처리 |
|---|---|
| 매운 걸 못 먹음+기분 추천 | 제한+넓은 추천 의도를 모두 반영. 이유+허용 구성 제안, 현재 면 고정 안내로 회피 금지 |
| 좋아+얇은면 조금 | 앞선 후보 수락+면 주문 동시 처리. 별도 실행 의도 없으면 plan0 |
