# D/Q/P 시작 워밍업 실제 측정 — 2026-11-05

**3/3 측정 완료. 대표 입력 3개는 16K/.58과 12K/.50 모두 함께 캐시 적중했다. 추가 입력 뒤 12K의 Q 캐시 적중은 0으로 떨어졌지만 추론은 정상 완료했고, 세 요청 합계는 최초 8.04초보다 빠른 3.80초였다. 운영 시작 절차에는 아직 적용하지 않았다.**

원인: 어댑터별 프롬프트 계산 결과를 재사용할 수 있지만, 캐시의 모든 부분이 계속 재사용 가능한 상태로 유지되지는 않는다.
효과: 시작 워밍업의 실측 이득은 있으며, 일부 캐시 미적중이 곧 추론 실패나 전체 효과 소멸을 뜻하지 않는다.

## 1. 실행 범위

- 현재 D6/Q6/Pbest150을 별도 LoRA로 사용했다. 기존 필수 시나리오의 실제 HTTP 입력 토큰·출력 상한·문법을 그대로 재생했다. 운영과 같은 NF4/BF16, batch invariant ON, prefix cache ON이다.
- 로컬 임시 포트18001에서 설정별37회, 총74회 추론했다. 현행16,384/.58과 기존 후보12,288/.50을 각각 기동했다. 두 조건은 길이와 GPU 예약률을 함께 바꾼 비교이다.
- 순서: 첫 D/Q/P 3회 → 동일 D/Q/P 3회 → 재반복3회 → 저장된 후속 입력25회 → 처음 D/Q/P 3회. 첫3회가 실제 구현 시 워밍업에 해당한다. 나머지는 측정용이다.
- ROS·STT·TTS·VLM 실제 요청·로봇 명령은 실행하지 않았다. 저장 입력의 재생이므로 모델 출력으로 다음 상태를 만드는 closed-loop 시나리오 재평가가 아니다. Response는 이번 필수 시나리오의 task 경로이며 general/mixed까지 모두 워밍업한 시험이 아니다.
- 원본 소스41개와 세 어댑터의 경로·가중치·설정 SHA가 실행 전후 동일하다. 운영 시작 코드, 기본16K/.58, 어댑터, 대화 기록은 변경하지 않았다.

## 2. 응답 완료 시간과 캐시

단위는 초. HTTP 요청부터 전체 응답 수신까지이며 TTFT·음성 응답 지연이 아니다. 첫 호출도 vLLM 기본 엔진 워밍업 이후이며 기존 디스크 컴파일 캐시를 사용했다. 새로운 서버의 prompt cache가 빈 조건이지, 디스크 캐시까지 지운 조건이 아니다.

| 조건 | D 첫 호출 → 워밍업 후 | Q 첫 호출 → 워밍업 후 | P 첫 호출 → 워밍업 후 | D+Q+P 합계 |
|---|---:|---:|---:|---:|
| 현행16K/.58 | 3.355 → 0.824 | 1.810 → 0.918 | 2.799 → 0.868 | **7.964 → 2.610** |
| 후보12K/.50 | 3.390 → 0.810 | 1.779 → 0.954 | 2.871 → 0.869 | **8.040 → 2.633** |

두 조건에서 최초 cached_tokens는 D/Q/P 모두0이었다. 워밍업 후에는 **D8,512/8,524, Q3,904/3,957, P7,744/7,750** 토큰이 적중했다. 다음 동일3요청 반복도 같은 적중량이며 합계는16K2.593초,12K2.584초였다.

동일 입력을 재사용한 효과이므로 임의의 새 사용자 발화가 항상 같은 속도를 낸다는 뜻은 아니다. 입력·출력 토큰 수와 JSON 결과가 같은 반복끼리 비교했으며, 초기 비용 감소를 prefix cache 하나의 효과로만 분리해 측정하지는 않았다.

## 3. 추가 입력 뒤 캐시가 없어지는 경우

저장된 서로 다른 대화 상태 입력25개를 추가 처리한 뒤 처음3요청을 다시 보냈다.

| 조건 | D 적중/시간 | Q 적중/시간 | P 적중/시간 | 합계 |
|---|---:|---:|---:|---:|
|16K/.58|8,512 / 0.817초|3,904 / 0.920초|7,744 / 0.876초|**2.613초**|
|12K/.50|8,384 / 0.870초|**0 / 1.862초**|7,040 / 1.068초|**3.800초**|

12K에서는 같은 Q 입력인데 cached_tokens=0으로 바뀌었다. 캐시를 사용할 수 없어 다시 계산한 관측이며, 개별 블록의 제거 시점/원인까지 추적한 것은 아니다. D/P는 여전히 일부 계산을 재사용했다. 두 조건의 후속25요청에서도 각각 캐시 적중0인 요청이3개 있었으므로,16K에서 모든 요청의 캐시가 항상 유지됐다고 해석하지 않는다.

**캐시 미적중 때 비용은 재계산 지연이다. 이번에는 오류·토큰 잘림 없이 정상 완료했다.** 최종 같은3입력의 JSON 출력과 출력 토큰 수는 최초·워밍업 후·재반복·추가입력 후 모두 동일했다. 유한 캐시의 일반적인 동작은 [vLLM 공식 prefix caching 설명](https://docs.vllm.ai/en/latest/design/prefix_caching/)과 부합한다.

## 4. 출력·메모리·종료

74개 요청 모두 finish_reason=stop 및 JSON 파싱에 성공했다. 과거 저장 출력과 비교하면12K37/37,16K36/37이 JSON까지 같았다.16K의 나머지1개는 P의 “크림으로 선택했어요.”가 “크림으로 주문에 반영했어요.”로 바뀐 표현 차이였으며, 뒤의 “얇은면을 보통 양으로 담을까요?”는 같았다. 이는 광범위한 출력 결정성이나 전체 시나리오 품질을 보장하지 않는다.

이번 **LLM 단독** 장치 VRAM 표본 최고는16K20.00GiB,12K18.02GiB였다. NVML v1 장치 사용량이며 드라이버 예약을 포함한다.50ms 목표 샘플링, 최대 표본 간격은 각각96.9ms/66.6ms였다. STT/TTS 동시 상주의 기존28.97GiB/31.37GiB 기록을 대체하지 않는다.

두 시험 scope inactive, GPU compute 프로세스0,8000/18001 리스너 없음으로 종료를 확인했다. 원본 소스41개·어댑터 불변, 자원 guard/모니터 오류 없음이다.

## 5. 판정과 다음 적용 단위

**시작 시 대표 D/Q/P 요청을 실행하고 결과를 폐기한 다음 앱 준비 완료를 표시하는 방향은 타당하다.** 이번 대표3요청은 시작 준비에 약8초를 더 쓰고, 동일 첫 사용 입력의 전체 응답 대기를 약5.4초 줄였다. 서버 기본 기동은 이번16K65.02초/12K61.02초였으며 기기 상태에 따라 달라진다.

실제 구현에서는 운영과 같은 프롬프트·어댑터·문법을 쓰되 워밍업 결과를 실세션 history/state, TTS, ROS 명령으로 전달하지 않아야 한다. API 연결 가능과 SOOMAC 사용 준비 완료를 구분한다. 캐시 유지를 이유로 GPU 예약률을 올리는 변경은 이번에 하지 않았다.12K도 대표3요청 워밍업 이득이 확인됐으며, 이전 전체 스택 VRAM 결과를 함께 고려해야 한다.

실패 이력: 최초 시도는 측정용 interpreter의 pynvml 미설치로 모델 실행 전에 종료됐다. 다음 시도는 정상 `/health`의 빈 본문을 JSON으로 처리해 준비 확인에서 대기했다. 소유 시험 서버만 종료하고 HTTP200/빈 본문 처리를 고친 r2에서74회 측정을 완료했다. 패키지 설치는 하지 않았고 이전 실패 로그도 보존했다.

교차검수: 내부 코드·로그 외부 전송은 앞선 자동 승인 거절 이후 재시도하지 않았다. 내부 정보·측정값 없이 공개된 일반 워밍업/캐시 원리만 Codex CLI(gpt-6-sol/high)에 전달한 별도 검토는 **조건부 찬성**이었다. 로컬 구현이나 실측값의 독립 검수 완료를 뜻하지 않는다. 주담당자는 응답 원문·사용량·시간·SHA·종료 증거를 직접 대조했다.
