# LLM Node V5 Tool 동작과 후속 응답 정책

참고:

- [`llm_node_v5.py`](../src/soomac_irc/soomac_irc/llm_node_v5.py) — Tool 결과, 자유응답, VLM 응답을 최종 발화로 조립하고 ROS 실행을 연결하는 코드이다.
- [`agent_v5.py`](../src/soomac_irc/soomac_irc/agent_v5.py) — 8개 Tool을 실제 주문 상태에 적용하고 정책 응답과 다음 행동을 만드는 코드이다.
- [`call_model_v5.py`](../src/soomac_irc/soomac_irc/call_model_v5.py) — Tool 분류 프롬프트와 `respond` 자유응답 프롬프트가 있는 코드이다.
- [`order_v5.py`](../src/soomac_irc/soomac_irc/order_v5.py) — 메뉴 정본, restriction, 필수값, 물리 실행 계획을 검증하는 코드이다.
- [`test_response_followup_v5.py`](../src/soomac_irc/test/test_response_followup_v5.py) — 후속 응답 조립에 관한 현재 회귀 테스트이다.
- [`tool_turns_20260920_160441_957012.jsonl`](../src/soomac_irc/soomac_runtime_logs/tool_turns_20260920_160441_957012.jsonl) — 순서 오류와 자유응답 할루시네이션을 확인한 실제 로그이다.

→ **V5의 기준은 `정책 응답 + 자유응답`을 무조건 함께 생성하는 것이 아니라, 필요한 자연어 설명은 자유롭게 만들고 주문 상태·다음 행동·로봇 실행 여부는 Python만 확정하는 것이다.**

## 1. 이번 문제의 결론

원래 기대한 대화는 다음과 같다.

```text
사용자: 양파 적게
로봇: 양파를 적게로 반영했어요. 이대로 야채 담기를 진행할까요?
사용자: 진행해
Tool: confirm_section
로봇: 야채 담기를 시작할게요.
```

실제 문제 로그에서는 `양파 적게`가 주문에 반영됐을 뿐 `confirm_section`은 아직 호출되지 않았는데, 자유응답이 다음 section으로 넘어갔다고 말했다. 주문 상태와 로봇 실행 순서는 정상인데 **최종 발화만 실제 상태보다 앞서간 것**이다.

Cause: 정책 응답 뒤에 자유응답 모델이 주문 흐름까지 이어 쓰면서, 검증되지 않은 다음 단계와 실행 상태를 발화했다.

Effect: V5에서는 주문 흐름을 자유응답에서 분리하고, 현재 `order`와 `execution`으로 계산한 Python 후속 문장만 붙인다.

## 2. V4와 다르게 바뀐 파일

| 파일 | V5에서 바뀐 내용 | 현재 효과 |
|---|---|---|
| `order_v5.py` | V4를 별도 V5 파일로 복사했다. | V4를 건드리지 않고 V5만 실험할 수 있다. 현재 주문 규칙 자체는 V4와 같다. |
| `agent_v5.py` | `build_selection_next_step()`을 공개 함수로 만들고 restriction을 반영해 남은 선택지와 현재 선택량을 계산한다. | `버섯 싫어요` 뒤에는 양파만 묻고, `양파 적게` 뒤에는 야채 확정을 묻는다. |
| `agent_v5.py` | `set_order` 안에서만 후속 문장을 붙이던 로직을 제거했다. | 모든 응답 경로가 `llm_node_v5.py`의 같은 중앙 조립 규칙을 사용한다. |
| `call_model_v5.py` | 자유응답 역할을 설명·추천 이유·공감·잡담으로 제한하고 `selected`, `active_task`, `task_queue`를 사실 정보로 전달한다. | 모델이 상태를 참고할 수 있지만 다음 section 결정과 작업 시작·완료 선언은 맡지 않는다. |
| `llm_node_v5.py` | 정책·자유·VLM 응답 뒤에 검증된 다음 행동을 붙이고, 자유응답의 실행 주장과 자체 질문을 문장 단위로 제거한다. | 자연스러운 설명은 유지하면서 할루시네이션으로 만든 주문 흐름은 발행하지 않는다. |
| `test_response_followup_v5.py` | 문제 로그를 포함한 후속 응답 조립 테스트 8개를 추가했다. | 기존에 재현된 `버섯 싫어요 → 양파`, `양파 적게 → 확정 질문` 흐름을 고정한다. |

## 3. 현재 기본 실행 설정

`llm_node_v5.py` 상단의 현재 기본값은 다음과 같다.

```python
ENABLE_VLM = True
ENABLE_VLM_UI_IMAGES = True
ENABLE_TOOL_LORA = True
ENABLE_RUNTIME_LOG = True
```

따라서 VLM과 Tool LLM adapter는 운영체제 환경변수가 아니라 파일 상단의 `True`로 기본 활성화된다. 예외적으로 `ENABLE_DUMMY_VLM_PASS`만 `SOOMAC_DUMMY_VLM_PASS` 환경변수를 읽는다.

V5는 패키지 import를 사용하므로 내부 파일을 직접 실행하지 않고 패키지 루트에서 module로 실행해야 한다.

```bash
source /opt/ros/humble/setup.bash
cd /home/roma/IRC_SOOMAC3.0/src/soomac_irc
/home/roma/miniconda3/envs/gemma4_env/bin/python -m soomac_irc.llm_node_v5
```

Cause: `python /.../soomac_irc/llm_node_v5.py`로 직접 실행하면 Python이 상위 패키지 경로를 잡지 못해 `soomac_irc.agent_v5` import가 실패한다.

Effect: `-m soomac_irc.llm_node_v5`로 실행하면 V5 파일끼리의 package import가 정상적으로 연결된다.

## 4. 최종 응답 조립 규칙

```text
사용자 발화
  → Tool adapter가 8개 Tool 중 하나를 선택
  → Python transaction이 주문 변경 가능 여부를 검증
  → 정책 응답이 있으면 정책 응답 사용
  → respond이면 설명·공감용 자유응답 사용
  → describe_scene이면 VLM의 장면 설명 사용
  → 실제 order·execution에서 Python 다음 행동 계산
  → 중복 질문과 검증되지 않은 실행 주장을 제거한 뒤 발행
```

정책 응답 자체가 질문하는 경우, 작업이 바로 시작되는 경우, section이 자동으로 넘어가는 경우에는 후속 문장을 중복해서 붙이지 않는다. `respond`의 자유응답은 질문 문장과 `반영했`, `확정했`, `담기를 시작`, `다음 단계`, `진행할게` 같은 운영 문장을 제거한 뒤 안전한 설명만 유지한다.

(내가 의역해보자면 자유응답은 손님과 자연스럽게 이야기하는 역할이고, 주문표 수정과 로봇 진행 안내는 실제 주문표를 들고 있는 Python 직원의 역할이다.)

## 5. Tool 1 — `set_order`

### 역할

`set_order`는 사용자가 메뉴값이나 restriction을 **변경만** 요청했을 때 사용한다. 변경은 검증한 뒤 반영하지만 이 Tool만으로 로봇 작업을 시작하지 않는다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 정상 변경 | `양파 적게` | `요청한 주문 변경을 반영했어요. 현재 야채 선택은 양파 적게예요. 버섯도 추가하거나, 이대로 담기를 진행할까요?` |
| restriction 뒤 남은 재료 안내 | `버섯이 싫어요` | `요청한 식이 조건을 반영했어요. 야채로는 양파가 남아 있어요. 어느 정도 양으로 넣을까요?` |
| 같은 값 반복 | 이미 양파 적게인 상태에서 `양파 적게` | `이미 같은 내용으로 선택되어 있어요.` 뒤에 현재 상태에서 가능한 다음 행동을 붙인다. |
| 잘못된 값 | `양파 초대형으로` | 메뉴에 없거나 형식이 맞지 않는 요청은 반영하지 않고 현재 가능한 다음 행동을 안내한다. |
| 이미 실행 중·완료된 재료 변경 | 양파 담기 시작 뒤 `양파 많이` | `이미 담기 시작한 항목은 변경할 수 없어요.` |
| 지나간 section 변경 | 육류 단계에서 `면을 넓은면으로` | `이미 작업이 끝난 단계의 항목은 변경할 수 없어요.` |
| 안전 restriction 충돌 | 담기 전 선택한 버섯에 `버섯 알레르기` | restriction을 반영하고 아직 담지 않은 버섯은 주문에서 제거한다. |
| 이미 담은 재료와 안전 restriction 충돌 | 버섯 담기 시작 뒤 `버섯 알레르기` | 버섯을 되돌릴 수 없다고 경고하고 이후 가능한 선택만 안내한다. |

### V4와 달라진 점

V4는 `set_order`에만 후속 안내가 붙었고 restriction으로 제외된 재료도 다시 제안할 수 있었다. V5는 남은 재료를 restriction으로 거르고, 현재 선택량을 포함한 확정 질문을 중앙에서 만든다.

## 6. Tool 2 — `set_order_and_confirm`

### 역할

`set_order_and_confirm`은 사용자가 **변경과 현재 section의 즉시 진행을 한 문장에서 모두 명확히 요청**했을 때 사용한다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 변경과 진행 모두 유효 | 면 필수값이 갖춰질 수 있는 상태에서 `넓은면 보통으로 하고 진행해` | 변경을 반영하고 현재 section의 작업 queue를 만든 뒤 `면 담기를 시작할게요.`를 발행한다. |
| 필수값 누락 | 소스가 없는 상태에서 `얇은면으로 하고 진행해` | `아직 소스 선택이 필요해서 작업을 시작하지 않았어요.` 뒤에 누락 항목을 안내한다. |
| 변경 일부 차단 | 이미 시작한 양파를 바꾸면서 `많이로 바꾸고 진행해` | 변경을 차단하고 작업도 시작하지 않는다. |
| restriction 충돌 | `버섯 알레르기니까 버섯 많이 넣고 진행해` | 충돌값은 제거하고 `일부 요청을 반영할 수 없어 아직 작업을 시작하지 않았어요.`라고 안내한다. |
| 이미 같은 값으로 완성 | 필수값이 모두 있는 상태에서 같은 값을 말하며 `그대로 진행해` | 새 변경이 없어도 현재 section이 완성됐으면 확정 검사를 통과해 작업을 시작할 수 있다. |

Cause: 변경 일부가 실패했는데 나머지만으로 로봇을 시작하면 사용자가 의도한 주문과 달라질 수 있다.

Effect: `invalid`, 실행 중, 지난 section, restriction 충돌이 하나라도 있으면 즉시 시작을 막는다.

## 7. Tool 3 — `refuse_section`

### 역할

`refuse_section`은 현재 section의 재료 **전체를 같은 이유로 제외**할 때 사용한다. 현재 구현은 야채, 육류, 추가 재료 section에서 동작한다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 취향상 전체 거절 | 야채 단계에서 `야채는 전부 싫어요` | `현재 단계 재료를 모두 제외하고 다음 단계로 넘어갈까요?`라고 한 번 더 확인한다. |
| 취향상 거절 확인 | 위 질문 뒤 `응` | 현재 section을 skip하고 다음 section으로 이동한다. |
| 취향상 거절 거부 | 위 질문 뒤 `아니` | 현재 section에서 계속 고르도록 다시 안내한다. 단, 아래의 알려진 상태 버그가 있다. |
| 안전·식단 이유 전체 제외 | `야채를 먹을 수 없어요` 또는 명시적 식단 제한 | 전체 restriction을 적용하고 재확인 없이 현재 section을 skip한다. |
| 일부 재료만 거절 | `버섯만 싫어요` | 전체 section 거절로 인정하지 않는다. 이 발화는 정상적으로는 `set_order` restriction으로 분류되어야 한다. |
| items가 현재 section 전체와 불일치 | 야채 단계인데 소시지가 섞인 전체 거절 Tool | 요청을 정확히 이해하지 못했다고 안내하며 skip하지 않는다. |

### 현재 확인된 문제

**취향(`dislike`) 전체 거절은 재확인 전에 restriction과 기존 선택 제거가 먼저 적용된다.** 사용자가 재확인에 `아니`라고 답해도 section은 유지되지만 먼저 적용된 restriction이 원복되지 않는다.

필요한 수정은 restriction과 주문 제거를 `pending proposal`로 보관하고, 사용자가 `응`이라고 했을 때만 commit하는 것이다. `아니`이면 원래 주문을 그대로 유지해야 한다.

## 8. Tool 4 — `recommend_order`

### 역할

`recommend_order`는 사용자가 추천이나 자동 선택을 요청했을 때 추천안을 만들며, **추천안을 주문에 즉시 반영하지 않는다.**

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 추천 범위 불명확 | `추천해줘` | `현재 단계만 추천할까요, 아니면 남은 주문 전체를 추천할까요?` |
| 현재 단계 추천 | 야채 단계에서 `지금 단계만 담백하게 추천해줘` | restriction과 기존 선택을 제외한 추천안을 보여주고 `이대로 할까요?`라고 묻는다. |
| 남은 주문 추천 | `나머지는 알아서 골라줘` | 현재와 미래의 아직 선택하지 않은 section만 추천안에 넣는다. |
| 특정 section 추천 | `육류랑 추가 재료 추천해줘` | 지정한 section 안에서만 제안한다. |
| 추천과 restriction 동시 요청 | `소시지는 못 먹고 나머지는 추천해줘` | restriction을 먼저 반영하고 충돌하지 않는 추천안만 만든다. |
| 추천 범위가 이미 선택됨 | 선택이 끝난 section을 다시 추천 요청 | 이미 모두 선택됐다고 안내한다. |
| 제한 때문에 추천 불가 | 허용되는 재료가 하나도 없는 범위 추천 | 제한 조건에서 추천할 재료가 없다고 안내한다. |

추천 확인에서 사용자가 `진행해`라고 말하면 `confirm_section`이 저장된 추천안을 **현재 restriction으로 다시 검증**한 뒤 주문에 반영한다. 오래된 추천안을 그대로 믿지 않는 구조이다.

### 추가 개선 후보

현재 추천 메뉴값은 Tool adapter가 생성하고 Python은 범위·정본·restriction을 검증한다. 추천 결과 자체까지 완전히 재현 가능하게 만들려면 향후 Python 추천 규칙으로 옮길 수 있다. 이는 현재 할루시네이션 문제를 해결하는 데 필수인 변경은 아니다.

## 9. Tool 5 — `confirm_section`

### 역할

`confirm_section`은 사용자가 현재 선택이나 직전 추천안을 명확히 확정했을 때 사용한다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 현재 section 정상 확정 | `이대로 진행해` | 필수값을 다시 확인하고 작업 queue가 만들어지면 `야채 담기를 시작할게요.`라고 발행한다. |
| 필수값 누락 | 면 종류만 고른 상태에서 `진행해` | `아직 소스, 어느 정도 양을 드실지 선택이 필요해서 작업을 시작하지 않았어요.` |
| 추천안 확정 | 추천 질문 뒤 `좋아, 진행해` | 저장한 추천안을 재검증해 반영하고 해당 section 작업을 시작한다. |
| 추천안이 새 restriction과 충돌 | 추천 뒤 제한 조건이 바뀐 상태에서 확정 | 추천안을 반영하지 않고 충돌 사실을 안내한다. |
| 추가 재료 없이 extra 확정 | 추가 재료 단계에서 아무것도 고르지 않고 `그냥 진행해` | extra를 `empty_confirm`으로 skip하고 뚜껑 단계로 이동한다. |

### 현재 확인된 문제

현재 section의 모든 재료가 개별 restriction으로 제외되면 다음 행동 문장은 `section을 제외할지 말씀해 주세요`라고 말하지만 `awaiting_confirm`은 만들어지지 않는다. 사용자가 `응`이라고 답하면 정상적인 skip 확인으로 이어지지 않고 `confirm_section`의 필수값 검사에 막힐 수 있다.

필요한 수정은 사용 가능한 현재 재료가 0개가 된 순간 `refuse_section`과 같은 skip proposal을 만들고, 이유가 안전 제약이면 즉시 skip하며 취향이면 재확인을 받는 것이다.

## 10. Tool 6 — `cancel_order`

### 역할

현재 V5의 `cancel_order`는 이름과 달리 **전체 주문을 실제로 취소하지 않는다.** 모든 상태에서 주문과 물리 상태를 그대로 유지한다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| 빈 주문에서 취소 | `주문 취소할게` | `아직 선택된 주문이 없어요.` |
| 선택 후 취소 | `전체 주문 취소해줘` | `전체 주문 취소는 지원하지 않아요. 바꾸고 싶은 메뉴를 말씀해 주세요.` |
| 로봇 시작 후 취소 | `다 취소해` | `이미 재료를 담기 시작해서 전체 주문을 취소할 수 없어요. 아직 담지 않은 재료는 변경할 수 있어요.` |

`cancel_validation.blocked`는 항상 `True`, `needs_confirmation`은 항상 `False`이다. 그런데 `llm_node_v5.py`에는 과거 `awaiting_confirm.type == "cancel_order"` 처리 분기가 남아 있어 현재 경로에서는 도달하지 않는 stale code이다.

### 결정이 필요한 부분

전체 취소를 제품 기능으로 지원할 것이라면 로봇 시작 전 초기화 범위와 확인 절차를 새로 정의해야 한다. 계속 미지원할 것이라면 Tool 이름을 `request_cancel_order`처럼 바꾸거나 dead pending 분기를 제거해 계약을 명확히 해야 한다.

## 11. Tool 7 — `respond`

### 역할

`respond`는 주문 변경이 없는 질문·설명·공감·잡담과 의미가 불완전한 발화를 담당한다. **자유응답을 없애지 않고, 주문 흐름 결정만 분리한 경로**이다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 모델 초안 | 최종 응답 예시 |
|---|---|---|---|
| 메뉴 설명 | `토마토 소스 맛이 어때?` | `토마토 소스는 산뜻한 맛이에요.` | 설명을 유지하고 `다음으로 선택할 항목은 면 종류, 면 양예요.`를 Python이 붙인다. |
| 공감과 추천 이유 | `기분이 안 좋은데 뭐가 좋을까` | `산뜻한 맛이 편할 수 있어요. 어떤 면을 선택하시겠어요?` | 첫 설명은 유지하고 모델이 만든 질문은 제거한 뒤 실제 누락 항목 질문을 붙인다. |
| 거짓 실행 주장 | `또 뭐 골라야 돼?` | `육류 선택을 확정했어요. 담기를 시작할게요.` | 초안을 제거하고 `현재 육류 선택은 ... 이대로 육류 담기를 진행할까요?`만 발행한다. |
| 안전한 문장이 하나도 없음 | 불완전한 발화 | 모델 문장이 전부 질문 또는 운영 주장 | 모델 문장을 버리고 Python 다음 행동만 발행한다. |
| 주문 내역 질문 | `지금 뭐 골랐어?` | 현재 `order` 안의 사실만 설명 | 설명 뒤에 현재 section의 검증된 다음 행동을 붙인다. |

### 현재 확인된 한계

현재 안전 검사는 문장을 `.!?` 기준으로 나누고 특정 한국어 표현을 문자열로 찾는 휴리스틱(heuristic)이다. `이제 만들겠습니다`처럼 목록에 없는 동의어는 통과할 수 있고, 반대로 유용한 질문도 모두 제거한다.

다음 개선은 자유응답을 `explanation`, `operational_claim`, `question` 같은 구조화된 출력으로 제한하거나, 자유응답 자체는 설명 필드 하나만 생성하도록 schema를 두는 것이다.

## 12. Tool 8 — `describe_scene`

### 역할

`describe_scene`은 사용자가 실제 카메라 화면이나 로봇 앞 장면을 봐야 답할 수 있는 요청을 했을 때만 사용한다.

### 현재 처리하는 상황과 예시

| 상황 | 사용자 예시 | 현재 결과 예시 |
|---|---|---|
| VLM ON + 이미지 있음 | `지금 카메라에 뭐가 보여?` | 마지막 camera image에서 보이는 내용만 1~2문장으로 설명하고 Python 다음 행동을 붙인다. |
| VLM OFF | 같은 질문 | `현재 카메라 화면 확인 기능을 준비하고 있어요.` 뒤에 현재 주문 다음 행동을 붙인다. |
| 이미지 없음 | 같은 질문 | `아직 확인할 카메라 화면이 없어요.` 뒤에 현재 주문 다음 행동을 붙인다. |
| VLM이 빈 응답 반환 | 같은 질문 | `카메라 화면을 정확히 설명하지 못했어요.` 뒤에 현재 주문 다음 행동을 붙인다. |
| 주문 내역 질문 | `지금 뭐가 담겼어?` | 카메라 요청이 아니므로 `describe_scene`이 아니라 `respond`로 처리한다. |

### 현재 확인된 한계

마지막 camera image를 사용하지만 이미지의 timestamp가 현재 질문 기준으로 얼마나 오래됐는지 검사하지 않는다. 오래된 frame을 현재 장면처럼 설명할 가능성을 줄이려면 수신 시각을 저장하고 freshness 제한을 두어야 한다.

## 13. 8개 Tool 전체에서 공통으로 달라진 점

| 이전 V4 동작 | 현재 V5 동작 |
|---|---|
| `set_order`에만 다음 행동이 붙었다. | 정책·자유·VLM 경로가 같은 중앙 후속 안내를 사용한다. |
| 자유응답이 다음 section과 작업 시작을 말할 수 있었다. | 자유응답은 설명·공감에 한정하고 주문 흐름 문장은 제거한다. |

| 정책이 이미 질문하거나 작업이 시작돼도 추가 안내가 중복될 수 있었다. | 추천 확인·제외 확인·작업 시작·자동 section 이동에는 후속 질문을 덧붙이지 않는다. |

## 16. 데이터 추가 여부

**현재 확인된 문제를 고치는 데 학습 데이터 추가는 우선순위가 아니다.** Tool이 `set_order`로 올바르게 분류되고 주문값도 정상 반영됐는데, 그 뒤의 자유응답이 순서를 앞질러 말한 것이 원인이기 때문이다.

필요한 것은 학습 데이터보다 다음 두 종류의 테스트 데이터이다.

- 실제 실패 로그를 고정한 응답 회귀 사례
- 8개 Tool마다 `order`, `execution`, `recommendation`, `awaiting_confirm` 전후 상태를 검사하는 상태 전이 사례

같은 의도의 사용자 발화가 반복해서 잘못된 Tool로 분류되는 로그가 쌓일 때만 Tool 분류 학습 데이터를 추가하는 것이 맞다.

## 용어 정리

- **정책 응답(policy reply)**: Python이 검증된 transaction만 사용해 만드는 주문 변경·차단·확인 문장이다.
- **자유응답(free reply)**: `respond`에서 질문 설명, 추천 이유, 공감, 잡담을 자연어로 생성하는 모델 출력이다.
- **중앙 후처리(central post-processing)**: 정책·자유·VLM 응답을 발행하기 직전에 실제 상태와 대조하고 다음 행동을 붙이는 공통 조립 단계이다.
- **상태 전이(state transition)**: 한 Tool 처리 전후로 `order`, `execution`, `recommendation` 같은 상태가 어떻게 달라지는지를 뜻한다.
- **restriction**: 알레르기, 섭취 불가, 식단 규칙, 비선호 때문에 특정 재료를 제한하는 주문 조건이다.
- **proposal**: 사용자 확인 전이라 실제 주문에는 아직 반영하지 않은 추천안 또는 section 제외안이다.
- **stale code**: 현재 실행 경로에서는 쓰이지 않지만 이전 설계에서 남아 있는 코드이다.
- **frame freshness**: 카메라 이미지가 현재 장면을 설명하기에 충분히 최근 것인지 판단하는 기준이다.

## 17. 기록 시점의 검증 조건

이 문서는 2026-09-20 현재 V5 소스와 실제 로그를 읽어 작성했다. 문서 작성 중에는 GPU 상태 조회, 모델 로딩, LLM/VLM 추론, ROS node 실행을 하지 않았다.

Effect: 소스와 로그에는 쓰기 작업을 하지 않았고 이 Markdown 문서만 추가했다.
