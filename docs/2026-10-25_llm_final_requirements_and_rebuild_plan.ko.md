## 목표

**사용자는 대본을 외우지 않고 자연스럽게 말한다. 세 모델은 뜻과 맥락을 이해하고, Python은 확정된 구조와 실제 로봇 상태를 검증한다.** 특정 발화 하나가 성공하도록 키워드를 늘리는 것이 목표가 아니다.

최신 요구는 **이전 대화와 state를 활용하는 자연스러운 직원형 권유**이다. “취향 저장했어요”로 매번 끝내지 않고, 처음 말한 매운맛 선호를 나중에 토핑 단계의 페퍼론치노 제안 이유로 연결한다. 단, Assistant의 과거 오답을 사용자 사실로 승격하지 않으며 기존 선택·수량·pending과 질문을 일치시킨다. 대화 전체 삭제·한 턴 회귀·새 고정 권유문 증설로 해결하지 않는다.

사용자가 원하는 기본 흐름은 다음과 같다. 이는 평가용 예시이며 문장·메뉴·취향·제약의 고정 순서를 강제하지 않는다.

| 시점 | 사용자 예시 | 원하는 판단·상태 | 원하는 말과 실행 경계 |
|---|---|---|---|
| 시작 | 매운 걸 잘 못 먹어. 기분도 안 좋은데 뭐 먹을까? | 매운맛 회피와 추천 요청을 함께 인식한다. 현재부터 남은 단계의 조합을 제안할 수 있다. | “매운맛을 피하고 싶으시니 크림 소스를 추천드려요…”처럼 이유를 설명한다. 추천 자체로 주문·실행을 확정하지 않는다. |
| 소스 선택 | 크림으로 할게. | 크림을 주문에 저장한다. 실제 소스 투입 시점은 바꾸지 않는다. | “크림으로 선택했어요.” 소스를 담았다고 하지 않는다. |
| 면 선택 | 좋아, 얇은 면 조금만. | 얇은면·low를 저장한다. 과거 추천의 normal이 덮지 않는다. | 현재 면 실행 확인 또는 명시적 즉시 실행 의도에 따른 실행으로 이어진다. |
| 야채 | 버섯 조금, 양파 많이 담아줘. → 아 그냥 둘 다 조금만. | 버섯 low·양파 high에서 둘 다 low로 변경한다. pending 대상·수량도 최신 상태와 맞춘다. | “양파와 버섯을 모두 조금씩 선택했어요. 이대로 담을까요?” 과거 high를 말하거나 먼저 담지 않는다. |
| 육류 | 게살 알레르기가 있어. 고기는 많이 먹고 싶은데 추천해줘. | 강한 제한과 추천 의도를 함께 처리한다. 게살을 제외한 허용 후보를 제안한다. | “게살은 제외하고 소시지를 많이 넣는 구성을 추천드려요.” 선택 확인과 실행 확인의 질문을 혼동하지 않는다. |
| 지시어 | 나머지만 / 그거 빼고 담아줘. | 직전 후보·현재 pending·최신 주문을 보고 대상이 유일하면 해석한다. 정말 모호하면 한 번 명확히 묻는다. | 같은 항목을 끝없이 다시 묻지 않는다. 주문 선택과 즉시 실행 구분은 유지한다. |
| 토핑 | 매운 거 못 먹어. / 앞서 저장된 같은 선호 | 현재까지 유지된 매운맛 회피에 맞춰 페퍼론치노를 제외한 치즈 제안이 가능하다. | “매운 걸 잘 못 드신다고 하셨으니 페퍼론치노 대신 치즈로 할까요?” 선호만으로 치즈 주문·실행을 자동 생성하지 않는다. |
| 단계 도착 | 새 사용자 발화 없이 meat/extra 진입 | 선호-only, 미리 확정한 주문, 미확정 추천을 구분한다. | 선호-only는 선택 질문, 확정 주문은 최신 수량으로 실행 확인, 미확정 추천은 확정 사실처럼 말하지 않는다. |
| 완료 | 실행 시작·작업 종료·VLM 결과·최종 완료 | 각 이벤트의 증거 수준을 구분한다. | 시작을 완료로, policy_success를 독립적인 VLM PASS로 말하지 않는다. |

크림·소시지·치즈는 위 조건의 예시이지 모든 사용자에게 강제할 답이 아니다. 유제품 제한이 추가되면 크림·치즈 추천을 그대로 유지할 수 없다. 기분에 맞는 추천은 음식 선택 제안이지 치료 효과 보장이 아니다.

**추천 범위를 지정하지 않은 일반적인 “뭐 먹을까 / 기분에 맞춰 추천해줘”는 현재부터 남은 선택 단계 전체의 조합을 다루는 것을 기본 목표로 삼는다.** 현재 면 양 한 항목만 바꾸고 전체 요청을 처리했다고 끝내지 않는다. 반대로 “이번 육류만 / 면 양만”처럼 좁힌 요청은 그 범위만 처리한다. 전체 코스는 모든 필드를 새로 덮어쓰는 명령이 아니다. 이미 확정된 선택은 유지하고, 제한 때문에 제외하거나 선택적으로 생략한 단계도 구분한다. proposal은 실제 변경 후보만 담고 설명은 유지 항목과 변경 항목을 구분할 수 있어야 한다.

**“해당 단계에서 재확인”은 사용자 선택 단계에 적용한다.** 기존 `lid` 및 마지막 `sauce` 자동 진행 계약은 보존한다. 소스에도 새 실행 확인을 끼워 넣는 변경은 이번 목표로 추정하지 않으며 별도 요구 확인·제어 검증 없이는 하지 않는다. 소스의 사전 선택과 실제 마지막 투입을 구분하는 것은 계속 필수이다.

## 2. 설계 원칙

### 최신 지침 — 고정 안내와 필드 제한

| 구분 | 유지·복원 기준 | 주의점 |
|---|---|---|
| 실행 시작 / 추천 불가 안내 | 10월 11일에도 있던 안전한 고정 경로를 기준으로 보존한다. | 발행 실패를 성공처럼 말하지 않아야 하며, 추천 불가 안내도 제한된 재료를 권하지 않아야 한다. |
| 실행 확인 거절 / 강한 제한 철회 거절 / 추천 제안 / 추천 수락 | 10월 20일 이후 늘어난 고정 발화는 모델 응답 경로로 되돌리는 설계 대상이다. | pending·policy·검증 자체를 없애는 것이 아니라 문장 생성 소유권을 분리한다. |

옛 8개 필드는 `route`, `order`, `restrictions`, `preferences`, `recommendation`, `commit`, `confirmation`, `clarify`이다. **추가 필드 수를 줄이는 것 자체가 목적은 아니다.** 현재 생략 기능을 보존하면서 기존 구조로 표현 가능한지 먼저 검증하고, 모호성을 새 키워드 규칙으로 감추지 않는다. 대안이 기존 요구를 만족하지 못하면 필드 계약 결정부터 사용자에게 보고한다.

원인: 응답 환각을 막는 정책과 자연어 우선 정책이 자료·코드에 섞여 있다.
효과: 안전 판단은 유지하고 표현을 모델에 돌리는 변경을 분리할 수 있다.

### LLM이 판단할 내용

| Agent | 책임 | 하지 않을 일 |
|---|---|---|
| Decision | 복합 의도, 주문·선호·제약의 추가/변경/철회, 멀티턴 지시어, 추천과 실행 확인의 수락/거절, 즉시 실행, 모호성 판단 | 현재 상태에 없는 대상·알레르기·동의를 지어내지 않는다. |
| Recommendation | 원문과 최신 상태를 함께 보고 허용 범위에서 필요한 폭의 추천·수정을 한다. 이유는 사용자 요구와 연결한다. | 선호를 확정 주문으로 승격하지 않는다. 전체 추천 요청을 항상 면 양 하나로 축소하지 않는다. |
| Response | 최신 확정 상태·적용 결과·pending·물리 증거에 맞춰 자연스럽게 설명하고 다음 질문을 한다. | 새 주문·ROS 명령을 만들거나 실제와 다른 성공·완료를 말하지 않는다. |

### Python이 담당할 내용

1. JSON 구조와 지원 메뉴·수량의 유효성을 검사한다.
2. 과거/진행 중 물리 작업, 강한 섭취 제한 및 충돌을 검사한다.
3. pending 종류·대상·section·최신 주문과 실행 권한을 관리한다.
4. ROS 계획의 중복 방지와 실제 실행·VLM·완료 이벤트를 관리한다.
5. 모델 실패 시 사실에 근거한 안전한 fallback을 제공한다.

사용자 원문의 뜻을 Python 정규식으로 다시 추론하지 않는다. 구조화된 메뉴와 검증된 성분 관계를 통한 안전 검사와, “바로/그거”를 찾아 의도를 재판정하는 코드는 다른 것이다.

### 전체 구조 검수에서 추가된 설계 쟁점

| 쟁점 | 요구되는 동작과 경계 |
|---|---|
| 현재 실행+미래 추천 | 둘 다 명확한 요청이면 조기 반환으로 한쪽을 조용히 버리지 않는다. 현재 실행 권한과 미래 추천 pending을 혼동하지 않는다. |
| 실행 거절+미래 주문 변경 | 거절은 실행을 막되, 실제로 반영한 미래 변경은 응답에서도 설명한다. |
| 제한의 자연어 표현 | 이미 구조화된 강한 제한을 취향으로 약화하지 않는다. 문자열 특례만 삭제해 명확한 제한을 unsupported로 버리는 것도 해결이 아니다. 모델의 메뉴 grounding과 validator의 안전 계약을 함께 검증한다. |
| 여러 제한 철회/확인 경합 | 강한 제한 확인은 유지한다. 한 요청만 처리했으면 남은 요청을 처리한 것처럼 말하지 않고 다음 확인 또는 재요청을 명확히 안내한다. 새 pending 저장소 도입을 미리 결정하지 않는다. |
| 코스 일부 수락 | 전체 수락·소스만 선택·나머지 추천 유지의 차이를 정한다. 채택하지 않은 제안을 확정 주문으로 몰래 승격하거나 history 밖에서 복원하지 않는다. |

일부 행동은 명확하고 나머지만 모호한 복합 발화도 평가한다. 전체 clarify 때문에 명확한 요청까지 항상 버리거나, 반대로 불명확한 부분을 추측해 실행하지 않는다. 구현 가능한 처리 범위와 보류 범위를 응답으로 분명히 설명해야 한다.

## 3. 즉시 실행 시나리오 검증

| 상태와 발화 | 기대 결과 |
|---|---|
| 현재 meat, 새 주문 “소시지 많이 넣고 바로 담아줘” | high와 명시적 실행 의도를 함께 반영한다. 검증 통과 시 재확인 없이 현재 단계 첫 plan 1건이다. |
| 유효한 execution pending, “바로 해줘 / 응 / 그렇게 해” | 최신 대상·수량·section을 확인해 수락하고 첫 plan 1건이다. 특정 즉시성 단어는 필수 조건이 아니다. |
| 일반 주문 “소시지 많이 넣어줘” | 주문을 반영하고 필요한 실행 확인을 기다린다. 임의 plan은 0건이다. |
| recommendation pending, “좋아 그걸로” | 추천 선택 수락과 실행 승인을 구분한다. 질문이 선택 확인이었다면 수락만으로 자동 물리 실행하지 않는다. |
| 빈 선택·pending 없음, “바로 해줘” | 실행할 대상을 추측하지 않는다. 무대상 재료 실행은 0건이다. |
| 빈 optional 단계, 명시적인 “이번 단계는 빼고 다음으로” | 생략 의도를 반영해 단계가 진행돼야 한다. 필수 면·lid·sauce를 임의 생략하지 않는다. |
| 기존 pending 거절+대체+즉시 실행 | 오래된 후보를 실행하지 않고 최신 교체 주문만 검증한다. |
| 미래 meat 주문을 noodle에서 요청 | 미래 선택은 보관할 수 있으나 물리 순서는 건너뛰지 않는다. |
| “바로 하지는 마 / ‘바로 해줘’가 무슨 뜻이야?” | 부정·인용을 실행 승인으로 오인하지 않는다. |
| 오래된 Assistant 질문만 남음 / stale pending / busy / 중복 입력 | 과거 동의를 복원하거나 중복 실행하지 않는다. |

`바로 시작해`, `바로 진행해`, `바로 담아줘`, `지금 해줘`, `즉시 진행해`, `응 그걸로 해`를 상태가 다른 최소 대조쌍으로 검사한다. 첫 plan 1건은 **전체 재료의 일괄 실행·완료를 뜻하지 않는다.** 이후 작업은 기존 완료·VLM 순차 게이트에 따른다.

## 4. 선호·제약·주문 철회 검증

| 사용자 의미 | 보존해야 할 구분 |
|---|---|
| 소시지를 좋아한다 | 선호이다. 수량 있는 주문이나 실행 동의가 아니다. |
| 소시지 좋아한다던 말 취소 | 해당 선호만 철회한다. 별도 확정 주문은 자동 취소하지 않는다. |
| 오늘은 소시지를 안 먹겠다 | 이번 주문 선택과 장기 선호 철회를 문맥으로 구분한다. |
| 소시지 빼줘 / 조금으로 | 미실행 주문 변경이다. `none`은 patch 취소 명령이며 persisted order의 수량으로 남기지 않는다. |
| 이미 미선택인 항목을 다시 빼달라 | 대상 해석 성공·변화 없음·대상 불명확을 구분한다. “이미 선택되어 있지 않아요”는 가능하고 같은 대상을 계속 되묻지 않는다. |
| 강한 제한을 없애달라 | 기존 별도 확인을 유지한다. 거절하면 제한을 보존한다. |
| 이미 담은 것을 빼달라 | 실제 제거할 수 없다는 정책을 설명한다. state만 지우거나 회수했다고 말하지 않는다. |
| Assistant가 과거에 취향을 추측했다 | 사용자 확정 사실로 승격하지 않는다. |
| 오래전 선호가 현재 state에 없다 | 근거 없이 복원하지 않는다. 현재 저장된 선호가 있으면 사실을 활용하되 과거 발화를 꾸며 인용하지 않는다. |

`current_update` 실행 거절과 `preselected` 거절의 주문 처리 차이는 기존 정책을 정확히 테스트한다. 겉보기 patch에 `none`이 없다는 이유만으로 데이터 오류라 단정하지 않는다. pending 해소에서 제거되는 항목까지 추적한다.

“이번에는 아직 담지 말고 선택은 유지해”와 “그 후보 자체가 싫어”도 정상 대조로 구분한다. 둘 다 단순 reject로만 표현해 source별 기존 동작에 맡기면 사용자 의도와 어긋날 수 있다. 이미 있는 주문 patch/confirmation으로 표현 가능한지 먼저 확인한다.

## 5. 맥락형 Response 설계

### 사용자 발화와 단계 이벤트

사용자 발화에 답하는 경로와 로봇 단계 전환에 답하는 경로는 **같은 Response Agent를 재사용하되 입력 발생 원인을 구분**해야 한다. 새 사용자 발화가 없는 이벤트를 가짜 user message로 대화 history에 넣지 않는다.

| 입력의 의미 | 필요한 사실 | 원하는 응답 |
|---|---|---|
| 사용자 주문/질문 | 현재 원문, 최근 대화, 확정 주문, 선호·제약, 적용/거절 결과, pending, 로봇 상태 | 질문에 답하고 실제 반영분을 설명한다. 과거 양을 현재 값처럼 말하지 않는다. |
| 관련 단계 진입·선호만 있음 | 해당 단계, 유효 선호, 선택 가능한 재료, 주문 미확정 사실 | “소시지를 좋아하신다고 하셨는데 이번에 넣으실까요?” |
| 관련 단계 진입·이미 주문 확정 | 최신 주문량, 해당 execution pending | “소시지를 조금 선택해 두셨어요. 이대로 담을까요?” 재추천·중복 주문을 받지 않는다. |
| 무관하거나 철회된 선호 | 최신 정본과 현재 단계 | 무관한 과거 이야기는 생략한다. |
| 실행·VLM·실패·완료 이벤트 | 실제 확인된 event 사실과 증거 수준 | 시작/검증 대기/재시도/최종 완료를 구별한다. |

위 표는 **목표 계약**이며 아직 구현된 신규 API라고 주장하지 않는다. `trigger` 같은 turn-local 입력만 필요한지 검토하고 persistent state 필드를 우선 늘리지 않는다. 이벤트 응답에는 물리 제어권을 주지 않으며, 지연·중복·stale 이벤트가 재실행·중복 TTS를 만들면 안 된다.

무변경 요청은 검증된 요청 대상·연산·처리 결과를 턴 단위로 전달할 수 있는지 검토한다. 실제 변경 diff와 “이미 미선택이어서 변경 없음”은 구분한다. 원문이나 order에서 뜻을 다시 추측하게 하는 것과 Decision의 해석 성공을 전달하는 것은 다르다. 과거 사용자 원문이 사라졌다면 정확한 인용을 꾸미지 말고 “매운맛을 피하는 취향을 반영해”처럼 저장된 사실 수준으로 설명한다.

모델 호출 실패 턴 다음에 “그거로 해”가 들어오는 경우도 검사한다. 실패 턴을 정상 적용된 주문으로 저장하면 안 되지만, 실제 주고받은 발화가 통째로 history에서 사라져 참조가 끊기는 문제도 구분한다. 최근 20메시지는 사용자·응답 10쌍과 같지 않으며 단계 이벤트 안내도 포함된다. 필요한 참조가 실제 입력에 있는지 확인한 뒤 의미 사용 실패와 입력 누락을 나눈다.

### 자연스러움과 사실성

1. 이유를 말한다: “게살 알레르기를 반영해 게살은 제외하고 소시지를 추천드려요.”
2. 질문의 의미를 맞춘다: “추천 구성을 선택할까요?”와 “지금 담을까요?”는 다른 승인이다.
3. 사실을 구분한다: 주문에 추가, 담기 시작, 담기 검증, 완료는 같은 상태가 아니다.
4. 말투를 자연스럽게 한다: 조사·받침·수량 합성·존댓말을 확인하며 사용자 반말을 그대로 따라 할 필요는 없다.
5. 실패 시 사실만 안내한다: 무한 재질문·가짜 대상·금지 재료 권유 대신 검증된 상태로 fallback한다.

짧게 답하라는 프롬프트 자체가 고정 멘트 문제의 원인은 아니다. 실제로 Response가 호출되지 않거나 Python이 추천 근거를 치환하는 경로를 별도로 고쳐야 한다. 의미 검사기를 또 다른 키워드 의도 판정기로 만들지도 않는다.

## 6. STT / TTS 정책

**로봇 실행 중 STT 차단은 유지한다.** 상태 질문은 주문을 받는 대화 구간에서 처리한다. TTS 재수음·잡음으로 주문이 바뀌거나 pending이 승인되면 안 된다.

잘못된 수음은 다음처럼 구분한다. 문맥상 대상이 충분히 명확한 표기 변형은 모델이 해석할 수 있어야 한다. 대상·극성·알레르기 여부가 위험하게 모호하면 명확화한다. 저장 텍스트만 있고 원음이 없으면 “STT가 틀렸다”는 원인은 확정하지 않는다. “먹을 줄 몰라”를 자동으로 강한 섭취 제한으로 만드는 target을 그대로 복사하지 않는다.

## 7. 데이터·모델·평가기 감사

### 데이터 전면 폐기와 새 후보 구축을 구분한다

**원본은 보존하고, 로그 기반 episode 후보를 새로 만들 수 있다. 기존 성공 데이터까지 전부 폐기한다는 결론은 아직 없다.** 현재 모델 계보, 원격 tar 학습 자료, 로컬 신규 후보는 각각 다르다. 미배포 데이터 결함을 현재 운영 adapter 퇴보의 직접 원인으로 소급하지 않는다.

현재 설정은 Decision v3.4 epoch4 / Recommendation v2 epoch4 / Response v1.3 epoch3이다. 실제 프로세스가 로드한 가중치 해시가 로그에 없으면 설정만으로 동일성을 증명하지 못한다. `all_gates_pass` 같은 과거 설정 표시는 이번 검수 통과 증거가 아니다.

10월 11일도 무결한 정답 baseline은 아니다. `session_20261011_165022_325333_pid68448` T2는 “매운 걸 별로 안 좋아한다”인데 Decision raw가 `preferences=[{value:매콤하게,action:add}]`를 출력했다. 내부 `decision_final`에서는 같은 값이 `preference_options`에 있다. 외부·내부 필드를 혼동해 “Decision은 비었는데 저장 코드가 생성했다”고 판정하면 원인을 잘못 고치게 된다. 옛 성공 사례를 보존하되 옛 실패 출력은 새 학습 정답으로 복사하지 않는다.

### 생성 순서

1. 실제 세션을 동결하고 source SHA·턴·발화·실제 출력·state·ROS 이벤트를 연결한다. 성공 사례도 함께 보존한다.
2. 사용자 요구에서 **독립적인 기대 상태와 금지 행동**을 먼저 작성한다. 실패한 모델 출력이나 현재 Runtime 동작을 그대로 gold로 삼지 않는다.
3. 기대 Decision/Recommendation과 상태 전이를 Runtime에 재생해 불일치를 찾는다. Runtime과 일치했다는 이유만으로 정답을 확정하지 않는다.
4. 같은 의미의 자연어 변형과 다른 의미의 최소 대조쌍을 만든다. Response target은 검증한 결과 상태에 맞춰 작성한다.
5. 세 Agent 입력을 실제 serializer·prompt·schema로 구성하고 검증한다. 승인 전 원본·release·remote payload를 덮어쓰지 않는다.

대화 전체(episode)가 1차 단위이고, 각 Agent의 학습 행은 그 대화에서 파생한다. 같은 episode·템플릿·history 조각을 train/test 양쪽에 섞지 않는다. 원문 실패 대화를 holdout으로 쓰면 train에는 그 원문이나 거의 같은 변형을 넣지 않는다. 오류 유형을 참고하는 것과 평가 정답을 외우게 하는 것은 다르다.

### 생성·평가 축

| 축 | 정상 사례와 반드시 구분할 반례 |
|---|---|
| 조사·받침·합성 문장 | 자연스러운 “양파와 버섯을 조금씩” / “많이이”, 조사 중첩 등 |
| 높임말·반말 | 반말/존댓말 사용자 입력 모두 의미 동일, 응답은 자연스럽고 정중 |
| 특정 단어 의존 | 명사 명시 / 지시어 / 동의어 / 우회표현, 같은 단어가 있는 인용·부정 |
| 긍정·부정·정정 | 좋아한다 / 좋아하지 않는다 / 아까 말 취소 / 오늘만 안 먹는다 |
| 수음·중의성 | 복구 가능한 오타 / 위험하게 불명확한 대상·극성 / 단순 지식 질문 |
| 복합 의도 | 제한+선호+추천, 상태질문+주문, pending 거절+교체+즉시 실행 |
| 추천 범위 | 남은 코스 전체 / 미래 한 단계 / 현재 면 양만 / 전부 불가능 |
| 상태·대화 기억 | 최신 low vs 과거 high, 선호 vs 주문, assistant 추측 vs 사용자 사실 |
| 무변경·진행 | 이미 제거됨 / 실제 제거 / 대상 불명확 / 명시적 optional 생략 |
| 물리 근거 | plan 발행 / active / 결과 대기 / FAIL·UNCERTAIN / trusted PASS / 정책상 진행 |

### 평가기는 잘못 통과시키는 것과 정상 탈락을 함께 검사한다

| 층 | 채점 대상 |
|---|---|
| Agent 단독 | JSON 유효성, 의도·대상·극성·수량·추천 범위·응답 사실성 |
| 상태 전이 | order/preferences/restrictions/pending 전후, 철회 재부활, 미승인 실행 |
| 전체 Runtime | 모델 raw뿐 아니라 Graph 결과와 Node 최종 발행문, plan payload·중복, 다음 단계 진행 |
| 대화 전체 | 반복·불필요한 재확인·막힘·사용자 정정 후 회복, 완료까지 이어지는지 |
| 물리 증거 | ROS 발행과 controller 수신·동작·VLM·최종 완료의 구분, 미측정은 UNKNOWN |

오답 주입(mutation test): 미승인 “담기 시작할게요. 더 넣을까요?”, 제한과 충돌하는 크림 추천, 면만 완료됐는데 소스 완료 주장, 현재 low를 high로 설명, 없는 pending 생성은 탈락해야 한다. 정상 대조: 부사 “보통”, 올바른 부정문, “주문에 추가했어요”, 유효 pending의 “응”, preselected 교체에서 patch에 none이 없어도 결과가 올바른 경우는 잘못 탈락시키지 않는다.

추가 정상 대조로 빈 optional 단계의 합법적 skip에는 물리 재료 plan 1건을 강제하지 않는다. 소스 제한은 필드명 sauce가 아니라 실제 값 크림 등으로 검사한다. 보호된 수량을 한국어로 “적게 바꿀 수 없어요”라고 설명했을 때 내부 enum low가 없다는 이유로 탈락시키지 않는다.

8-field 복원에서 생략을 무조건 commit=true에 합치고 빈 commit을 모두 허용하면 무대상 실행 차단(S35)이 무너지고, 모두 막으면 명시적 생략(S08)이 막힌다. 이 차이를 표현할 계약과 정상 대조가 해결되기 전에는 schema 변경을 채택하지 않는다.

**항상 명확화만 하거나 아무것도 실행하지 않는 모델도 합격할 수 없다.** 안전 실패율과 별도로 적절한 실행·추천 폭·진행 성공률·불필요 질문을 채점한다. 자연어 의미 판정은 독립 검수·정상 대조·사람 판정을 결합하며, 몇 개 테스트 통과를 환각 0 보증으로 쓰지 않는다.

## 8. 재학습 정책

Agent별로 기존 checkpoint, prompt-only, 최소 Runtime 변경, 후보 데이터 보강 후 adapter를 같은 동결 평가에서 비교한다. 전면 재구축 후보와 검증 원본+보강 후보도 필요하면 비교할 수 있으나 **평가 전에 기존 데이터를 삭제하거나 새 모델을 채택하지 않는다.**

| Agent | 우선 확인 | 재학습을 판단할 조건 |
|---|---|---|
| Decision | 복합 의미 누락·극성·지시어·pending·생략과 실행 구분 | 동일 입력/정리된 계약에서도 반복 실패할 때 |
| Recommendation | 전체/미래/현재 요청 범위, 확정값 보존, 강한 제한, 다양한 이유 | 정상 scope·prompt로도 추천 범위와 조건 반영이 부족할 때 |
| Response | 호출 경로, state 입력, 이벤트 계약, 멱등 요청, 사실·조사·질문 의미 | 실제로 호출되는 올바른 입력에서도 상태 불일치·부자연스러움이 남을 때 |

신규 학습은 기존 adapter 위의 무조건 연속 누적이 아닌 독립 후보로 비교한다. 실제 학습·체크포인트 교체·원격 작업 변경은 별도 승인한다. 코드와 입력이 바뀌면 각 Agent 데이터·평가기 계약도 같은 버전으로 봉인해야 한다.

최종 오케스트레이션 책임은 조정자에게 있다. Astra 코드 구조 검수, Astra 최신 로그 검수, Claude 로봇 로그·데이터 검수를 근거별로 대조한다. 검수자의 의견 수로 정답을 정하지 않는다. 근거 없는 주장·잘못된 집계·미검수 범위를 최종 보고에서 정정한다.

현재 이 문서 작성은 **요구사항·계획 수립**이며 Runtime 복원, 데이터 후보 생성 완료, GPU 재추론, adapter 재학습 완료가 아니다. 원격 학습과 Docker를 취소·교체하지 않는다. 로봇 토픽·정본 이름·제어 순서는 변경하지 않는다.

### 2026-10-25 검수 취합 결과

**Astra(high) 구조·최신 로그 검수와 Claude 데이터·로그 보고 및 Git 이력 보완을 회수해 조정자 판정을 완료했다.** 70세션 688턴은 자료 인벤토리 규모이다. 최신 대표 실패는 원문으로 교차확인했고 이전 40세션은 구조 집계·분류와 대표 본문을 확인했다. 이를 688턴 또는 학습 후보 8,500행의 의미 전수 합격으로 부르지 않는다. 새 라이브 224707/225109 세션은 초판 동결 범위 밖이다.

확인된 핵심은 모델의 복합 의미/극성 오류, 실제 상태와 다른 Response, 고정 안내의 제한 재료 노출, 질문과 pending 대상 불일치, 잘못된 학습 target과 평가기 오채점이다. 현재 운영 adapter와 원격 학습 자료의 직접 인과는 미확정이다. **원본을 전부 폐기하는 대신 계약·평가기부터 교정하고 로그 기반 후보를 새로 검증한다.** 기존 160개 회귀 테스트는 통과했지만 새 요구 충족이나 수정 완료 증거는 아니다. 검수자 초판의 잘못된 수치·원인 분류·실물 실행 단정은 연결된 조정자 판정에서 정정했다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 정본 상태(canonical state) | 현재 확정된 주문·선호·제약·pending 및 로봇 상태이다. 과거 대화로 임의 덮어쓰지 않는다. |
| 멱등 요청(idempotent request) | 이미 빠진 재료를 다시 빼달라는 등 결과 상태는 같지만 의미는 이해된 요청이다. |
| 입력 계약(input contract) | 모델에게 실제 전달되는 키·값·발생 원인과 각 필드 의미의 약속이다. |
| 대화 에피소드(episode) | 여러 턴과 각 턴의 기대 상태·응답·이벤트를 함께 가진 검증 단위이다. |
| 독립 정답 기준(oracle) | 현재 모델이나 코드 출력이 아니라 요구사항과 검증된 사실에서 정한 기대 결과이다. |
| 정상 대조(negative control) | 오답을 잡는 평가기가 정상 표현까지 오답 처리하지 않는지 확인하는 사례이다. |
| 그림자 평가(shadow evaluation) | 실물 로봇을 움직이지 않고 입력·모델·상태/발행 기대를 비교하는 평가이다. |

(내가 의역해보자면, “말을 자유롭게 한다”는 것은 사실을 자유롭게 바꾼다는 뜻이 아니다. 같은 검증된 사실을 사용자의 맥락에 맞게 설명하고, 충분히 명확한 요청은 실제로 진행할 수 있어야 한다.)
